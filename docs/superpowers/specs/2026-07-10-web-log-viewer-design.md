# Web 日志查看设计

## 目标

为 Telegram KOL Research 提供统一、可持久化的应用日志，并在 Web 界面中提供一个可滚动分页查看的系统日志页，便于定位 Telegram 监听、信号处理、自动交易、Deepcoin 交互、后台任务及 Web 操作的问题。

## 范围

- 记录应用内 `INFO` 及以上级别的日志，保留已有异常堆栈。
- 同时写入控制台和项目数据目录下的轮转日志文件。
- 单个日志文件最大 10 MB，保留 10 个历史副本；超出后由日志处理器自动清理。
- 新增只读的日志页面，最新记录优先，默认每批 100 条，滚动到底自动读取更早记录。
- 页面提供手动刷新和日志级别筛选（INFO、WARNING、ERROR）。

不在本次范围内：将日志存入业务 SQLite 数据库、全文检索、用户权限系统、远程日志聚合。

## 架构

新增 `app_logging` 模块集中配置名为 `telegram_kol_research` 的根 logger。该 logger 使用 UTF-8 的 `RotatingFileHandler` 写入 `logs/telegram-kol.log`，并使用 `StreamHandler` 输出到服务标准输出。配置应具备幂等性，重复创建应用或重复调用配置函数不会重复附加 handler。

业务模块通过 `logging.getLogger(__name__)` 取得子 logger；Web 应用不再依赖只属于 Uvicorn 的 logger 名称。应用启动时调用统一配置，后续现有与新增的关键路径会沿用该 logger 命名空间。

日志页不访问数据库。读取层只接受由应用配置确定的日志目录，按当前文件和轮转副本组成的时间顺序读取文本行，将每条记录解析为时间、等级、logger 名和消息；无法解析的行作为连续文本归到上一条记录，避免多行异常堆栈被拆散。读取层对外提供基于 `offset` 与 `limit` 的稳定分页接口。

## 数据流

1. 应用启动配置日志输出位置与轮转策略。
2. Web 请求、后台任务和交易相关逻辑写入结构一致的应用日志；异常使用 `logger.exception` 保留 traceback。
3. 用户通过主界面“系统日志”入口进入 `/logs`。
4. `/logs` 渲染页面骨架；浏览器请求 `/api/logs?offset=0&limit=100`。
5. API 按最新优先返回日志条目、是否仍有更多记录和下一读取 offset。
6. 浏览器安全地以 `textContent` 渲染条目；滚动容器接近底部时自动请求下一批。刷新会清空当前列表并重新从最新一批开始读取。

## Web 界面

主页面现有顶部导航增加“系统日志”链接。日志页采用独立模板：顶部有返回主界面链接、级别下拉筛选和刷新按钮；下方为固定高度且可滚动的日志列表。每条日志展示本地时间、级别、logger 与完整消息。ERROR 条目以错误色强调，WARNING 以警告色强调，长消息与 traceback 使用等宽字体、保留换行并自动换行。

初始批次和后续批次均为 100 条。API 对 limit 限制为 1 至 200，非法 offset 或 limit 返回 HTTP 422。筛选在服务端完成，切换等级后重置 offset 并重新加载最新匹配记录。

## 可靠性与安全

- 若日志文件尚不存在，API 返回空结果而非错误；页面显示“暂无日志”。
- 若某个轮转文件在读取时被轮转或删除，跳过该文件并继续返回可读结果。
- 日志配置目录由应用参数或默认数据目录决定，不从 HTTP 请求接收路径，防止任意文件读取。
- API 响应与浏览器渲染都不将日志内容解释为 HTML。
- 业务日志仅记录操作结果和必要的追踪标识（如 message、signal、order、position ID）；不得记录 API Key、passphrase、签名、完整 Authorization 头、Telegram session 内容或完整敏感请求体。

## 测试

- 单元测试验证配置创建轮转文件、重复配置不产生重复 handler、写入内容可被读取。
- 单元测试验证跨当前文件和轮转文件的倒序分页、级别筛选、无文件与多行 traceback 的行为。
- Web 测试验证 `/logs` 返回页面，`/api/logs` 返回分页 JSON，并拒绝非法分页参数。
- 现有 Web 相关测试须继续通过。

## 部署

日志文件属于运行时产物，加入 `.gitignore`，不提交到 Git。服务器更新时继续使用现有 `scripts/server_git_update.ps1`：拉取已审查提交、重新安装 editable package、重启 `telegram-kol.service`。部署后通过 `/logs` 验证服务启动记录和最新请求记录可见。
