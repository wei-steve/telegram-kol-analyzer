## 4. 失败了会怎样

| 情况 | 处置 |
|---|---|
| 交易所明确拒绝 | 立刻冻结，不重试，记 `convergence_submit_rejected` |
| 发出去了但不知道结果（超时/网络断） | 冻结为 `submit_unknown`，**不重发**，等人工看 |
| 发出去了、回执有单号，但随后查挂单查不到 | 冻结，记"回执与挂单不一致"，等人工看 |
| 第一张成功、第二张前发现仓位变了 | 停在第一张，不发第二张 |

**没有任何一条路径会自动重发或自动加仓。** 最坏情况是"挂了一半"，而不是"挂重了"。

## 5. 必须说清楚的一件事：批准之前，系统会把这四张单反复"算完再扣住"

代码里现在多了一份**释放名单**，默认是**空的**。名单里没有的仓位，系统每一轮都会：

1. 把整套止盈计划**完整算一遍**（就是第 3 节那四张单），
2. 把"本来会发出什么"**记进审计**（仓位号、每档价与量、用哪个端点），
3. **然后停手，一张不发。**

所以在您批准之前：**交易所上的止盈数量恒为 0**，而"将要发出什么"是有账可查的、每轮都在复核的。
您批准之后，我们把这两个仓位号加进名单，同样这四张单才会真的发出去。

**这样做的理由**：把"代码是不是对的"和"要不要开始下单"拆成两件事。
前一件已经由测试和演练证明；后一件不该由我们代替您决定。

## 6. 这些数字是怎么来的（可复核）

- 仓位与挂单：用生产 worker 自己的凭据只读查交易所，凭据未落盘、未打印。
- 4 张单的价与量：把生产库**复制一份**，在副本上跑**真实的计划器函数**，打印它准备发出的报文。副本用完即删，生产库核对过未被触碰（两行仍是 `conflicted`，四条腿仍是 `planned`）。
