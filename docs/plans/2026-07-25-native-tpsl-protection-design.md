# DeepCoin 原生 TPSL 保护设计

## 目标

让真实持仓的主止损、第二止损和分批止盈遵循 DeepCoin 原生 TPSL
语义，并在交易所手机端的“止盈止损”列表中可见、可核对。所有迁移
必须先创建并验证新订单，绝不在仓位无保护时撤销旧订单。

## 订单阶段与 API 归属

### 未成交的限价/条件入场委托

尚无精确 `posId` 时，主止损仍附着在入场委托上。新建委托传递
`slTriggerPx`、`slTriggerPxType=last` 和 `slOrdPx=-1`；已有可识别的
委托订单使用 `replace-order-sltp`。此阶段不得调用 `set-position-sltp`。
分批止盈继续等待成交和精确分仓归属。

### 已成交的精确分仓

市场入场在取得并验证 `posId` 后，使用 `set-position-sltp` 创建主止损。
第二止损同样使用该 API，以 `slTriggerPx` 创建一条独立的原生 TPSL
市价止损，价格位于主止损风险方向外 20 bps。每个止盈目标使用同一 API
创建独立的原生 TPSL 市价止盈，`tpTriggerPx` 为目标价、`sz` 为经过合约
步长校验的分批数量。

## 原生 TPSL 识别

DeepCoin 的待挂 TPSL 行可能省略 `posId`。匹配顺序为：

1. 本系统已持久化的 `ordId` 精确匹配；
2. 否则匹配合约、方向、TPSL 类型、建仓/订单时间，以及精确数量；
3. 对 `sz=0` 的全仓止损，允许作为该精确分仓的全仓保护候选，但只在其余
   身份条件唯一时接受；
4. 任一候选不唯一、字段冲突或读回不完整均冻结，不猜测归属。

人工订单不被系统接管。检测到手工 TPSL 且不能由现有系统订单 ID 精确
归属时，自动迁移和补单对该分仓冻结并生成可审计原因。

## 迁移与故障策略

系统拥有的旧通用 `trigger-order` 第二止损迁移为原生 TPSL 时：

1. 读取精确实时持仓、原止损、现有 TPSL 和旧触发单；
2. 保留旧单，提交新的原生 TPSL；
3. 按新 `ordId`、类型、价格、方向、数量/全仓语义回读；
4. 仅在读回完全一致后取消同一分仓、同一系统拥有的旧通用第二止损；
5. 新单提交、读回或取消结果不明时停止并冻结，保留现有保护订单。

分批止盈迁移同样先创建、回读并记录每一条原生 TPSL，旧止盈单只有在全部
新目标均验证后才可取消。已有人工 TP/SL、主止损未验证、仓位归属不唯一或
数量计划不完整均不执行迁移。

## 验收条件

- 未成交限价/条件入场继续通过委托级 TPSL 保护；
- 已成交分仓的第二止损和每个分批止盈显示为原生 TPSL；
- 每个系统订单都有精确订单 ID、价格、方向、数量和回读证据；
- 迁移过程没有任何时段缺失主止损或已验证旧保护；
- 手工订单不被修改或撤销；
- 所有冲突和不确定结果保持冻结、可审计且不可自动重试。
