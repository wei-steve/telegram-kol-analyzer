# "保本类"管理指令被附带数字误拒：分析与修复方案

日期：2026-09-21
状态：分析完成，修复方案待用户批准；未实施
来源：Codex 值守补救的首个真实回放（`docs/codex-oncall-status.md` 8.7，raw 17813）
关联：`docs/2026-09-05-management-stop-price-gate-result.md`（闸门原设计）、`docs/management-reliability-status.md` 第 180 行（2026-09-08 同类事故与 step 3b）

## 1. 现象

2026-09-20 北京时间 11:37，大镖客 11分组：

> 早上在81200附近看到提醒进了空的，现在你就移动止损……所以在这个成本开的空可以**减仓移动止损到成本**做无风险持仓

系统识别为 `partial_then_break_even`（减半后保本）——**识别正确**。但候选同时带着 `stop_loss_text = "81200"`，
计划器以 `management_stop_action_conflict` 把**整条指令**拒绝：既没减仓、也没移止损。
BTC 空单带着 82300 的原止损继续持有 6 小时 24 分，直到 18:01 KOL 喊离场。

## 2. 根因

`management_stop_price_gate.stop_action_conflicts`（`management_stop_price_gate.py:46`）：

```python
return action in IMPLICIT_STOP_ACTIONS and (
    stop_mode == "explicit_price" or stop_price not in (None, "")
)
```

动作属于"保本类"（`partial_then_break_even` / `move_stop_to_break_even` / `break_even_by_market`）**且**带了任何明确价格 → 拒绝整条指令。
该判定在三处生效：计划器入口（`strategy_management_planner.py:528`）、`validate_management_stop`、执行前复核 `validate_batch_stops`。

设计初衷（2026-09-05）：保本动作的止损价本应由系统取"实际开仓均价"，消息又给了一个明确价，两者语义矛盾，宁可不做。
**问题在于这条规则默认"附带的数字是 KOL 想要的另一个止损价"，而生产数据说明它从来不是。**

## 3. 生产上全部 3 次触发（只读点查，2026-09-21）

| 批次 / 消息 | 原话 | 识别动作 | 被当成止损价的数字 | 这个数字其实是 | 后果 |
|---|---|---|---|---|---|
| 160 / raw 15402（09-08） | 第一止盈位已过，注意锁定利润，及时移动止损 | `partial_then_break_even` ✔ | 签名里的 QQ 号 `158241758` | 不是价格 | ETH 空单止损留在 2530，两天后人工平仓 |
| 161 / raw 15475（09-08） | **最低2450**，第二止盈位已到，注意锁定利润，及时移动止损 | `move_stop_to_break_even` ✔ | `2450` | 刚走出的最低价；对空单而言在现价下方，**不可能是止损** | 同上 |
| 169 / raw 17813（09-20） | 在这个成本开的空可以减仓移动止损到成本 | `partial_then_break_even` ✔ | `81200` | **成本价本身**（策略入场区间 80500–81600 之内） | BTC 空单止损留在 82300 六个多小时 |

三次的共同点：**动作标签每次都对；附带数字没有一次是"另一个想要的止损价"；三次都是整条拒绝、零操作。**

2026-09-08 之后已上线的 step 3b（`management_price_plausibility.py`，在闸门**之前**运行）只处理第一类：
数字与现价相差 10 倍以上 → 视为"消息没给价格"，按保本继续。它挡得住 QQ 号，挡不住后两类（数量级完全正常）。

## 4. 修复方案

**思路：沿用 step 3b 的既有机制，不动闸门。** 在同一个"闸门前剔除器"里，对保本类动作再认两种"这个数字不是新止损价"的情形；
认出来就和 3b 一样把它当作"消息没给价格"，改写内存中的候选视图与合约（`stop_mode → actual_entry_price`），后续流程与今天的正常保本完全一致。
**闸门的每一条规则原样保留**；认不出来的，照旧拒绝。

| # | 情形 | 判据（全部确定性，不含 AI） | 覆盖 |
|---|---|---|---|
| F1（已有） | 数量级不对 | 与现价相差 > 10 倍 | 15402 |
| **F2（新）** | **复述成本** | 数字落在该策略自己的入场区间 `[entry_range_low, entry_range_high]` 内（含端点）；或已知实际开仓均价时，与均价相差 ≤ 0.3% | 17813 |
| **F3（新）** | **不可能是止损** | 多单：数字 ≥ 现价；空单：数字 ≤ 现价（这样的"止损"一挂就触发，任何情况下都不是可执行的保护价） | 15475 |
| （不变） | 合理的、方向正确的、又不在入场区间里的另一个价格 | —— | 仍按 `management_stop_action_conflict` 拒绝 |

为什么 F2 用"入场区间"：KOL 说的"成本"就是他自己的入场价，按定义落在他给出的入场区间里；而系统的保本价取的是**我们自己的**实际开仓均价，
所以剔除这个数字不会改变最终挂出去的止损——它只是不再否决整条指令。0.3% 的均价容差用于没有入场区间的纯市价策略。

为什么 F3 安全：对空单，低于现价的止损会立刻触发；交易所也不会接受。一个不可能成为止损的数字，不应该有资格否决一个识别正确的保本动作。
F3 需要可用的现价报价；**报价不可用时不做 F3 判断**（与 3b 相同的边界：未知绝不放宽）。F2 不需要报价。

最后一行保持拒绝的理由：生产上没有这种样本；真遇到时是真歧义（"保本"还是"移到 80900"），而值守进程现在会在 2 分钟内告警。
等有样本再决定是否"先执行无歧义的减仓、只拒止损部分"。

### 4.1 改动范围

- `management_price_plausibility.py`：`sanitize_management_prices` 增加可选入参（`side`、`entry_range_low`、`entry_range_high`、`actual_entry_prices`），
  增加 F2 / F3 两种 finding（带 `disposition` 字段：`implausible_magnitude` / `restates_entry` / `not_a_possible_stop`）；
  合约与 `stop_loss_text` 的中和逻辑复用现有代码。模块 docstring 的"两条边界"保留并补充。
- `strategy_management_planner._identity_without_implausible_prices`：把 lifecycle 的入场区间、方向传进去；
  报价读取保持一次；无明确价格时仍然零市场读取。
- 记录：剔除证据照旧写进批次的 `target_snapshot`。事故台账——F1 保持现有 `management_price_implausible`（高）；
  F2 / F3 记为新类型 `management_price_not_a_stop`（**低**，不进 Telegram 类型表：这是"系统做对了"，不该再制造一条告警）。
- **不改**：闸门、执行器、识别提示词、任何设置、任何开关。`adjust_stop_loss` 完全不受影响（那里价格就是指令本身）。

### 4.2 行为变化（需要你明确批准的部分）

上线后，**过去会被整条拒绝的这三类消息将真的在交易所执行**：减仓（如有）+ 止损移到我们的实际开仓均价。
这是真实交易所写入语义的变化，但方向单一：只会让"保本 / 减仓后保本"这种**减风险**指令从"不执行"变为"执行"，
执行路径就是今天正常保本指令走的那条（所有权闸门、先挂后撤、撤前回读、TU 归属全部不变）。不会产生任何新的开仓、加仓或放宽止损。

### 4.3 测试

- 三条生产样本各做一条回归（按上表的消息、动作、数字、方向、入场区间、当时现价构造），断言：不再 `blocked`，合约 `stop_mode=actual_entry_price`，
  `target_snapshot` 里有剔除证据与 `disposition`。
- 反向：合理的另一个价格（空单，现价 80900，入场区间 80500–81600，消息给 82000）→ 仍然 `management_stop_action_conflict`。
- 边界：端点取等；无入场区间且无均价 → F2 不触发；报价不可用 → F3 不触发而 F2 照常；`adjust_stop_loss` 带同样数字 → 完全不经过剔除器；
  多单镜像用例；数字同时满足 F1 与 F3 时只记一次、`disposition` 取 F1。
- 执行前复核 `validate_batch_stops`：对已中和的合约不再报冲突（断言持久化的是中和后的合约与指纹）。
- 既有 3b 测试、闸门测试、复合执行器测试全部保持通过；最终候选跑一次全量。

### 4.4 验证等级与部署

- **L3**（真实交易所写入语义变化）：本方案即"确切的变更与回滚计划"。无 schema 变化、无数据修复，不需要生产库副本演练。
- 部署：`tg-deploy <sha>`（会重启 worker / web / ingest，用户已确认可以；选零在途窗口）。**自动交易开关全程不动。**
- 回滚：`tg-deploy <上一个生产 sha>`。回滚后行为回到"整条拒绝"，不留任何持久状态差异（剔除只发生在内存视图与新批次的合约里）。
- 上线后观察：值守进程（届时应为 `notify`）会对任何仍被 `management_stop_action_conflict` 拒绝的消息告警；
  首个命中 F2 / F3 的真实消息，逐项核对交易所上的减仓与新止损（L3 首笔实盘样本核对）。

## 5. 可选的第二步（不建议与上面捆绑）

识别提示词里补一句："保本类动作不要把成本价、已到达的止盈位、行情高低点填进 `stop_loss`"。
能从源头减少这类候选，但它改的是识别权威、验证成本高、且模型未必稳定遵守；第 4 节的确定性修复不依赖它。建议先上第 4 节，观察一到两周再决定。
