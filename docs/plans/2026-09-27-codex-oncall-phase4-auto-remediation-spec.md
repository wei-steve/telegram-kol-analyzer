## 1. 为什么要自动，以及它改变了什么

用户的判断：人工批准很难及时，错过时机就没有必要再批。生产数据支持这一点：`/choose` 从未被用过、5 条确认全部超时（总设计 7.1），
需要补救的真实目标约**每两天 1 条**，而最有价值的补救（全平、保本）都对时效敏感。

阶段 3 的安全来自三道闸门：G-A 提案闸门、G-B 批准闸门（**人**：判断参数与时机、确认身份、两次点击）、G-C 执行闸门。
阶段 4 **去掉 G-B**。所以要回答的只有一个问题：**G-B 里那个人替系统挡掉了什么，现在由什么确定性检查挡？** 第 4 节逐条回答。

不变的东西：
- 执行参数仍然**只**由 worker 从生产库和交易所快照重算；请求里只有案件号与消息号。
- Codex 仍**不在权限路径上**，诊断照旧只是给人看的文字。
- 仍然只走 `apply_position_management_remediation_action` → `execute_management_batch`，主链路的全部检查原样生效。
- 只做减风险动作；永不开仓 / 加仓 / 放宽止损 / 撤止损 / 改杠杆。
- 不碰任何自动交易开关，不写 `groups.yaml` / 交易设置。

## 2. 模式

`TELEGRAM_KOL_ONCALL_REMEDIATION_MODE` 新增取值 `auto`：`off < shadow < approve < auto`。

- `auto` 下每条提案先过 G-A 与第 4 节的自动闸门 G-D：
  - 全部通过 → 不发按钮，直接进入 G-C → apply，执行后发通知（第 7 节）。
  - G-A 通过、G-D 不过 → **降为只提示**：发阶段 3 的只提示提案消息，并写明"未自动执行：<G-D 理由>"。
    是否同时附批准按钮见第 11 节第 4 条。
- **分动作放开**：`TELEGRAM_KOL_ONCALL_REMEDIATION_AUTO_ACTIONS`（逗号分隔的 `action_kind`，默认空）。
  不在其中的动作即使 `MODE=auto` 也只走只提示。放开顺序见第 9 节。
- 未配置 `AUTO_ACTIONS` 或为空 → `auto` 等价于 `shadow`，启动日志写明。

## 4. 去掉人工批准后的补位（G-D 自动闸门，全部在 worker 内、零 AI）

人在 G-B 里实际做的判断，逐条换成确定性检查：

| # | 人会看出来的问题 | G-D 检查 | 数据来源 |
|---|---|---|---|
| D1 | "这条消息当时没执行的原因，现在真的消失了吗？"（A7 只挡住已知的不可推翻原因；不认识的原因，人会犹豫） | **原因白名单**：源指令项 / 批次的原失败原因必须属于下列"瞬时"原因之一，否则只提示：`prior_partial_batch_unresolved`（且前驱已收口）、`target_strategy_binding_visibility_retry_expired`（且此刻仓位在）、`exchange_snapshot_incomplete` / 快照读失败、`close_final_preflight_failed`、`protection_missing_cancellable_order_id`；**未知原因一律只提示** | 指令项 `error_json` / `result_json`、同消息批次 `reason_code` |
| D2 | "KOL 后来又说了别的吗？"（撤回、改价、已离场） | **没有后继消息**：同一 lifecycle（或同一 strategy_instance）在源消息之后没有任何管理类候选或管理批次，不论状态如何；有就只提示 | `signal_candidates.target_lifecycle_id` 索引、`strategy_management_batches.strategy_instance_id` 索引 |
| D3 | "我自己手动动过这个仓位吗？" | **仓位自消息以来未被人为改动**：此刻交易所上的仓位数量、保护单集合（按 `TU` / `ordId`，不读仓位行 `slTriggerPx`，见 ARCHITECTURE 4.8）与账本 / 执行事件在消息发布时刻之后的记录一致；出现账本解释不了的变化 → 只提示 | 快照 + `position_protection_ledger` + `execution_events`（按绑定索引） |
| D4 | "这个价下去会不会立刻被打掉 / 离市价太近？" | 止损类：新止损在市价正确一侧，且距离市价 ≥ `AUTO_MIN_STOP_DISTANCE_PCT`（默认 0.3%，按币价比例，同入场阈值口径）；否则只提示 | 同一次快照的行情（`get_ticker_quote`，与止损网关同源同新鲜度要求） |
| D5 | "保本会不会变成市价平仓？"（阶段 3 提案文案里特意写出这一可能） | **用户裁定（第 11 节第 5 条）：允许**。`move_stop_to_break_even` 越过保本价时自动改为市价平仓；D5 不再拦截，只把计划器实际走的分支（挂保本止损 / 市价平）记入审计与通知，让用户事后看得到 | 计划器 `reserve_break_even_market_actions` 的判定结果 |
| D6 | "系统现在稳吗？" | **系统健康**：worker 启动已满 5 分钟；近 10 分钟没有对账快照错误、没有事件循环卡顿告警、没有 `severe_protection_incident`；否则只提示 | 进程启动时刻、`runtime_incidents` 按时间索引 |
| D7 | "还来得及吗？"（人会判断时机） | **更短的自动时效窗**（从消息发布算）：`full_exit` 15 分钟、`partial_take_profit` 10 分钟、`move_stop_to_break_even` 30 分钟、`adjust_stop_loss` 30 分钟；超出自动窗但仍在阶段 3 窗内 → 只提示 | `raw_messages.posted_at` |
| D8 | "今天已经补了好几次了" | **更低的限额**：自动执行每天 ≤ 3 笔、同一群每天 ≤ 2 笔、同一 lifecycle 一生 1 笔（A10 已是每消息每意图一次）；同一 lifecycle 冷却 30 分钟 | 提案表 |
| D9 | "这类动作我见过它做对吗？" | **分动作证据门槛**：某动作要进 `AUTO_ACTIONS`，状态文档 9.4.7 里该动作须有 ≥ 3 条"自动执行会是对的"的只提示样本，且没有任何一条"会是错的"。这是放开的前置条件，由人按证据改配置，不做成运行时查询 | 状态文档 + 部署清单 |

所有 G-D 检查都写 `events`（`gate='D'`、`check`、实际值、阈值）。任何一条失败的去向都是**降为只提示**，不是拒绝。
G-D 自身抛异常 → 只提示，并计入第 8 节的异常计数。

## 5. 执行流程（`auto`）

```
值守建案 → POST 端点（不变）→ worker 后台任务：
  G-A 通过 → G-D 全部通过 → 提案 state=proposed（approver=auto）→ 立即 CAS proposed→executing（库内单飞 + 进程锁）
  → G-C（同 scope 重建计划、指纹逐字相等、执行时刻再判 D7 自动窗与 A8）→ apply
  → 跟随批次终态（阶段 3 的 finalize，跟随超时见第 11 节第 6 条）→ 执行后回读 → 通知
```

- 从"提案通过"到"进入 apply"之间不留等待窗，所以阶段 3 的"指纹漂移"风险在 `auto` 下基本消失（没有人点击的那几分钟）。
- `plan_changed` 仍只拒绝本次、不计熔断（2026-09-26 裁定），并降为只提示。
- 执行后**回读**：批次终态之后，额外读一次交易所快照（同 scope），核对预期效果（仓位数量、止损价、保护单集合）是否达成，写入审计表。
  回读不符 → `uncertain` 处理（第 8 节）。

## 6. 审计记录

### 6.1 为什么另加一张表

`oncall_remediation_events` 只记闸门与状态变化的摘要（`detail_json` ≤ 2 KB）；交易所请求与响应散在
`execution_events`、`position_mutation_intents`、`strategy_management_legs` 的 `request_json` / `response_json` 里。
用户的要求是**每一笔都能从一处完整倒查**，而且不受其他表今后任何保留期策略的影响
（2026-09-26 的磁盘方案只动 TP/SL 观测表与上下文解析请求全文，不碰上述执行表，但审计不应依赖这一点）。

### 6.2 新表 `oncall_remediation_audit`（每笔自动或人工批准的执行一行，只 INSERT；终态时再 INSERT 一行"结果"，不 UPDATE）

| 字段 | 内容 |
|---|---|
| `proposal_id`、`phase` | 所属提案；`pre_apply` / `result` |
| 触发 | `case_key`、`case_no`、值守规则、`raw_message_id`、`chat_id`、群名、`posted_at`、源指令项 id / 状态 / 原失败原因、候选 id |
| 目标 | `lifecycle_id`、`strategy_instance_id`、`execution_binding_id`、`pos_ids`、scope JSON |
| 执行前仓位 | 交易所快照中目标仓位的数量、均价、方向、保护单集合（`TU` / `ordId` / 触发价 / 数量）、快照指纹、行情价与时间 |
| 闸门逐项结果 | A1–A12、D1–D8、C1–C4 每一条：`check`、`passed`、实际值、阈值 |
| 重算的参数 | `action_kind`、`action_id`、指纹、`expected_effect`（比例 / 止损价 / 是否保量）、计划器给出的有效动作（如 `break_even_by_market` 的分支） |
| 交易所往来 | 该批次所有 legs / components / `position_mutation_intents` / `execution_events` 的 `request_json` 与 `response_json` **原样复制**（交易所请求体不含密钥；复制时再过一遍脱敏正则，与值守阶段 2 同一套） |
| 结果 | 批次终态、`reason_code`、执行后回读（仓位数量、保护单集合）、预期是否达成、耗时（发布→建案→提案→apply→终态） |
| 通知 | 执行后通知的 Telegram `message_id` 与发送结果 |

- 单行上限 64 KB（CHECK）；超限时按"先砍最旧的 `execution_events` 响应体"顺序裁剪并记 `truncated`，与值守案件包同法。
- 数量级：约每两天 1 笔 × 2 行 × ≤ 64 KB，一年 < 25 MB。
- **保存期：永久**（不纳入任何保留期任务）。若以后要清理，只能导出到 `/var/backups/telegram-kol/` 并留 sha256 后再删，另行批准。
- 只 INSERT：代码里没有 UPDATE / DELETE 该表的路径（静态断言，同 `events`）。
- 提供只读 CLI `oncall-remediation-audit <提案号>`，把两行合并打印成一份可读报告，供倒查。

## 7. 执行后通知（系统 bot，纯文本、中文）

每一笔自动执行都发，**不受每日提案消息上限约束**：

```
🤖 已自动补救 P<n>（值守 #<案件号>）
消息：<群名> #<raw_message_id>（<北京时间>），距发布 <m> 分钟
动作：<币种> <多/空> <动作中文>
结果：<例：新止损 2484 已挂并回读确认，旧止损已撤净 / 仓位已减至 0.5 / 已全部平仓>
依据：参数由系统从生产数据重算；原因「<原失败原因中文>」已消失
倒查：/audit P<n>
```

- 失败：`❌ 自动补救失败 P<n>：<理由>。自动补救已暂停，改为只提示。`（见第 8 节）
- 结果未知：`⚠️ 自动补救结果未知 P<n>：<理由>。自动补救已暂停，请人工核对交易所。`
- 降为只提示时：沿用阶段 3 的只提示提案消息，末尾加一行"未自动执行：<G-D 理由中文>"。
- **首 N 笔**（每个动作的前 5 笔自动执行）：通知末尾加"这是 <动作> 的第 k 笔自动补救，请回看"，
  并把状态文档 9.4.7 的核对表延续为"自动执行核对表"，每笔逐项核对后才算数。

## 8. 失败即关闭与一键关停

- **熔断更严**：`auto` 下任何一笔真正进入执行后的 `failed`，或任何一笔 `uncertain`，或执行后回读不符 → **立即**把补救降为 `shadow`
  （`control.auto_suspended = 1`，写 `events`，发通知）。不是阶段 3 的"连续 2 次"。恢复只能由批准人在系统 bot 发 `/auto_on`（过 B1 校验、写 `events`）。
- G-D 或后台任务异常连续 3 次 → 同样降为 `shadow`。
- **一键关停**（都不碰自动交易开关）：

| 层级 | 操作 | 效果 |
|---|---|---|
| 只停自动 | 系统 bot `/auto_off`（批准人） | 立即降为只提示；在途的 `executing` 不中断（中断更危险），其余照旧 |
| 停全部补救 | 系统 bot `/oncall_off` | 阶段 3 原样：作废在途提案 |
| 配置 | worker env `MODE=shadow` 或清空 `AUTO_ACTIONS`，重启 worker | 重启后生效 |
| 值守不再请求 | 值守补救 env `REQUESTS=off`，重启值守 | 下一轮生效 |

- 重启时 `executing` 的处理沿用阶段 3（无批次号 → `uncertain` 并暂停自动；有批次号 → 继续跟随，绝不重跑）。
- 回滚代码前先 `/oncall_off` 并确认 `executing` 为 0（同阶段 3）。

## 9. 分动作逐步放开的顺序

每一步都是单独的配置变更与单独的确认；每一步的前置条件是 D9 的证据门槛，以及上一步的首笔实盘样本逐项核对通过。

| 顺序 | 动作 | 理由 |
|---|---|---|
| 1 | `full_exit` | 生产上执行路径跑通最多（30 天 12 次成功）；纯减风险；参数只有"全部"，没有价格可错 |
| 2 | `move_stop_to_break_even`（含越过保本价时的市价平仓分支，第 11 节第 5 条） | 生产 3 次成功；价格来自入场价而非消息原文；市价平仓分支按用户规则允许，结果在通知里写明走了哪个分支 |
| 3 | `partial_take_profit` | 生产 2 次成功；比例来自消息，最容易被误读；部分止盈批次的收口时长待只提示期核对（状态文档 9.4 裁定 2） |
| 4 | `adjust_stop_loss`（仅收紧） | 生产 30 天**零次**执行；阶段 3 刚修掉一个让它必然失败的缺陷（`53c0de14`）；价格来自消息原文，最依赖识别质量，放最后 |

`partial_then_break_even`、`adjust_take_profit`（G1）、`/choose` 之后的项（G2）、G3 批次在本阶段仍然排除。
