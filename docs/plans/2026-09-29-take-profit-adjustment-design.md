- 日期：2026-09-29
- 基线：`origin/main` = `6450ac67`（生产 `0bcb894e`，两者之间只差文档）
- 状态：**设计待用户拍板，未写代码**
- 风险级别：**L3**。原因：新增一个会写交易所的生产者，执行「撤止盈单 + 挂新止盈单」。识别和规划两层属于 L1/L2，但整个功能按 L3 管理。

   **这是比「卡住」更危险的一面：方向错了。**

## 2. 根因（代码定位）

### R1 管理层没有「调止盈」这个意图（G1，仍然成立）

- `management_directives.resolve_management_directive` 完全不读 `lifecycle_event.take_profit`，
  判断顺序里也没有止盈调整分支。只改止盈的消息会落到 `intent="none"`，原因码 `no_actionable_risk_reduction`。
- `strategy_management_planner.SUPPORTED_INTENTS`（第 138 行）只有 `partial_take_profit`、`full_exit`、
  `adjust_stop_loss`、`move_stop_to_break_even`、`partial_then_break_even` 五个。
- `signal_candidates.take_profit_text` 在整个管理路径里**没有任何读取点**：只写不读。
- 交易所一侧其实已经有这个能力：`deepcoin_execution_actions.adjust_position_tpsl` 支持
  `adjust_take_profit`，`protection_replacement.replace_take_profit_group` 也实现了
  「先撤旧 → 确认撤净 → 再挂新」。但**没有任何自动生产者调用它们**。

### R2 百分比一律被当成「现在平掉这么多」

`_has_partial_clause`（`management_directives.py:435`）只要看到下面任一条件就判为减仓：
消息里有百分比；`_PARTIAL_TERMS` 里的词（包括「分批止盈」「第一止盈」）；「一半」；「半仓」。
它分不清以下两种说法：

- 「止盈 50%」：执行动作，现在平掉；
- 「两个止盈位各 50%」「设置自动止盈 50%」：止盈单的分配比例，挂在未来的价位上。

后一种被当成前一种，就会**提前市价减仓**（18199 就是这样）。

### R3 止损价提取正则会吃到止盈价

`message_recognition._extract_explicit_stop_loss_from_management_text` 的第一个模式是：
`(?:止损|…)[^0-9]{0,20}([0-9.]+)`。它先命中标题里泛指的「止盈**止损**」，
然后跨过换行，抓到「止盈位：73070」里的数字。8 条样本全部复现：`stop_loss_text == take_profit_text`。
如果换成开了自动交易的群，就会生成一条「止损 = 止盈价」的 `adjust_stop_loss`。
对空单来说这个价在现价下方，大概率被止损价闸门拒掉，但这纯属侥幸。

### R4 止盈收敛器会把止盈拉回入场时的计划

`trigger_take_profit_convergences.desired_take_profits_json` 在入场时写一次，之后再也不变。
`trigger_take_profit_convergence_executor._prepare_plan` 看到本单名下的止盈价位或张数
和这份计划不一致，就返回 `convergence_owned_take_profit_mismatch`，状态变成 `conflicted`，
直到仓位关闭都没人处理。快照里 binding 345 / 346 就是这样
（原因是止盈成交，不是调止盈）。
**所以即使只补上 R1，只要不同时改写这份计划，改完的止盈单也会让收敛器进入冲突态。**
这正是「比例一变就卡住」在代码里对应的位置。

### 会不会连带挡住同一仓位的其它动作

- **现在不会**。`blocked` 是终态，唯一索引 `uq_strategy_management_batches_active_strategy`
  只约束**非终态**批次（`status NOT IN ('succeeded','blocked','resolved')`），
  所以之后的保本和平仓照常规划。
- **修好之后就会**：新增的调止盈批次在执行期间会占住这个唯一槽位，
  这时来的保本或平仓会被挡住。所以第 3.6 节的「截止时间 + 可被取代」是硬要求，不是可选项。

## 3. 修法

### 3.1 目标语义（推荐，待确认）

**按 KOL 的新结构重建我们「剩余仓位」上的止盈单，而不是只改价位。**
理由：用户说的「卡住」正是结构对不上；KOL 说的比例指的是**当前持仓**。

对每个仓位（每个 `pos_id` 单独算；两条入场腿就算两次）：

1. **基数**：交易所实时 `pos`，也就是剩余张数。已成交的档位不再参与分配。
2. **价位**：
   - 本条消息里明确写出的价位（必须能在原文里找到，沿用 `_text_contains_explicit_stop_value` 的做法）；
   - 消息只给比例、没给价位（18199）：用**策略价** `lifecycle.take_profit`，与「价位取策略价」的规则一致；
   - 两者都没有：**拒绝并提醒**（18294），绝不退化成减仓。
3. **比例**：
   - KOL 给了各档比例且合计 100（「各 50%」按档数展开）：照用；
   - 只给了部分档位的比例（14306：「79100 挂 50%」）：**只替换对应档位**，其余档位保持原样，见问题 Q3；
   - 没给比例：档数没变，就沿用我们现有的比例；档数变了，就用入场时那张默认表
     （1:100、2:50/50、3:40/30/30……，`take_profit_plan._allocations`），见问题 Q2。
4. **已成交的档**：账本 `filled` 的档是历史，不撤、不补。KOL 的新列表里如果还包含这个价位
   （例如重复列出已到的第一止盈），这一档视为已经消耗掉，从新计划里去掉。
5. **现价已经越过的档**（多单价位 ≤ 现价，空单价位 ≥ 现价）：这种单挂不上去，或者挂上就立刻触发。
   推荐做法是去掉这一档，份额按比例并入其余档，并提醒用户，见问题 Q4。
6. **止损不在这条路径里改**，除非同一条消息也明确给了止损（欧阳模板）：
   这时先改止损、后改止盈，止损沿用现有的 `adjust_stop_loss` 规则和闸门（见 3.4）。

### 3.2 张数：最小下单量、步长、除不尽

直接复用 `trigger_take_profit_convergence_executor._allocate_sizes`：

- 每档按比例向下取整到步长，**余数给最后一档**（与入场时的规则相同）；
- 某一档低于最小张数时，**从最远的档开始减档**，剩下各档重新归一到 100%。
  这是用户 2026-09-08 定的 `small_position_tiering_shrink_to_allocatable`；
- 连一档都挂不出来（剩余张数 < 最小张数）：拒绝，原因码 `take_profit_adjust_size_below_minimum`，
  **保留现有止盈单不动**，并提醒。

### 3.3 不用改就不改（幂等）

算出目标集合 `{(价位, 张数)}` 以后，和本单名下现有的有效止盈单**精确比较**。
完全一致就直接判成功（`take_profit_adjust_already_satisfied`），不做任何写入，只发一条「已一致」的通知。
18199 回放会落到这里：15 张按 50/50 拆出来就是现在的 7/8。

### 3.4 执行顺序与写入

复用现有部件，不新写下单代码：

1. 在 `position_authority_lock` 下读实时仓位、完整的 `trigger-orders-pending`，
   并用 `resolve_protection_authority` 解析保护集合。任何一项读不全都算「不知道」：
   拒绝，**零写入**。
2. 如果同时改止损：`replace_stop_group`（先挂新，确认后再撤旧），失败就按现有规则冻结和告警，
   **这时不再动止盈**。
3. **先在同一个事务里把收敛计划改成新目标**（`desired_take_profits_json`），
   并把旧止盈保护腿标成 `superseded`（解决 R4）。
4. `replace_take_profit_group`：先撤旧，按 ordId 精确回读，确认撤净，再挂新，再回读。
   沿用现有语义：
   - 撤单失败：旧止盈保持武装，没有挂任何新单，记 `take_profit_replace_incomplete`，批次 `blocked`，提醒；
   - 撤完但挂新失败：仓位仍有止损，不是裸仓。记同一事件，批次终结，
     之后由**止盈收敛器按新计划重试**（第 3 步保证它追的是新计划，不会拉回旧计划）。
5. 账本、`position_take_profit_orders`、保护腿三处都由现有的网关和写入点落库，不新增写入点。
   止损阶梯只看账本里的止盈行，会自动跟着新档位走，已成交的档仍然算第 1 档。

### 3.5 识别与规范化

- `resolve_management_directive` 新增意图 `adjust_take_profit`。判断位置**放在 `has_partial` 之前**，满足以下任一条件即可：
  - 模型给出的 `management_action` 包含 `take_profit`、`set_take_profit_plan`、`adjust_take_profit`
    这类「计划」词，而不是 `partial_take_profit` 或 `*_reached`；
  - 原文有「止盈位：X」「止盈改到 / 上移 / 下移 X」「设置（好）止盈」「剩下看向 X 目标位」。

  同时必须满足：**没有现在就执行的动词**，比如「止盈了」「先出」「平掉」「减仓」「现价 / 市价……止盈 X%」。
- 百分比判定：只有和「各 / 每档 / 分别 / 自动止盈 / 挂」这类词在同一分句时，才当作**分配比例**；
  其余情况仍然当作减仓，现有减仓路径不变。有歧义时**偏向不减仓**：挂止盈不会扩大风险，提前平仓是不可逆的。
- 修 R3：止损价只从「止损 / 止损位 / 损位 / 保护价 + 冒号或空格 + 数字」这种紧邻的标签形式里取；
  「止盈止损」连写不算止损标签。
- 同一条消息同时带止损（欧阳模板）：意图仍然是 `adjust_take_profit`，contract 里加一个止损子项，
  按 3.4 的第 2 步执行。

### 3.6 不能卡住

- 批次写 `execution_deadline_at = planned_at + 180 s`。超时由 `management_recovery_timeout` 收口，
  终态 `blocked / take_profit_adjust_deadline_expired`，并提醒。**不允许出现没有截止时间的状态。**
- **可被取代**：调止盈批次还没开始写的时候，新来的 `full_exit`、`move_stop_to_break_even`、
  `adjust_stop_loss` 可以取代它（加进 `_supersede_partial_batches_in_session` 的可取代集合），
  和 A-6「减风险指令不能被挡」的规则一致。已经开始写的，由截止时间兜底，最长 180 s。
- **每一个拒绝都要提醒**：走现有的管理通知（`strategy_management_notification`），
  通知文案给出原因码的中文解释，至少包括：没给价位、张数不够、档位已被越过、保护集合解析失败、撤单失败。
  现在最大的问题正是「静默」。

### 3.7 开关

新增设置 `take_profit_adjust_mode ∈ {disabled, shadow, live}`。
- `shadow`：完整走完识别、规划和目标计算，把「本来会怎么改」写进批次快照并提醒，**零交易所写入**。
- `live`：执行 3.4。
默认值见问题 Q5。关掉就回到今天的行为，但 R2、R3 的修复不受这个开关影响，一直生效。

## 5. 交付与风险

- **分两步交付，都在同一个候选里完成**：
  - (a) 只改识别和规范化：R2、R3、新意图、shadow 规划与提醒，零交易所写入；
  - (b) `live` 执行。

  本会话做到「候选 sha + 全量通过」为止，**不部署、不推 `origin/main`**。
