## 0. 结论速览

1. **0bcb894e 修好了「比例被误拒」，但米娅最常用的那句话在新代码上仍然不会执行。**

   但这句话会被当成**单纯的部分止盈**，止损价 P 又没有标记「来自本条消息」。执行器入口的止损门看到一个
   来源不明的止损价，就把**整批拒绝**（`management_stop_provenance_invalid`），所以减仓也不会执行。
   这不是推测：09-23 大镖客的两个减仓批次 177、178 就是这样被拦下的。受影响的是 #17900、#17901、#18154，
   以及今后所有同样写法的消息。
2. **#19597 在新代码上能执行，但止损不会放在 83200。** 它会减 5 张，剩余 5 张的止损放在**策略价 83800**。

   规则取策略价，83200 比 83800 更松，所以被弃用。按这个做法，09-28 那笔大约是 **0 附近收场**，实际是 **−9.10 USDT**。
   但执行时现价如果已经 ≤ 83800，剩余仓位该怎么处理还没有验证（见 M5）。
3. **平掉部分仓位、但不改止损的指令（「第一止盈位到了」），在所有群都会被同一道门拦下。** 原因是生成候选时，

## 2. 剩余问题、根因与修法

### M1 「止盈X%，剩余仓位止损位上移至 P」不执行（米娅主问题，所有群通用）

**根因**（三段串联，每段都用生产数据核过）：

1. 模型给这类消息的标签，通常只有 `partial_take_profit`，`stop_loss` 字段为空
   （#17900 / #17901 / #18154 / #18479 都是这样；只有 #19597 带了 `move_stop_to_protect` 和 83200）。
   `resolve_management_directive` 判断要不要保护，只看两样东西：保本词表，以及载荷里的 `stop_loss`。
   词表里没有「止损位上移至 / 移动至 / 无风险持仓」这类写法，于是结果是单纯的 `partial_take_profit`
   （`management_directives.py:315-335`）。
2. `_apply_lifecycle_event_decision` 会再从原文里抽止损价（`message_recognition.py:1509`），
   但来源取的是 directive 的 `stop_price_source`，而这里是 `None`（`message_recognition.py:1542-1546`）。
   抽不到的时候（#17900 只写了「剩余仓位上移至80600」），
   `_upsert_management_signal_candidate` 会把**策略原来的止损**当作止损价写进候选（`message_recognition.py:4795-4801`）。
3. 执行器入口 `validate_batch_stops`（`management_stop_price_gate.py:174-240`）把腿上所有 `stop_loss_text`
   都当成「消息明写的止损」处理，要求来源是 `current_message_text`，否则整批 `blocked`
   （`strategy_management_executor.py:1417-1420`）。部分止盈和止损捆在同一个批次里，所以减仓也一起丢了。

**修法**（只动 directive 解析，外加候选的来源字段）：

- a. 在 `resolve_management_directive` 里，如果**有部分止盈**，同时本条消息（不看载荷）能抽出一个「止损 / 剩余仓位」
  后面跟着的移动价 P（「止损位上移至 P」「剩余仓位上移至 P」「止损移动至 P」「止损下移至 P」），
  就把它当作 `current_message_stop`，来源记为 `current_message_text`。
  这样整条消息升级成 `partial_then_break_even`，走 09-28 已经在生产成功过的复合路径（批次 183）。
- b. 对 P 的处理完全交给现有的价格合理性模块。这个模块已上线并由用户裁定过，不做改动：
  - P 比策略保本价更紧，就采用 P；
  - P 更松、在错的一侧，或者离谱（比如 64100），就改用策略价。
  预期结果：
  - #17900 / #17901：减 2 张（7×0.4 向下取整），剩余止损放在 80700（策略第一腿价，80600 更松）；
  - #18154：减 4 张，剩余止损放在 84100。这正是 KOL 笔误想写的价。
- c. 「无风险持仓 / 做无风险」加进保本词表。它只影响「有部分止盈、却没写价格」的情况：这时保护价取策略价。
- d. 抽取正则补上「剩余仓位 / 剩余持仓 … 上移 / 下移 / 移动至 P」（#17900），
  并且要求 P 通过 `_is_plausible_management_stop_loss`。

**回放用例**：
- 用 #17900、#17901、#18154、#19597 的原文和真实载荷，从候选生成一路跑到规划器和止损门：
  修复前 `management_stop_provenance_invalid`，修复后 `ready`，比例和止损目标如上。
- 反例：
  - 「止盈50%」（不带价格）仍是单纯的部分止盈；
  - 「止损上移至 83200」（不带比例）仍走 `adjust_stop_loss`，行为不变；
  - 两个不同的止损价 → 仍然拒绝。

**风险**：L2（管理执行路径）。

### M2 只减仓、不改止损的指令被同一道门拦下（所有群）

**根因**：M1 第 2、3 段的另一半。候选把 `lifecycle.stop_loss`（策略原止损，没有变）写成了 `stop_loss_text`，
来源为空；执行器入口因为来源无效，整批拒绝。

**生产证据**：大镖客 09-23 的 #18543「第一止盈位到了」、#18578「精准踩到第二止盈位」，
批次 177、178 都是 `management_stop_provenance_invalid`，候选止损 2785 就是原止损。
09-05 以来，非复合部分止盈批次的结果：

| 批次 | 拦截原因 |
|---|---|
| 159、166、172、174 | `protection_price_or_size_mismatch` |
| 160、161、169 | `management_stop_action_conflict`（后来被价格合理性模块取代） |
| 177、178 | `management_stop_provenance_invalid` |

没有一次成功。

**修法**：
- 非保本类意图，如果本条消息**没有写止损**，候选不再抄原止损，`stop_loss_text` 为空，含义是「保留现有保护，按剩余张数缩量」。
- 实施时必须先核实：旧的部分平仓执行器（`execute_management_batch` → `_resize_protection_rows_for_remaining_position`）
  在没有计划止损时能不能只按剩余张数缩量。如果不能，就改为「不抄原止损，同时给这个值打上
  `stop_price_source='lifecycle_existing'` 标记，止损门对这个来源只校验它和现有账本止损一致」。二者选其一，以测试为准。
- 同时要查清 `protection_price_or_size_mismatch`（159 / 166 / 172 / 174）在当前代码上是不是还会出现。
  如果还会，就是第三道拦截，一并列进实施报告；**不在本稿里预设修法**。

**回放用例**：
- 批次 177 的真实结构（ETH 空单、原止损 2785、「第一止盈位到了」）：修复前 `provenance_invalid`，修复后规划 `ready`，执行器止损门放行。
- 反例：消息明写一个来源不明的止损价，仍然拒绝。

**风险**：L2。

**修法**：
- 在尾仓分支里调用 `_management_fraction(lifecycle_event, combined)`：
  - 取到明写比例就用它，同时区分「平掉 X%」和「保留 X%」两种语义；
  - 取不到才用 0.8；
  - 载荷和文本不一致时，沿用现有的 `management_fraction_ambiguous` 拒绝。
- 新增 `reason_code=tail_retention_explicit_percentage`。
- `has_protection` 为真时，意图升级为 `partial_then_break_even`。这和非尾仓分支一致。

### M4 加仓（#19514）：见 Q1，由用户选

### M5 复合「减仓＋保本」在保本价已被穿过时的执行（需在实施时验证）

- #19597 规划时现价取 83900、83800、83700，结果完全相同：都是 `ready`，剩余止损 83800。
  这里有一个问题：现价是 83700 时，多单止损放在 83800 是在错的一侧，交易所会拒单，或者立刻触发。
  非复合的 `move_stop_to_break_even` 在这种情况下会转成 `break_even_by_market` 市价平仓
  （批次 185 已成功）；复合路径没有这个分支。
- **修法**：实施时先写回放测试（复合批次、保本价在现价错的一侧），看执行器实际怎么做。
  - 如果是拒单或者挂起，就按用户规则「冲突即市价平仓」处理：剩余部分改成市价平。
  - 如果执行器已经能正确处理，只保留测试。

**风险**：L2。

### 8.1 与设计稿的差异

- **M5 不需要修代码。** 复合执行器 `replace_remaining_protection` 在保本价落到现价错的一侧时，已经会对剩余仓位市价平仓

- **M2 选了「不抄原止损」。** 没有用 `lifecycle_existing` 标记，因为测试证明旧的部分平仓执行器按交易所实时保护单缩量，
  并不读这个字段。为了不破坏军长规则解析器（它靠这里的「抄止损」记录一次真实的止损移动），
  只让 AI 识别路径关闭抄写。保本类意图照旧一律为空。
- **`protection_price_or_size_mismatch`（批次 159 / 166 / 172 / 174）** 与 M2 无关。它比对的是账本保护行与交易所同一订单的
  价格和数量，是设计内的拦截（fail-closed），当前代码上仍会发生；本次没有修。
- **Q1 补丁的判据：** 同一 lifecycle 在 `signal_at` 之后有 `automation_reason=lifecycle_apply_failed`，
  且载荷里的 `management_action` 含 `add_position` / `increase_position`。查询走 `raw_messages(chat_id, posted_at)` 复合索引，
