# 历史仓位分页状态一致性修复设计

## 目标

修复历史仓位渐进加载的两类状态不一致：部署后仍运行旧 JavaScript 的页面会显示没有事件绑定的新按钮；加载第二页后底部仍错误显示“已显示 20 / 100 条”。

## 根因

历史仓位片段由当前服务端渲染，而顶层页面可能在部署前已长期打开。新服务端可以把“加载更多”按钮放进旧页面，但旧页面中已执行的 JavaScript 不包含该按钮的绑定逻辑，因此点击无反应。完整刷新后会加载带新资源版本的脚本，按钮随即正常工作。

分页计数的服务端字段当前表示“本页数量”，但模板和浏览器把它呈现为“累计已显示数量”。第二页仍有 20 条，所以追加到 40 条后页脚仍显示 20。

## 方案

### 资源版本握手

- 根页面和所有工作台片段都携带同一个 `asset_version`。
- 浏览器请求懒加载片段时发送当前根页面的资源版本。
- 服务端或浏览器发现根页面版本与片段版本不同后，不合并片段。
- 页面显示“检测到新版本，正在刷新…”，保存当前交易分页和列表/群组视图，然后只执行一次完整刷新。
- 刷新后继续打开历史仓位及用户原先选择的视图。

已经运行在修复前旧脚本中的页面无法主动执行新检测逻辑，因此本次发布后仍需一次完整刷新；从该版本开始，后续资源版本变化能够自动收敛。

### 客户端累计状态

- 片段协议明确区分 `page_item_count`、`total_count`、`next_cursor` 和 `has_more`。
- 第一页用实际卡片数量初始化累计值。
- 追加页按稳定的 `data-history-position-id` 去重，以实际新增的唯一仓位数增加累计值。
- 真实列表和按群组视图共享同一个累计计数；切换视图不重新计算或重置。
- 手动刷新历史仓位或应用/清除日期筛选时从新第一页重新初始化累计值。

## 展示规则

- 第一页：`已显示 20 / 100 条`。
- 正常追加第二页：`已显示 40 / 100 条`。
- 若第二页有一条重复：`已显示 39 / 100 条`。
- 没有下一页：`已显示全部 100 条`。
- 请求失败：保留原计数和内容，显示“加载失败，重试”。
- 资源版本不一致：不追加内容，显示更新提示后完整刷新。

## 错误处理

- 自动完整刷新设置一次性会话标记，避免版本异常造成刷新循环。
- 版本不一致的响应不能更新游标、计数、列表或群组 DOM。
- 追加失败不能改变累计值或把 `has_more` 错置为 false。
- 重试继续使用原浏览快照和游标。

## 验证

本地测试覆盖：

- 同版本片段正常合并；
- 不同版本片段不合并且只触发一次完整刷新；
- 20 → 40 → 60 的累计变化；
- 重复仓位不增加累计值；
- 真实列表与按群组共享计数；
- 加载失败、手动刷新和筛选重置；
- Web 页面、静态资源与标签持久化回归。

生产验证在 Chrome 中完成：完整刷新后打开历史仓位，确认初始 20 条；点击加载更多后真实列表和按群组均扩展到 40 条，页脚显示 `40 / 总数`；检查控制台无分页异常，且仅发生历史仓位 GET 请求。

## 回滚

无需数据库迁移或交易状态转换。回退前端版本握手、片段元数据和累计状态提交即可恢复现状；持仓、委托、策略执行和 DeepCoin 写路径不受影响。
