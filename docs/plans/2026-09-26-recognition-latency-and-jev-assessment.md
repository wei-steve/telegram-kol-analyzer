## 1. 链路图与时间戳来源

```
Telegram 服务器                 ingest 进程                        worker 进程
posted_at ──(A 收到)──▶ raw_messages.created_at ──(B 入队)──▶ jobs.enqueued_at
                                                                   │ (C 排队：同群串行 lane + 轮询)
                                                                   ▼
                                                     jobs.completed_at（= 认领时刻，见 §1.1）
                                                                   │ (D 识别前准备)
                                                                   ▼
                                     mimo_recognition_runs.started_at
                                        │ (E 首轮识别；逐次尝试见 mimo_recognition_attempts.duration_ms)
                                        ▼
                                     mimo_recognition_runs.completed_at
                                        │ (F 上下文分析，需要时；否则约 0.2 s)
                                        ▼
                     context_resolution_attempts.created_at（调用返回后一次写入）
                                        ▼
                     recognition_decisions.created_at（权威结果落库）
                                        │ (G 指令落库) message_instruction_items.created_at
                                        │ (H 执行认领) authoritative_execution_attempts.claimed_at
                                        │ (I 交易所往返) side_effect_started_at → outcome_recorded_at
                                        ▼
                                     交易所
```

| 段 | 公式（后减前） | 备注 |
|---|---|---|
| A 收到 | `raw_messages.created_at − coalesce(edit_date, posted_at)` | `posted_at` 只精确到秒，系统性偏大 0–1 s |
| B 入队 | `jobs.enqueued_at − raw_messages.created_at` | |
| C 排队 | `jobs.completed_at − jobs.enqueued_at` | 拆成两部分：lane 等待（同群上一条还没处理完）和其他等待（轮询间隔、并发上限） |
| D 识别前 | `runs.started_at − jobs.completed_at` | |
| E 首轮识别 | `runs.completed_at − runs.started_at`（第一条 run） | 与 `Σ attempts.duration_ms` 逐条一致，说明这一段全部是模型调用，没有本地开销 |
| F 上下文分析 | `context_resolution_attempts.created_at（initial_resolution）− runs.completed_at` | 表里没有耗时列，只能这样近似 |
| E+F 到落库 | `recognition_decisions.created_at − runs.completed_at` | 不走上下文时 P50 约 0.2 s |
| 端到端（到落库） | `recognition_decisions.created_at − posted_at` | |
| G 指令落库 | `message_instruction_items.created_at − recognition_decisions.created_at` | |
| H 执行认领 | `authoritative_execution_attempts.claimed_at − recognition_decisions.created_at` | |
| I 交易所往返 | `outcome_recorded_at − side_effect_started_at` | |

### 1.1 一个容易踩的坑

`message_processing_jobs.claimed_at` 在作业结算时会被清空。`completed_at` 写的是认领那一轮的 `tick_time`，不是处理完成时刻（`message_processing_worker._settle_message_processing_job`）。

所以：
- `claimed_at − enqueued_at` 在生产数据上算不出来；
- `completed_at − claimed_at` 并不是「worker 单条处理耗时」；
- 真正的排队时长是 `completed_at − enqueued_at`；
- 单条作业总处理时长在库里**没有记录**。

以后如果要常态化监控，建议加一个真正的完成时间列。

## 3. 长尾成因

1. **gpt-5.6-luna 合同校验失败后切换备用模型（2026-09-25 起，最新、最大的识别长尾）。**
   - 从 09-25 开始有 61 条消息报「MiMo response missing strategy」（`mimo_response_invalid`），另有 15 次网关 502（`codex-api.dwpc.com.cn`）。
   - 失败的那一次尝试平均耗时 28–65 s（模型内部重试 2 次），随后切到 mimo-v2.5，又要 34–100 s。502 这一路单次失败要 62–76 s（例如 09-25 23:10 峰哥群 7 张连发图全部如此），说明网关 502 前还卡了很久，重试前的等待值得单独收紧。
   - 近 3 天 12.5% 的消息（67 / 535）走了这条路径，这些消息的识别 P50 88 s，只尝试一次的消息 P50 16 s。
   - 3 天识别 P90 因此从约 27 s 抬到 65 s。
   - ~~推断：模型在非策略消息上省略了 `strategy`。~~ 已查实，根因是 2026-09-25 02:35 发布的共享提示词 v10 与校验器不一致，见 §7。
2. **上下文分析慢，而且多数调用没有产生动作。** mimo-v2.5 P50 33 s；54% 的调用结论是 hold，16% 是 unresolved。
3. **同群串行 lane 把单条耗时放大成排队。** 连发 7–10 张图时，最后一张要等前面每一张都完成「识别 + 上下文」，端到端可达 13–16 分钟。
4. 早期（09-13 前后）的 mimo-v2.5 链首时代，单次识别平均 47–100 s，网络错误时单次可达 605 s。切到 gpt-5.6-luna 之后这类长尾已经消失。
5. 收到这一段（A）的 P99 为 18 s，偶有 59 s，属于 Telegram 推送侧的抖动，与识别无关。

## 4. Jev 评估（书面，未做实测）

### 4.1 Jev 是什么（据 docs.typesafe.ai，2026-09-26 读取）

- 属于 System One 模型：输入是状态（文本或 JSON）加若干问题，输出带类型的判断，不生成文本。
- 三种问题：
  - Noul：是非题，返回概率；
  - Choice：单选，最多 255 个选项，返回每个选项的概率和置信度；
  - Score：有序打分，2–10 档。
- 同一请求里的多个问题并行评估。
- 当前版本 `jev-1.13.0`：
  - 按输入 token 计费，每百万 token 0.042 美元，输出免费；
  - 上下文 64k，状态加最长问题不超过 32k；
  - 限流每分钟 1 200 次请求。
- 延迟：官方 cookbook 里，一篇长文配 13 个问题批量调用约 0.27 s。这个数字没有说明从哪里测的。
- **只接受文本，不支持图片。**
- **英文最好；中文能处理，但官方明说效果不如英文**，要求先在自己的数据上验证。
- 不做客户数据训练；零数据保留（ZDR）只对企业客户提供。

### 4.2 按识别契约逐项判断

| 契约字段 | 性质 | Jev 能否胜任 | 说明 |
|---|---|---|---|
| `input_reading.observed_text`（读图） | 视觉转写 | **不能** | 不支持图片，而 51% 的消息带图 |
| `recognition_result`：是策略 / 非策略 / 识别失败 | 判断 | 能（Choice） | 前提是图片已经被转成文字；「识别失败」对应图不可读，Jev 看不到图 |
| `message_classes`：新策略 / 策略管理 / 仓位管理 / 闲话 / 图片不可读 | 判断 | 能（Choice），「图片不可读」除外 | 同上 |
| `instructions[].kind`（9 种） | 判断，但一条消息可含多个动作 | 部分能 | 每种动作各问一个 Noul；多动作的拆分和顺序是结构化工作 |
| `strategy.symbol` / `side` | 抽取 | 部分能 | side 是二选一可以做；symbol 要先由代码给出候选币种，再用 Choice 选 |
| `strategy.entry` / `stop_loss` / `take_profit` / `leverage` | 结构化抽取 | **不适合** | 数字要逐字取出，还有多档止盈、区间、「附近」等写法。官方做法是正则抽出候选数字、Jev 只判断角色，这在群里的中英混写里风险很高，而且图片里的价格它根本看不到 |
| `strategy.order_type`（市价 / 限价） | 判断 | 能 | |
| `lifecycle_event.event_type` / `management_action` | 判断 | 能（Choice） | |
| `target.lifecycle_id` / `thread_id` | 从候选里选 | 能（Choice，候选由代码提供） | 候选没列进去就选不到 |
| `confidence` | 概率 | 天然提供 | 需要按我们的数据重新定阈值 |
| `reason` | 生成文本 | **不能** | 审计和页面展示要用 |
| 上下文分析 `decision`（hold / manage / new / exit / cancel / revise / unresolved） | 判断 | **很适合**（Choice） | 输入全是文本：近期消息、候选线程、首轮结构化结果 |
| 上下文 `target_thread_ids`、`supporting_message_ids` / `opposing_message_ids` | 从候选里选 | 适合（每个候选一个 Noul，或一个 Choice） | |
| 上下文 `management_action`、`conflict_types`、`risk_reducing_fanout_allowed` | 判断 | 适合 | |
| 上下文 `reason` | 文本 | 不能 | 可以由代码用模板拼出 |
| 触发判断「这条是否需要上下文」 | 判断 | 适合（Noul） | |

**结论：Jev 不能替代首轮识别。** 首轮识别的核心是「读图 + 抽数字」，这正是 Jev 做不了的。
Jev 真正适合的是**上下文分析**：它的输入是纯文本，输出基本是从有限选项里做判断。而这一步正好是 mimo-v2.5 P50 33 s，且占管理类消息端到端的一半以上。

### 4.3 组合方案与估算

**方案 0：先做不需要 Jev 的修复（推荐最先做）**

- 0a. 查清 gpt-5.6-luna 的「missing strategy」违约。如果确实是非策略消息省略了 `strategy`，就让解析器接受缺省值为 null；或者在提示词里要求模型始终输出这个键。
  - 预计近 3 天识别 P90 从 65 s 回到约 27 s，均值从 27.7 s 回到约 18 s；
  - 同时连带减少同群 lane 等待。
  - 风险低，属于合同宽容度改动，需要回归测试。
- 0b. 把 `context_resolution` 环节的链首从 mimo-v2.5 换成更快的模型，页面上就能改。
  - 需要注意：gpt-5.6-luna 在上下文环节的历史样本只有 27 次，P50 53 s，还有 45 次 exhausted，表现并不好。
  - 所以先离线对比，再决定换不换。
- 0c. 审视上下文触发闸门。（原文「74% 的触发来自首轮非策略消息」有误，已在 §2.3 更正；按首轮原样重算的结果见 §8。）

  - 但 `entered_holder_language` 这类触发正是为了抓首轮漏掉的管理指令而设的，所以要按触发原因逐项分析，不能一刀切。
- 0d. 同群 lane 内的推测性并行识别：同群排队中的消息先并行跑首轮识别，结果仍按顺序落库。
  - 连发场景下排队 P90（约 70 s）可以大幅下降；
  - 属于 L2 级改动，涉及并发和顺序语义，要单独设计。

**方案 1：Jev 做首轮前的快速分诊，闲话直接短路**

- 只对纯文本消息可用，约占 49%。带图的消息 Jev 看不见，仍要走完整识别。
- 被短路的是闲话，而闲话本来就不需要快，它自己的时延收益没有意义。
- 唯一的收益是让同群后续消息少排队：按纯文本闲话约占 40%、每条省 16 s 粗算，lane 等待大约能降 20–30%。
- 代价：多了一个外部依赖，每条消息多一次跨境调用（估计 0.5–2 s）。
  最大的风险是漏判，把一条中文管理指令误判为闲话后，这条指令就丢了。
- **不推荐。** 同样的收益用方案 0d 就能拿到，而且没有漏判风险。

**方案 2：Jev 做上下文分析里的判断（唯一值得实测的方向）**

- 形态：状态里放同群近期消息的文本、首轮结构化结果和候选线程列表。一次请求里并行问三个问题：
  - `decision`，Choice，7 个选项；
  - 每个候选线程「是否为目标」，Noul；
  - `management_action`，Choice。
- 动作规则：
  - Jev 判 hold 且置信度高时，直接 hold；
  - Jev 判为动作且置信度高时，先影子记录，不直接执行；
  - 其余情况照旧调用现有的上下文模型。
- 估算：走上下文的 32% 消息里，54% 的结论是 hold。如果 Jev 能以高置信度接住其中大部分，这部分从约 33 s 降到约 1–2 s。
  - 走上下文的消息，端到端 P50 预计从约 75 s 降到约 45 s；
  - 管理类端到端均值预计下降约三分之一；
  - lane 等待也随之下降。
  - 这些数字依赖 Jev 在中文群消息上的准确率，**目前是推测**，必须实测。
- 风险：
  1. 中文效果官方未背书；
  2. 需要确认从腾讯云服务器能否稳定访问 `api.typesafe.ai`，以及延迟多少；
  3. 群消息要发给第三方（ZDR 需要企业合同）；
  4. 必须遵守 AGENTS.md 的约束：先以影子模式上线，不得绕过现有的策略定位和上下文解析，关闭和回滚路径要先测好。

**方案 3：不引入 Jev**

- 如果方案 0a–0c 做完，识别 P90 回到约 27 s、上下文调用减半，端到端 P90 可能已经从约 140 s 降到 60–80 s。
- 届时再评估 Jev 的边际收益，可能就不值得增加一个外部依赖了。

**推荐顺序**：先做 0a（最便宜、最确定），再做 0c 分析、0b 离线对比；0d 单独设计。方案 2 的实测等用户批准后再做，作为 0b 的候选之一。

## 7. 第 1 项：「缺少 strategy」与 502 的根因

### 7.1 缺少 strategy：提示词 v10 与校验器不一致（已查实）

| 共享提示词版本 | 时间段 | gpt-5.6-luna 调用 | 其中报「missing strategy」 | mimo-v2.5 报此错 |
|---|---|---|---|---|
| v8 | 至 2026-09-25 03:13 | 2 229 | **0** | 0 / 41 |
| v10（四分类契约，09-25 02:35 发布） | 09-25 03:27 起 | 301 | **61（20%）** | 8 / 79 |

- 第一条失败出现在 09-25 03:56，即 v10 生效后 29 分钟。
- v10 正文要求：「数组里没有 新策略 元素时，strategy 必须为 null」「闲话：strategy 必须 null」。
- 而 `recognition_experiments._validate_authoritative_payload` 仍要求 `payload["strategy"]` 必须是 dict，否则抛出 `ValueError("MiMo response missing strategy")`。
- **模型是在照提示词办事，拒收它的是我们自己的校验器。** 四分类设计稿 §10 A4 本来就规定阶段 1 校验器「缺字段与违规都不抛错」，这里是阶段 1 漏掉的一处。
- 下游的落库代码（`message_recognition.py` 多处、`authoritative_instructions.py`）早就把非 dict 的 `strategy` 当成 `{}` 处理。所以非策略消息上接受 `null`，产物语义不变。
- 失败的消息最终全部被判为非策略（66 条 none、3 条 position_update、1 条 exit_position），是 mimo-v2.5 答出来的。
- **所以修的是校验器，不是提示词**：
  - 非策略或识别失败时，接受 `strategy` 为 null 或缺失；
  - 「是策略」时仍然严格要求它是 dict；
  - 不改写 payload，四分类影子解析要看到原样的 null。
- 这不违反「28 日前不改提示词和契约」的约束：它只是让校验器跟上**已经发布**的 v10 契约。

失败的代价在于同模型重试：校验失败对同一输入几乎必然复现，但 `_call_mimo_authoritative_with_retry` 对所有异常都一视同仁地重试一次。「合同违规不做同模型重试」按四分类设计稿属于阶段 3，这次不碰。校验器修好之后，这类失败本身就不再发生。

### 7.2 502：网关要拖 30 秒左右才返回，同模型重试又要 30 秒

- 请求超时是单一的 60 s（`httpx.Client(timeout=60)`），502 并不是超时触发的。是网关 `codex-api.dwpc.com.cn` 自己阻塞约 30–37 s 后返回 502。
- 一个模型的两次尝试加 1 s 间隔，合计 62–76 s，与观测吻合。
- 14 天里 19 行 502 失败，**重试之后全部仍然失败**。它们集中出现，例如 09-25 22:00–23:59 连续 16 次，属于网关故障期。
- 缩短读超时帮不上忙：正常识别 P99 就有 43 s，缩短反而会误伤正常请求。
- 修法：遇到 HTTP 5xx，**且链上还有下一个模型时**，不做同模型第二次尝试，直接换备用模型。
  - 链上只有这一个模型时保持重试一次，因为那是唯一的机会；
  - 超时、网络错误、4xx、合同错误的重试行为一律不变。
- 每次 502 事件预计省 31 s 左右。

## 8. 第 2 项：上下文触发条件逐项分析（只读）

### 8.1 口径

- 首轮结论取自 `request_summary_json.mimo_first_pass`，不是改写后的权威载荷。
- 「首轮可执行」的定义：`recognition_result=是策略`，或 `lifecycle_event.event_type≠none`。
- 每次调用的效果分为五类：

| 效果 | 含义 |
|---|---|
| 维持首轮 | 结论为 new_thread，首轮原样生效 |
| 首轮不可执行、结论 hold | 什么都没改变，这是纯开销 |
| 压下首轮动作 | 首轮可执行，被改成 hold / unresolved / 低置信度 |
| 改变或重定目标 | 首轮可执行，被改成 manage / exit / cancel / revise 且置信度 ≥ 0.7 |
| **抓回动作** | 首轮不可执行，上下文判出动作 |

### 8.3 建议

1. **收紧**：把方案甲的「首轮可执行」门扩展到 `entered_holder_language` 和 `revision_language`。首轮不可执行时，这两个关键词不单独构成触发理由。
   - 09-16 以来可省 66 次调用（占全部 449 次的 15%），节省约 2 970 s 的模型时间，平均每次 45 s；
   - 14 天回放**零漏抓**；
   - 这些消息端到端平均少约 45 s，同群后续消息的排队也相应缩短；
   - 改动面很小：`requires_context_resolution` 的收尾门多丢两个信号，沿用 `tests/test_context_trigger_actionable_gate.py` 的测试模式；
   - 属于 L1 级改动，按 AGENTS.md 规则需要 15 分钟或 5 条消息的观察窗；
   - **2026-09-28 之前不能做**：它改变首轮之后的触发语义，而四分类线正在攒 v10 的数据。放在 28 日之后排期。
2. **保留**：`text_image_conflict` 和 `cancellation_language`。它们是仅有的两个在首轮不可执行时真正抓回过动作的信号，已有实例 17368 和 18602。
3. **另案**：`entered_holder_language` 在首轮**已给出确切目标**时仍然会触发，并可能把正确答案覆盖掉，这是 2026-09-24 米娅 msg 696 的事故路径，至今未修。这是正确性问题，不是时延问题，建议单独立项，不和本条合并。

5. **结论**：触发条件本身已经比较紧了。上下文这一步慢，主要不是调得太多，而是**上下文模型本身慢**：mimo-v2.5 P50 33–52 s。触发收紧只能再省 15% 的调用。上下文提速的主攻方向，仍是模型选型的离线对比（§4.3 方案 0b，需要先解决 gpt 的越界问题），以及之后可能的 Jev 实测（已暂缓）。
