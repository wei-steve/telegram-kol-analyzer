# 回复上下文撤单设计

## 背景

飞扬频道的消息 4007 回复了 BTC 多策略 4004，并明确表示“这笔也取消”。原策略当时有两笔待触发入场单，但生命周期识别只向模型提供了最近策略列表和聊天文本，未提供 Telegram `reply_to_message_id` 与被回复策略的结构化身份。模型因当前消息没有币种或策略 ID 输出 `none`，导致没有创建 `cancel_entry`，两笔挂单随后成交。

## 决策

采用上下文增强方案（方案 A），不引入新的确定性撤单规则：

1. 生命周期 AI 输入增加当前消息的 `reply_to_message_id`。
2. 若回复目标是同频道的一条策略原消息，输入增加该策略的结构化摘要：消息 ID、生命周期 ID、标的、方向、状态、入场区间，以及绑定订单/仓位的概览。
3. 生命周期提示词要求模型将“明确撤单语义 + 回复待入场策略”识别为 `cancel_entry`，并输出该策略唯一的 `target_lifecycle_id`。
4. 识别结果继续使用既有 `cancel_entry` → 候选项 → Deepcoin 撤单流程；不新增交易 API 路径。

## 安全边界

- 只有同频道、精确回复到已知策略原消息时才提供该回复策略上下文；普通消息不改变现有匹配行为。
- 模型仍必须给出唯一 `target_lifecycle_id` 且置信度达到现有阈值；上下文本身不直接授权交易。
- 对“撤单”回复，若目标已进入 `entered` 或撤单预检发现订单已成交，绝不将 `cancel_entry` 升级为全平。系统记录阻断原因并发送运营告警，由人工决定是否平仓。
- 历史消息 4007 不自动回放；其挂单已成交形成的持仓不因本修复被自动改变。

## 数据流

`RawMessage.reply_to_message_id` → 生命周期上下文加载被回复消息及对应 `StrategyLifecycle`/`ExecutionBinding` → AI 输出唯一 `cancel_entry` → 现有候选项和执行通路只撤销该绑定的未成交订单腿 → 订单腿、执行事件、生命周期状态持久化。

若执行前状态已从 pending 变为 entered，处理终止于“需要人工处理”的告警，不提交平仓单。

## 验收标准

- 4004→4007 等价场景能生成对 4004 的 `cancel_entry`，并只撤销两笔绑定挂单。
- 无回复、跨频道回复、回复非策略、模糊措辞均不产生撤单。
- 撤单竞争导致已成交时，没有 `close_bound_position_market` 或其他平仓提交事件，且存在可见的阻断/告警记录。
