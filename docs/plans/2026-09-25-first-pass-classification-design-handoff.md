## 1. 用户的原话与意图（不要改写，这是需求本身）

用户 2026-09-24 对首次分析任务的定义：

> 首次分析的任务我觉得：**新策略、策略管理、仓位管理**（后补：加 **闲话**）
>
> **新策略**：有交易合约标的，有入场价格，有止损价格，（允许暂时没有止盈目标）
>
> **策略管理**：前面给出了策略，但是策略还没有入场，现在需要对策略作出调整。
> 还有一种情况，「BTC准备87500做空，半仓入场」，这种消息有合约名称有入场价，
> 但是没有止损价，不应该看作策略，但是后面的半仓入场，预示着准备出现的正式策略
> 是半仓对待。另一种情况，先发了一个完整策略，下一条消息「半仓入场」，
> 预示着上一条策略以半仓对待。
>
> **仓位管理**：前面有策略（1个策略或者多个策略，也许是相同合约名称，也许不同
> 合约名称），策略已经触发入场，仓位管理就是对已经触发入场的持仓进行管理，
> 也许是调整止盈价，调整止损价，临时离场，部分止盈
>
> 提示词应该还有一个字段配合这个分类，**一定要注意可能出现空值字段**

关于上下文分析：

> 不是所有消息都要触发上下文分析，**如果首次分析明确目标就不需要进行，
> 避免大大浪费 token**。起码首次分析判断为策略管理和仓位管理才需要上下文分析。
>
> 上下文分析**也只需要分析一次，没必要重试**，除非模型范围连接错误之类的情况

关于重试与模型能力：

> 首次分析除非是模型因为网络之类的问题，返回失败。否则不应该重试，
> **识别错误那是模型能力问题，重试也没用**，如果因为模型能力问题令答案漂浮不定，
> 那怎么重试都没意义。我们需要假设模型是有正确辨别能力的。
> **模型的能力应该以人工进行历史核准来判断。**

关于分类粒度（由 v2 失败反推）：

> 可能就是**分类太细**，所以识别率出错。

## 2. 现状：契约长什么样

生产用的是 `trading.analysis.shared` v8（def=1），契约版本 `v1`，
模型 `gpt-5.6-luna`。输出两个字段分工：

- `recognition_result`：`是策略` / `非策略` —— 只回答「这是不是一条**新开仓**策略」
- `lifecycle_event.event_type`：`none | entry_confirm | cancel_entry | exit_position | position_update`
  （另带 `target_lifecycle_id` / `management_action` / 价位等）

**用户的四分类与现有字段的映射**（已核对代码，`ai_recognition_config.py:134` 起）：

| 用户分类 | 现有表达 |
|---|---|
| 新策略 | `recognition_result = 是策略` |
| 策略管理 | `cancel_entry`（撤未入场）、`entry_confirm`（「半仓入场」定量） |
| 仓位管理 | `position_update`（部分止盈/移止损/调价/继续持有）、`exit_position`（完全离场） |
| 闲话 | `recognition_result = 非策略` 且 `event_type = none` |

所以**信息已经够，缺的是一个显式的单一分类字段**，现在要靠两个字段组合推导。
`exit_position` 是用户没提但必须保留的一类，提示词 `ai_recognition_config.py:154`
有专门规则防它与 `position_update` 混淆，不要合并。

`entry_confirm` 的两种形态（用户举的两个例子）**已由另一会话实现**
（`006972e1`：确认消息为下一笔入场定量，而不是自己开仓），改造时不要推翻它。

## 3. 下一步要做什么

1. **设计新契约**：一个显式分类字段（四值）+ 一个配合字段。
   **空值语义必须明确写进提示词与解析器**：哪些分类下哪些字段允许为 null，
   哪些为 null 就是契约违规。用户特别强调了这一点。
2. **向后兼容**：`recognition_result` 与 `lifecycle_event` 有大量下游读者
   （执行、管理链路、web 展示、对账）。先加不删，跑影子比对，再切换。
3. **然后**才改上下文解析的触发与重试（见 §4）。

## 4. 改造时必须一并解决的三处已知缺陷（都有实盘证据）

**(a) 触发判据被关键词盖过**（`authoritative_recognition.py:215-224`）
用户要的「首次分析明确目标就不解析」这条判据**已经存在**，叫
`management_without_exact_target`（`event_type != "none"` 且 `target_lifecycle_id` 为空）。
但另有三条是**纯文本关键词**：

```python
REVISION_LANGUAGE     = ("更新", "修改", "改为", "调整", "replace", "update")
CANCELLATION_LANGUAGE = ("取消", "撤销", "撤单", "cancel")
ENTERED_HOLDER_LANGUAGE = ("有入场", "已入场", "持仓", "保护成本", "保本", "继续持有")
```

2026-09-24 米娅 msg 696 就因文末「做无风险**持仓**」命中第三条而触发解析，
**尽管首次分析已经给出 `target_lifecycle_id = 1319`**。那次解析本不该发生。

**(b) 降级把首次分析抹平**（`authoritative_recognition.py:663-674`）
上下文解析返回 `hold` / `unresolved` 时：

```python
payload.update(
    recognition_result="非策略",
    lifecycle_event={"event_type": "none", "confidence": 0.0},   # ← 首次分析在这里消失
)
```

米娅那次，首次分析读出的 `position_update` / `partial_take_profit, move_stop_to_protect`
/ `stop_loss: 84500` / `target_lifecycle_id: 1319` 全部被抹掉，
下游再也看不出这条消息曾被判为仓位管理。**结果是止盈 50% 与移止损都没执行，
仓位裸持 1.6 小时，最后由用户手动平仓。**

失败关闭的用意正当（目标不确定就别动仓位），但它**只认上下文解析一个来源**：
首次分析已给出目标、两次 `reanalysis` 已 `completed` 且判定一致，
只有最后一次 initial_resolution 说不确定，而它读到的交易所状态把
`thread 688`（root = msg 693，活仓）与 `msg 688`（前一日已 expired）混淆了。

**(c) 契约类失败也会重问模型**（`context_resolution.py`，`terminal = attempt_number == 2`）
`target_outside_candidate_set` 是确定性的结构错误，第二次问不会有新信息。
应与网络失败分开：网络失败重试（`ContextNetworkRetryPolicy` 已区分），契约失败不重问。
**这与用户「不该重试」的要求一致**，但注意区分：六次尝试的
`context_fingerprint` **两两不同**，那是设计里的「状态变化后重分析」
（原设计第 5 条），不是同一个问题问六遍——要砍的是 attempt **内部**那两次。

**另**：`target_outside_candidate_set` 的诊断记了「有 1 个 target」「不在集合里」，
**却没记它是什么**。连续失败六次只留下「不匹配」，无法定位。先补这个再谈别的。
