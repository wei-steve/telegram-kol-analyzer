## 1. 现状（只读核查结果）

### 1.1 每个页面现在怎么拿数据

| 页面 | 首次加载 | 之后怎么更新 | 问题 |
|---|---|---|---|
| 策略（现在是默认页） | 打开即拉 `/strategy-records` 整段 HTML | **不自动更新**。任何群有新消息时都会亮出「有新变化，点击查看」，点了才整段替换 | 提示和策略是否真的变了无关；「上次成功更新」时间有误（见 1.4） |
| 持仓 | 点开后拉 `/positions-panel?initial=positions` 整段 HTML | 只在窗口重新获得焦点时比对一次，变了就显示「检测到新的持仓数据 · 点击更新」 | 页面一直开着的时候价格和止损止盈都不会动 |
| 动态 | 点开后拉全局时间线 | 每 5 秒轮询 `/api/freshness`，有新消息就显示「有新消息 ↑」按钮，点了才加载 | 已有数据（识别状态等）不会原地更新 |
| 群组 | 点开后拉群组列表和所选群消息 | 有新消息时**不管当前在哪个页**都重拉 `/groups`，把整个群组列表整块替换 | 所选群的消息面板从不自动刷新：前端判断的页面名是 `'messages'`，这个页面名在 2026-07-13 改成懒加载之后已经不存在了（`app.js:5068`、`app.js:5106`），问题还在 |
| 更多 | 点开后加载设置表单 | 不更新 | 这里是表单，本来就不该自动更新 |

全站公共部分：每 5 秒请求 `/api/monitor-status` 和 `/api/freshness` 两次，窗口重新获得焦点时补查一次；另外每个标签页还开着一条 `/api/events` SSE 长连接。

### 1.2 SSE 在生产上是断的

`LiveUpdateBroker`（`live_updates.py`）只在**进程内部**广播。发布事件的地方有两处：收到新消息（`raw_ingest.py:195`，在 ingest 进程里）和生命周期变化（`lifecycle_monitor.py:2203`，在 worker 进程里）。可是浏览器连的是 **web 进程**，而 2026-08 拆分进程以后，web 进程自己从来不发布任何事件。所以：

- 生产上 `/api/events` 除了一开始的一行 keep-alive，**永远不会收到任何事件**。过去 30 分钟的 journal 里有 7 次连接，数据帧为 0。
- 每个打开的标签页白白占着一条长连接。
- 附带发现：ingest 和 worker 里的 `published_events` 列表只追加、从不清理，会一直缓慢增长（量不大，这次不改，放在第 7 节）。

也就是说，现在页面上的「实时」其实全靠每 5 秒一次的轮询。

### 1.3 以前的「整页刷新 / 闪动」是怎么来的（git 历史）

| 时间 | 提交 | 做法 | 后果 |
|---|---|---|---|
| 2026-04-21 | `d88f2901` | 每 15 秒 `setInterval(refreshCurrentGroupPanel)`，用 `innerHTML` 整块替换面板 | 整块重建，滚动位置跳动 |
| 2026-05-24 | `0c29d3f6` | 同一个定时器上再加 `refreshGroupList()`，群组列表也整块替换 | 同上 |

根本原因只有一个：**更新的单位是「整个面板」**。只要还是整块换，就一定会闪、会丢滚动位置、会收起已经展开的内容。这次要把更新单位改成「单张卡片、单个数字」。

### 1.4 截图里两处可疑时间：查清了，都是显示或取数有问题，不是真实数据

**(a) 「上次成功更新：2026/9/29 18:56:58」**

- 这是浏览器按**本机时区**格式化出来的：`formatStrategyRecordSuccessTime` 用的是 `new Date(v).toLocaleString()`（`app.js`）。这台 Mac 的时区是美国太平洋时间（PDT，UTC−7），**9/29 18:56:58 PDT 就是北京时间 9/30 09:56:58**。页面上其它时间都按北京时间显示，只有这一处按本机时区，所以看起来像「停在昨天」。
- 另外，服务端首屏给这个字段的值是 `max(raw_messages.posted_at)`，也就是**最新一条消息的时间**，并不是列表的更新时间（`web_app.py:9071`），名字和含义对不上。首屏之后前端会用本地的「拉取成功时间」覆盖它，但因为列表不会自动刷新，这个时间也就停在打开页面的那一刻。

**(b) 策略卡片的「最近变化」全都是「09-30 09:56」**

- 「最近变化」取的是这张卡片关联的几张表 `updated_at` 的最大值：生命周期、识别决策、识别结果、**执行绑定**、执行事件、管理批次（`strategy_records.py:2781` 和 SQL 版 `:3562`）。
- 生产库点查（`ix_execution_bindings_venue_status` 索引，绑定参数跑过 EXPLAIN）：**196 条执行绑定的 `updated_at` 完全相同，而且大约每 22 秒整体跳一次**（02:03:08 → 02:03:30 UTC）。其中包括早就 `closed` 的绑定。
- 原因在 `execution_bindings.py:4211`：对账每一轮都会把所有绑定（包括已关闭的）按订单腿重新推导一遍，最后**无条件**执行 `binding.updated_at = recovered_at`。`web_app.py:11541` 的注释也写明了这一点（「A reconcile pass refreshes updated_at on most non-terminal bindings … roughly 180 of them」）。
- 所以凡是有执行绑定的卡片，「最近变化」显示的都是「最近一轮对账的时间」，按「最近变化」排序也就等于没排。

## 2. 目标与不做的事

目标：

- 数据在原地更新：价格、盈亏、止损止盈、状态文字、新卡片出现、旧卡片消失都直接反映在页面上。
- **不重建整个页面**：滚动位置不变，展开的 `<details>` 保持展开，正在输入的表单不被覆盖，焦点不丢，没有「加载中」变暗。
- 多个浏览器同时打开时，服务器负担不随浏览器数量线性增长，也不引入慢查询。
- 持仓排在第一位，并且是默认页。

不做：

- 不改识别、交易、对账的行为（第 4.3 节的源头修复单独列出，由用户决定）。
- 不引入前端框架或构建流程（保持原生 JS + Jinja 片段）。
- 不从 web 进程直接调用交易所（web 没有执行权限，也不该占用交易所读取配额）。

## 3. 推荐方案：一个轻量的「版本号」轮询 + 按卡片对比替换

### 3.1 为什么不用 SSE 推送

- 要让 SSE 真正生效，必须先解决跨进程问题：ingest 和 worker 的事件得传到 web。办法无非是：web 轮询数据库再推给浏览器（本质还是轮询，只是多了一层长连接），或者新增一个进程间通道（Unix socket、Redis 等），这就成了新组件，要按 L2 评估。
- 我们的数据源本来就是「worker 每约 5 秒刷新一次仓位缓存文件」和「消息入库」，都不是毫秒级的，5 秒一次的轮询就能跟上源头。
- 轮询是无状态的：断线、重启、nginx 重载都能自然恢复，不用处理长连接的边界情况。

结论：**本次不用 SSE，改用一个很便宜的版本号接口**；前端不再打开 `/api/events`（后端接口先保留，不删，便于回滚）。以后如果真需要亚秒级推送，再单独立项做跨进程推送（见第 6 节问题 4）。

### 3.2 新接口 `GET /api/live/state`（替代现在的两个轮询）

一次请求返回：

```json
{
  "server_time": "2026-09-30T10:05:12+08:00",
  "monitor": { "state": "monitoring", "label": "监控中" },
  "versions": {
    "messages":   "r:1234567",          // max(raw_messages.id)，只走索引，同现在的 /api/freshness
    "positions":  "p:9f3a…",            // 仓位缓存文件内容哈希（去掉 captured_at），不查库
    "strategies": "s:…",                // 见下
    "groups":     "g:…"
  },
  "positions_captured_at": "2026-09-30T10:05:09+08:00"
}
```

- `messages`：沿用 `build_global_freshness_statement()`，已经是走索引的查询（`67c9ee19`）。
- `positions`：web 已经在读 `data/web_cache/deepcoin_live_positions.json`（worker 约每 5 秒写一次，实测文件 mtime 每 5 秒一跳）。版本号取「去掉 captured_at 之后的内容哈希」，这样只有仓位、价格、止损止盈真的变了，版本号才会变。**不查库，也不调交易所。**
- `strategies`：由几个只走主键或索引的 `MAX(id)` 拼成：`strategy_lifecycles`、`execution_events`、`strategy_management_batches`、`recognition_decisions`，再加上「进行中生命周期」（`lifecycle_status IN ('entered','pending_entry')`，走 `ix_strategy_lifecycles_status`，生产约 30 行）的 `max(updated_at)` 和行数。**刻意不用 `execution_bindings.updated_at`**（它每 22 秒整体跳一次，见 1.4 b）。每条查询都要用绑定参数跑 EXPLAIN 确认走索引，并写进测试。
- `groups`：`messages` 版本号加上群组配置文件的 mtime（群组开关、标签改了也能反映出来）。

**服务端共享缓存**：`/api/live/state` 的结果在 web 进程里按 **2 秒 TTL** 缓存，同一时间只允许一个请求去计算（single-flight）。所以不管开多少个浏览器，数据库每 2 秒最多被这几条索引查询访问一次。接口是同步 `def`，FastAPI 放到线程池里执行，不会卡住 web 的事件循环；worker 是独立进程，SQLite 处于 WAL 模式，读不会挡写。

### 3.3 前端：只有版本号变了才去拉对应片段，然后按卡片对比

轮询节奏：

- 页面可见时每 **5 秒**请求一次 `/api/live/state`（和现在一样是 5 秒，但请求从两个合并成一个）。
- 页面隐藏（切到别的标签页、锁屏）时**停止轮询**；重新可见时立即补一次。
- 只有「当前正在看的那个页面」对应的版本号变了，才去拉那个页面的片段；其它页面只记下「已过期」，切过去时再拉。

拉到片段以后，不再整块 `replaceChildren`，而是交给一个新的小函数 `patchKeyedList(currentRoot, nextRoot)`（原生 JS，约 150 行，写在 `app.js` 里，不引外部库）：

1. 每张卡片都有稳定的 key：持仓用 `data-position-pos-id`，策略用新增的 `data-strategy-record-key`（lifecycle_id，没有的话用 `pos:<pos_id>`），动态和群组消息用 raw_message_id，群组列表用 chat_id。
2. 按 key 对比新旧卡片：
   - 内容相同：不动。
   - 内容不同：只替换这一张卡片内部变化的节点。替换前把卡片里 `details[open]`、正在输入的表单值和焦点记下来，替换后还原。**如果用户的焦点正在这张卡片的输入框里，这张卡片先不动**，等失去焦点后再更新。
   - 新卡片：插到它应在的位置。
   - 消失的卡片：移除。
3. 如果变化发生在当前可视区域**上方**，用 scroll anchoring 补偿 `scrollTop`，保证眼前看到的内容不会被挤走。
4. 更新过的卡片闪一下很淡的背景色（约 1 秒，`prefers-reduced-motion` 时不闪），让人知道「这里刚变过」。这只是提示，不是重绘。
5. 页面顶部的「上次更新 10:05:12」随每次成功轮询更新（北京时间）。

各页面的具体做法：

| 页面 | 看哪个版本号 | 拉什么 | 更新方式 |
|---|---|---|---|
| **持仓（优先）** | `positions`，以及 `strategies`（归属状态） | `/positions-panel?initial=positions`（从缓存文件渲染，不调交易所） | 按 pos_id 更新卡片：数量、均价、止盈止损列表、归属状态、「更新时间」。当前 tab、分组或列表视图、「仓位操作」展开状态都保留（沿用现有的 `exchangePositionUiState`）。「检测到新的持仓数据 · 点击更新」按钮取消 |
| 策略 | `strategies` | `/strategy-records?<当前筛选>`，只拉当前页 | 按卡片 key 原地更新。**顺序变化不自动重排**（避免卡片在眼前跳来跳去），改成顶部显示一行「排序有变化 · 点击重排」；新增或移除的卡片直接生效。计数（各筛选按钮上的数字）直接更新。「有新变化，点击查看」提示取消 |
| 动态 | `messages` | 新增增量片段 `/activity/timeline?after_raw_message_id=X`（只返回更新的消息卡片） | 用户在顶部：新卡片直接插到顶部。用户往下翻了：插入以后补偿滚动位置，眼前内容不动，顶部显示「有 N 条新消息 ↑」，点了滚回顶部。已加载卡片的识别状态由第一页的对比更新 |
| 群组 | `groups`，所选群还要看 `messages` | 群组列表 `/groups`；所选群的消息面板 | 群组列表按 chat_id 更新计数和开关状态，不再整块替换；修掉 `'messages'` 这个死判断，所选群的消息面板有新消息时按「动态」同样的规则处理。**只在群组页可见时才拉**（现在任何页面都会拉 `/groups`） |
| 更多 | 不看 | 不拉 | 表单页不自动更新 |
| 策略详情页 `/strategy-records/{id}` | 本次不做，放第 7 节 | | |

### 3.4 断线、重连和提示

- 一次轮询失败：不提示，下次照常。
- 连续 2 次失败：页面顶部状态条显示「实时更新暂停，正在重试…（上次更新 10:05:12）」，重试间隔按 5 → 10 → 20 → 30 秒退避，最长 30 秒。
- 恢复：立即补拉当前页面的片段，状态条变回「实时」，提示自动消失。**不弹窗，也不整页刷新。**
- 返回 401（登录过期）：状态条显示「登录已过期，点此重新登录」，停止轮询。
- 静态资源版本变了（部署之后）：沿用现有的 `WorkbenchAssetVersionMismatchError`，提示「页面已更新，点此刷新」，**不自动 reload**。
- 片段内容不完整或解析失败：保留当前内容，按连续失败处理，不清空页面。

### 3.5 服务器负担估算

| | 现在（每个标签页） | 改后（每个标签页） |
|---|---|---|
| 固定轮询 | 2 个请求 / 5 秒 | 1 个请求 / 5 秒，隐藏时为 0 |
| 长连接 | 1 条（SSE，实际收不到数据） | 0 |
| 数据库 | 每个请求都查 | 所有标签页共享 2 秒缓存，最多每 2 秒一组索引查询 |
| 片段拉取 | 仅手动 | 只有当前页的版本号变了才拉：持仓在有仓位时最多每 5 秒一次；策略和动态只在真的有变化时拉 |

需要注意的是策略片段：`/strategy-records` 本身不轻（会汇总 4 组生命周期数据，再加仓位上下文）。为此：

- 策略片段在服务端按 `(筛选参数, strategies 版本号, positions 版本号)` 缓存最近一份渲染结果，多个浏览器看同一个筛选时只算一次。
- 第二批实施时先在生产 journal 上量一下这个接口现在的耗时（只读）；如果超过 300 ms，把策略页的拉取间隔下限设为 15 秒。

### 3.6 风险等级

- 第一批（导航、默认页、时间修正）：只改网页 → **L1**。
- 第二批（实时数据）：不新增长连接，不新增后台任务，web 进程里只多一个带 TTL 的内存缓存，反而少了 SSE 长连接 → **L1**。观察窗里额外检查 web 的请求速率和响应时间，以及 worker 心跳有没有变化。

## 4. 分批

### 第一批：小而确定（确认后立即做）

**4.1 导航顺序和默认页**

- 导航顺序改为：**持仓 · 策略 · 动态 · 群组 · 更多**（`_workbench_nav.html`，桌面和手机两套导航）。
- 默认页改为持仓，下面几种情况都一样：
  - 前端：`scheduleInitialWorkbenchView`、`setWorkbenchView` 的兜底值、`openDashboardPanel('main')` 的返回页，都从 `'strategies'` 改为 `'positions'`。
  - 模板：首屏默认激活持仓面板和持仓按钮。
  - 服务端：`/` 在没有 `?view=` 时也直接渲染持仓（`render_initial_positions` 默认为真），数据来自缓存文件，`allow_sync_refresh=False`，**不同步调交易所**，首屏直接出持仓，不用等懒加载。
  - 登录后跳回 `/`，所以也会落在持仓。
  - `?view=strategies` 等显式参数照旧生效。
- 策略页改为点开时再加载，和其它页面一样。

**4.2 修正「上次成功更新」**

- 服务端首屏传「本次渲染时间」（带时区），不再传「最新消息时间」。
- 前端所有这类时间统一用 `Asia/Shanghai` 格式化（`toLocaleString('zh-CN', {timeZone: 'Asia/Shanghai', …})`），不再跟随本机时区。
- 文案改为「列表更新于 09-30 09:56:58」。
- 持仓面板里的快照时间目前显示「HH:MM:SS UTC」，统一改成北京时间。

**4.3 修正「最近变化」**

- 网页侧（本批做）：计算「最近变化」时**不再使用 `execution_bindings.updated_at`**，改用这些更有意义的时间：生命周期、识别决策、识别结果、执行事件、管理批次、订单腿的 `updated_at`。订单腿只在状态真正变化时才写，这一点需要子代理核实，核实不了就不用它。三处都要改：
  - Python：`strategy_records.py:2781` 的 `_latest_timestamp(...)` 去掉 binding。
  - SQL：`strategy_records.py:3562` 的 `latest_expression` 去掉 `ExecutionBinding.updated_at`。
  - 没有生命周期的孤儿绑定卡片（`:3166`）改用它最近一条执行事件的时间，没有事件时用 `created_at`。
