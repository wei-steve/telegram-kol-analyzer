# Deepcoin 精确止损保护修复设计

## 目标

修复 Deepcoin 分仓持仓的主止损所有权误降级，确保新持仓在创建止盈前已经拥有一个独立、精确绑定 `closePosId` 的第二市价止损，并通过带指纹的人工审批流程为符合条件的存量持仓补建第二止损。

本设计不在主止损失败后自动追单。主止损失败时，系统保留预先存在的第二止损、冻结该持仓的自动管理并发送高优先级告警。

## 已确认的生产事实

- 受影响主止损请求已经使用 `slOrdPx=-1`，即触发后市价执行；`orderType=limit` 属于入场条件单，不是止损成交方式。
- Deepcoin 对持仓 `1001124330609705` 的主止损返回 `errorCode=203`、`NotEnoughMoneyToClose`，交易所给出的账户计算结果小于零。
- 当前待触发 TPSL 响应经常不返回 `posId` 或 `closePosId`。
- 系统已经持久化部分权威 `ordId ↔ posId ↔ execution_order_leg_id` 关系，但保护健康检查仍要求交易所响应再次携带精确持仓 ID，导致主止损被误降级为 `protection_missing`。
- 第二止损创建器只接受 `status=verified` 的主止损，因此全部触发入场持仓被同一条件阻塞。
- 当前第二止损记录为零。市价入场持仓还被 `order_kind=trigger_limit` 过滤规则排除。

## 方案选择

采用“精确所有权证据链”方案。

不采用以下方案：

- 仅调整第二止损创建与健康检查的执行顺序：无法修复主止损误降级和后续止盈阻塞。
- 通过币种、方向、数量、价格或时间推断止损归属：多个同向分仓并存时存在串单风险，不能成为自动交易权限。

## 核心数据流

新持仓保护流程固定为：

```text
入场订单成交
→ 精确确认 posId
→ 创建或采用主止损
→ 持久化不可变 ordId ↔ posId ↔ execution_order_leg_id ↔ binding_id
→ 重新读取交易所挂单
→ 按权威 ordId 验证主止损仍存在
→ 创建第二止损
→ 重新读取并验证第二止损
→ 创建分段止盈
```

Deepcoin 后续查询缺少 `posId` 时，只有同时满足以下条件，主止损才能继续保持 `verified`：

- 订单所有权来自系统提交响应、触发入场子单关联或人工指纹确认；
- `ordId` 在数据库中只属于一个精确 `posId` 和一个活动入场腿；
- 交易所待触发列表中仍存在同一 `ordId`；
- 订单的产品、方向、保护类型和价格没有与持久化证据冲突；
- 当前精确持仓仍然存在且入场腿为 `active + verified`。

出现重复订单 ID、所有权冲突、订单消失、明确失败或交易所读取失败时，继续失败关闭，不得使用启发式证据恢复自动权限。

## 第二止损规则

第二止损距离从 50 bps 改为 20 bps：

- 多仓：`primary_stop × 0.998`
- 空仓：`primary_stop × 1.002`

计算结果按合约价格步长向风险侧保守取整：

- 多仓向下取整；
- 空仓向上取整。

第二止损必须：

- 使用 `POST /deepcoin/trade/trigger-order`；
- 使用 `orderType=market`；
- 使用精确 `closePosId`；
- 使用 `mrgPosition=split`；
- 覆盖当前精确持仓数量；
- 位于主止损的风险侧；
- 位于清算价的安全侧；
- 使用唯一客户端订单 ID；
- 在数据库中保证每个活动精确持仓最多一个活动第二止损。

保护创建顺序固定为“主止损 → 第二止损 → 分段止盈”。第二止损未重新读取并验证前，不允许创建止盈。

第二止损覆盖所有系统自动建立且精确归属的分仓持仓，包括触发入场和市价入场。手工仓、无绑定仓和归属冲突仓继续排除。

## 失败状态机

### 主止损成功

- 持仓消失后终止第二止损和剩余止盈的本地活动状态；
- 交易所仍存在的残留保护必须进入显式清理计划；
- 不得再次提交平仓。

### 主止损明确失败

例如 `NotEnoughMoneyToClose`：

- 记录不可变 `stop_trigger_failed` 事件和事故；
- 保留已经验证存在的第二止损；
- 不自动重新市价平仓；
- 冻结该持仓的自动止盈调整、移动止损和自动减仓；
- 发送一次高优先级告警，包含精确 `posId`、主止损价、第二止损价、错误码和当前持仓状态；
- 根据账户或群组风险阈值阻止继续加仓。

第二止损不能绕过 Deepcoin 的账户偿付能力检查。如果第二止损也明确失败，系统只告警和冻结，不无限重试。

### 结果未知

- 状态设为 `protection_unknown`；
- 不重试、不撤单；
- 重新读取精确持仓、待触发单和历史单；
- 只有确认原请求未产生订单后，才能进入人工恢复计划。

### 订单缺失

- 状态设为 `protection_missing`；
- 已验证第二止损继续保留；
- 禁止自动止盈与管理；
- 生成只读恢复计划，不自动猜测或重建。

第二止损采用同样的成功、明确失败、结果未知和缺失状态机。

## 存量持仓补建

存量修复分为只读计划和人工批准执行。

只读计划逐仓输出：

- 精确 `posId`、策略实例、入场腿、绑定和原消息；
- 当前数量、方向、保证金模式和清算价；
- 主止损订单 ID、价格、状态和所有权来源；
- 按 20 bps 计算的第二止损价；
- 当前是否已有第二止损或相似未归属条件单；
- 合约价格步长和数量步长；
- 可执行、冲突、证据缺失或交易所状态未知；
- 快照时间和不可变计划指纹。

补建必须满足：

- 持仓仍存在且执行前数量未变化；
- 入场腿为 `active + verified`；
- 主止损权威所有权唯一；
- 主止损仍在待触发列表；
- 没有活动第二止损或相似未归属条件单；
- 第二止损位于主止损风险侧和清算价安全侧；
- 合约价格、数量步长有效；
- 执行前快照与人工批准指纹完全一致。

执行时每次只允许一个精确持仓：

1. 重新读取并验证指纹；
2. 提交精确 `closePosId` 的市价条件单；
3. 持久化响应；
4. 重新读取并确认订单 ID、触发价、数量和精确持仓；
5. 验证成功后才能处理下一个持仓。

结果未知时立即停止整个批次。

主止损已明确失败的持仓不进入普通批量补建，必须作为高风险人工恢复案例单独处理。

## 可观测性

第二止损候选被跳过时必须记录有界原因，不能静默返回。至少包括：

- `backup_primary_stop_not_verified`
- `backup_position_not_exact`
- `backup_position_not_live`
- `backup_existing_order`
- `backup_similar_unscoped_order`
- `backup_contract_spec_unavailable`
- `backup_liquidation_price_missing`
- `backup_price_not_safe`
- `backup_snapshot_changed`
- `backup_exchange_outcome_unknown`

Web 详情和系统告警应分别展示主止损与第二止损，不得把两者合并成一个“有保护”状态。

## 测试策略

### 纯逻辑

- 20 bps 多空方向计算；
- 按价格步长向风险侧取整；
- 清算价边界；
- 精确持仓数量覆盖；
- 错误或冲突证据拒绝。

### 所有权与状态机

- Deepcoin 响应缺少 `posId`，但已有唯一权威 `ordId ↔ posId` 时保持 `verified`；
- 没有权威映射时不得用价格、方向、数量或时间认领；
- 主止损失败后第二止损保持活动；
- 结果未知时不重试；
- 重复 reconcile 不创建重复第二止损；
- 市价入场仓能够生成第二止损计划。

### 存量修复

- dry-run 对生产数据库和交易所零写入；
- 指纹变化拒绝执行；
- 相似未归属条件单阻塞；
- 每个 `posId` 只允许一个活动第二止损；
- 单仓结果未知时停止批次；
- 重复执行幂等。

## 生产发布

1. 本地完成聚焦测试和完整测试。
2. 提交并推送到 `codex/deepcoin-auto-trading-v1`。
3. 使用标准服务器 Git 更新流程部署。
4. 确认服务状态、生产 SHA、交易设置和只读管理审计。
5. 部署后先保持存量修复只读。
6. 为全部真实持仓生成 dry-run 计划。
7. 人工逐仓确认。
8. 先选择一个小仓位执行单仓补建并完成交易所、数据库和 Web 三方验证。
9. 再逐仓推进；任何未知结果立即停止。

不得使用测试 Telegram 消息或创建新的真实测试持仓。

## 发布闸门

- 主止损不再因 Deepcoin 响应缺少 `posId` 被误降级；
- 新持仓在止盈创建前已经验证第二止损；
- 第二止损默认距离为 20 bps；
- 存量 dry-run 不包含冲突或相似未归属条件单；
- 任何存量写入都需要人工确认的单仓指纹；
- 主止损失败不会触发自动追单；
- 第二止损失败不会触发无限重试。
