# 「每个持仓都要有双重止损」：现状与缺口（2026-09-23 只读查证）

**用户要求**：每个持仓都应该有双重止损；并称观察到「有时候止损会失败」。
**结论先行**：这个要求**目前没有任何机制保证**。两条能产生备份止损的路径，
一条停用、一条事件驱动，而且停用的那条还被一个判据缺口顶住。

---

## 1. 现在确实有仓位只有单张止损

账本里 `status in (verified, protected)` 的止损行，按仓位数：

```
1001125194995925   n=1   2445.0 (entry_protection_response)   2026-09-09
1001125385572797   n=1   2700   (exchange_adopted_by_tu)      2026-09-23  ← 当时的活仓
```

其余仓位都是 2 张，且第二张恒为第一张的 **20.0 bps**（`trigger_backup_stop_buffer_bps`），
向亏损方向——即主止损 + 备份止损并存。

## 2. 为什么没补上：`unowned_pending_stop_present`

`position_protection_incidents` 里，仓位 `…385572797` 有两条 `backup_stop_blocked`：

```
05:50:14   primary_stop_not_verified        （主止损还没验证；TU 采纳发生在 05:50:59）
05:51:04   unowned_pending_stop_present     ← 之后再没重试成功
```

**被这个原因挡住过的仓位共 16 个**，从 09-07 一直到 09-23，贯穿整个观察期。

判据在 `trigger_backup_stop_executor._unowned_pending_stop_can_affect_position()`：
对账户上每一张 pending TPSL 止损，只要它**同合约、同方向**、不是本仓主止损、
`pos_id` 为空或等于本仓，而且 **`ownership.owner_for_order()` 查不到主人**，
就返回 True 并阻断备份止损。

**它只查账本。** 而 `resolve_protection_authority` 对同一批单有一条排除判据——
`TU == "default"` 且四元组匹配我们自己仍 pending 的入场腿——
这条判据**没有被这里复用**。

于是两腿入场就会自己卡住自己：

```
腿1 成交建仓  →  该仓位要加备份止损
腿2 仍挂着     →  腿2 的自带止损在挂单表里：同合约、同方向、账本无主
                →  unowned_pending_stop_present
                →  腿1 的仓位拿不到备份止损，只剩单张
```

这正是 `…385572797` 此刻的处境（大镖客 ETH 多，腿1 2762 成交，腿2 2732 挂着，
腿2 自带止损 2700）。**和今天上午修的展示层缺口是同一个形态**——
同一批单，权威链认得、这条路径不认得——只是这次的后果不是标签难看，是少一重止损。

## 3. 更根本的一层：没有「每仓自动补备份」的常备机制

能写出备份止损的只有两条路：

| 路径 | 状态 | 说明 |
|---|---|---|
| `trigger_backup_stop_executor`（6f 通道 B） | **停用** | opt-in，靠代码常量里的 posId 名单放行；名单现在为空（4 个历史 id 于 09-11 / 09-12 全部退役）。历史上经它写下的账本行共 2 条 |
| `set_position_sltp` intent（主止损 ×(1±20bps)） | 活跃但**事件驱动** | 由管理指令 / 保本收敛 / 止损阶梯等触发，不是「新仓位建立后自动补一张」。今天 07:11:42 的 intent 745/746 就是这样成对出现的 |

所以「每个持仓都有双重止损」现在是**偶然结果**，不是保证：走到管理动作的仓位有，
没走到的就只有入场自带的那一张。

## 4. 建议（都改交易所写入语义，需用户单独批准）

**第 1 步｜修判据（L2）**：让 `_unowned_pending_stop_can_affect_position` 复用
`protection_authority.resting_entry_stop_owners()`，把「我们自己挂单入场腿自带的止损」
排除在「未归属」之外。

安全性：那张止损绑在**尚未成交**的入场单上，成交前不会平掉任何仓位；
入场一旦成交，它属于**新的 posId**，同样不作用于当前仓位。
这与 `ARCHITECTURE` §4.8 排除规则的理由完全一致。

**第 2 步｜决定常备化方式（L3）**：二选一——
- (a) 放开 `trigger_backup_stop_executor`：把 opt-in 名单改成「对所有 `attribution=verified`
  且在 `auto_trade` 群的仓位生效」。它自带六项字段校验与三道 guardrail，
  是为这件事造的，但**从未在默认开的状态下跑过**。
- (b) 在现有 `set_position_sltp` 路径上加一个收敛任务：仓位建立且主止损 verified 后，
  若无备份止损则补一张。复用已在生产跑的写入路径，但要新建触发与幂等。

**第 3 步｜补巡检（L1）**：任何活仓在主止损 verified 后 N 分钟仍只有单张止损 →
告警到人。无论选 (a) 还是 (b)，这一条都该有：它是「保证」与「偶然」的区别。

## 5. 待用户澄清

「有时候止损会失败」具体指哪一种：
(i) 止损单没挂上（本文第 1–3 节讲的就是这个），
(ii) 止损单挂上了但没触发，
(iii) 触发了但没成交 / 滑点过大。
三者的证据在不同的地方，处置也不同。
