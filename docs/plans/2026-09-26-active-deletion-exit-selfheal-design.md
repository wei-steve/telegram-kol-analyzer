## 1. 要解决的是什么

`source_message_deletion_exits` 的活跃态有四个：
`pending` / `cancelling_entries` / `closing_positions` / `reconciling`。
它们只要不是 `succeeded`，`source_execution_barrier` 就会把同群同币同向的新消息挡住。

已经落地的两件事：

- **看得见**：D6a 现在会在任一封锁态超过 6 小时未动时建案（`df0a54ab`）；
- **救得了**：`recovery_required` 有了"无凭据可撤就收口"的自愈（`0041ae06`）。

**缺的是第三件：活跃态卡住之后没有任何自愈。** 超时清扫器只认 `recovery_required`，
worker 自己又永远在等下一次认领。陈哥那条 lane 被封 11 天，是 `recovery_required` 这一支；
活跃态这一支同样能封，只是还没在生产上咬到人。

## 2. 证据：健康的退出一分钟内就结束

2026-09 至今 160 条 `succeeded` 的退出：

| 耗时 | 条数 |
|---|---|
| ≤ 1 分钟 | **153** |
| 1 分钟 – 1 小时 | 3 |
| 1 – 6 小时 | **0** |
| > 6 小时 | 4 |

那 4 条全是病例：209 / 231 是 2026-09-08 那次人工批量修复放掉的，
310 / 311 是本次陈哥事件人工解封的。**1 到 6 小时这一档是空的**——
也就是说 6 小时的横杆既不会误伤健康的退出，也不需要再往下压。

另一个关键数字：这 4 条卡住的 `attempt_count` 只有 **1–2**，
而正常流转过的行 `attempt_count` 能到几百上千（最大 2097）。
**卡住的行不是"反复尝试失败"，而是"根本没被再认领"。** 这决定了解法的方向。

## 3. 三类成因，不能用同一把锤子

`_claim_next_job` 的事实（读代码得到，不是推测）：

- 认领带 **5 分钟租约**（`claimed_at <= now-5min` 就能被别人抢走），
  所以**进程猝死留下的认领已经会自愈**，这一类不需要新设计；
- 每轮取候选 `WHERE state IN (_ACTIVE_STATES) AND (claim_token IS NULL OR claimed_at <= stale_before)
  ORDER BY id ASC LIMIT 20`，worker 每 tick 最多处理 `max_jobs=10` 条；
- 认领成功会把 `updated_at` 推到当前时间。

由此分出三类：

### C1 · 没被认领（`updated_at` 停住）

候选查询按 **id 升序取 20 条**。如果有 20 条以上活跃行、而低 id 的那些每轮都被取走又放回，
高 id 的行**永远进不了候选窗口**。这是饥饿，不是失败。
D6a 看得见它（`updated_at` 不动就是它的判据），但系统救不了它。

### C2 · 反复认领但不前进（`updated_at` 一直新）

一条每 5 秒被认领一次、每次都回到同一个活跃态的行，`updated_at` 永远是新的——
**D6a 现在看不见它**，因为 D6a 问的是"多久没动过"。
这一类今天在生产上没有样本（卡住的 4 条 `attempt_count` 都是 1–2），
但它是真实可能的形状，而且比 C1 更隐蔽。

### C3 · 真的有在途工作

该撤的单还没撤、该平的仓还没平。这一类**不该自愈**，封着 lane 是对的，
它要的是有人去看。

## 4. 方案：分三级，越往后越危险

### L1 · 调度公平（无交易所写、无状态跃迁）—— 解 C1

把候选查询从 `ORDER BY id ASC` 改成**按 `updated_at` 升序**（最久没动的优先），
或者保留 id 序但对本轮已失败的行加短退避。两者都只影响"先看谁"，不改任何判定。

- 好处：一条被饿住的行最迟下一轮就会被认领，C1 这一类自然消失；
- 风险：低。唯一要注意的是 `updated_at` 升序会让"刚放回去的行"排到最后，
  这正是想要的；但要确认不会让某条一直失败的行被无限重试到独占 `max_jobs`
  ——所以退避那一半不能省。
- 需要一条测试钉住：21 条以上活跃行时，第 21 条仍会在有界轮次内被认领。

### L2 · 让 C2 可见（无写）

给值守加一条判据（**归到 D6a 之下，不新开规则号**）：
一条活跃态的退出，`created_at` 距今超过 6 小时且仍未终结，**即使 `updated_at` 是新的**，
也建案。等价于把 D6a 的"多久没动"换成"多久没完成"——
按第 2 节的数据，健康的退出一分钟内就完成，这条不会误报。

实现上是同一条 sweep 多一个判据，读取形状不变（仍然是那条 `state IN (...)` 的索引查询，
把 `updated_at <= ?` 的界换成 `created_at <= ?` 或者两者取并集——**并集会不会破坏索引计划，
实施时必须用 `EXPLAIN QUERY PLAN` 验证**，这是上一轮定下的规矩）。

### L3 · 有条件释放（会改状态、会解封 lane）—— 只解 C1/C2 里"其实无事可做"的那部分

复用已经上线的 `_no_exchange_footprint_verdict` 三条判据（无 binding/pos/order id +
交易所读取成功 + lane 内每张持仓挂单都已归属别的绑定），**再加两条活跃态专属的守卫**：

1. **当前没有人正在做它**：`claim_token IS NULL` 或 `claimed_at <= now - 5min`（租约已过期）。
   释放必须是一条带 `claim_token` 的条件 UPDATE，输了 CAS 就放弃这一轮——
   绝不能把一条正在被 worker 处理的行从它手里抽走。
2. **年龄横杆用 6 小时**，与 D6a 一致，不另立第二个阈值。

释放动作沿用 `_release`，`last_reason` 用**新的常量**（例如
`released_active_no_exchange_footprint`），与 `released_no_exchange_footprint`
和 `position_gone_confirmed` 三者互相可分辨——事后要能一眼看出是哪条路径放的。

### 明确不做

- **不自动释放带凭据的退出**（有 `execution_binding_id` / `pos_id` / `order_id`）。
  那条路已经存在：凭 pos_id 向交易所证明仓位与挂单都消失，才放。
- **不自动撤单、不自动平仓**。本稿只谈"要不要继续封着 lane"，不碰交易所写。
- **不缩短 6 小时**，也不把 L3 用在 `recovery_required` 以外的旧路径上。
- **不动 barrier 的 `state != 'succeeded'` 规则**。

## 5. 为什么"释放"不等于"放弃撤单"

一条退出存在的理由是：源消息被删了，把它带来的挂单撤掉、仓位平掉。
L3 释放的前提是**我们从来没有为这条消息在交易所放过任何东西**
（无 binding、无 pos_id、无 order_id），并且**这条 lane 上现存的每一张单、每一个仓位
都已经归属于别的绑定**。两条合起来的含义是：没有任何东西在等这条退出去撤。
这时候继续封着 lane，代价是真实的（陈哥 11 天、11 条消息、4 条入场策略），
收益是零。

反过来，只要 lane 里有一张**无主**的持仓或挂单，它就可能正是这条退出该负责的孤儿——
那时候拒绝释放、继续封着才是对的。这条守卫已经在 `recovery_required` 那一支上线并验证过：
陈哥解封当天账户上确实有一张 BTC 多单，但它属于米娅群的 binding 383，可归属，所以放行。

## 6. 验证与观察

- 单测：L1 的饥饿场景（21 条活跃行）、L2 的"updated_at 新但 created_at 老"、
  L3 的五种组合（可释放 / 有无主持仓 / 交易所读失败 / 正在被认领 / 有凭据）。
- 上线前照例在生产上按新判据数一遍首轮量（现在五个活跃态一行都没有，预期 0）。
- 观察窗：上线后 7 天统计 L3 释放了几条、每条释放前封了多久、释放后有没有出现
  "释放完又冒出无主挂单"的反例。一条都没有释放也是合格结果——
  这条路径存在的意义是下一次卡死时不用等人来救。

## 7. 实施顺序建议

L1 → L2 → L3，分三次部署，每次之间留观察窗。

理由：L1 和 L2 都不写状态、不碰交易所，风险接近零，而它们很可能让 L3 永远用不上
（C1 消失之后，能走到 6 小时的活跃态退出就只剩 C2 和 C3 了）。
先把便宜且安全的做完，再决定 L3 值不值得做——**L3 是本稿里唯一会自动改变
"要不要封着 lane"这个判断的东西，它应该是最后一步，而不是第一步。**
