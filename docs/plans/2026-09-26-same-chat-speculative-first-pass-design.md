- 风险等级：实施属于 AGENTS.md L2（并发与顺序语义）；本稿的阶段 0 只加观测，属于 L1。

## 1. 要解决的问题

worker 在同一个群里严格串行：`claim_message_processing_jobs` 用 `ROW_NUMBER() OVER (PARTITION BY chat_id ORDER BY raw_message_id)`，每个群只认领最老的一条（`message_processing_worker.py:338-469`）。同群消息必须等上一条的「首轮识别 → 上下文分析 → 权威处理 → 执行」全部结束，才轮到下一条。

- 近 14 天，排队占端到端耗时的 41%，其中 84% 是同群 lane 等待。
- 最慢的 10 条消息全部是连发图片，端到端 742–964 s。
- 2026-09-16 以来 2154 条实时消息中，481 条被同群前一条堵住；lane 等待合计 38 572 s，首轮识别合计 44 233 s。

## 2. 硬约束：首轮识别不是纯函数

子代理考古的结论（已核对代码）：首轮识别在调用模型**之前**会先构造同群上下文，并把它注入系统提示词。调用链是 `assess_message_authoritatively` → `build_authoritative_context_for_message` → `compose_trading_prompt(context=...)`，见 `authoritative_recognition.py:1186-1196` 和 `recognition_experiments.py:509-513`。

上下文窗口（`contextual_message_window.build_contextual_message_window`）包含三类会被同群前一条消息改变的状态：

1. 同群近 72 小时、最多 50 条消息，**每条都带它自己的首轮证据**（`MessageEvidenceVersion.normalized_evidence`）；
2. 回复链：最多回溯 5 层，每层都带证据；
3. 同群活跃策略生命周期（`StrategyLifecycle`：pending_entry / entered / holding / expired）。

所以，如果在消息 N 还没处理完时就为 N+1 跑首轮，N+1 看到的上下文里：

- 缺少 N 的证据（N 的首轮还没写入）；
- 可能缺少 N 引起的生命周期变化（N 的执行还没发生）。

这就是本设计必须解决的「推测结果是否仍然有效」的问题。**不能简单地并行然后照单全收。**

以下环节必须保持串行，本设计不碰：上下文分析、权威决策落库、执行认领、交易所写入、策略解析。

## 3. 可借用的现有机制

- `build_message_input_fingerprint`（`message_evidence.py:326-397`）：对消息自身的文本、编辑时间、媒体内容做指纹。
- `message_evidence_extraction_claims`：按 `raw_message_id` 独占的 300 s 租约，天然防止同一条消息被重复识别。
- `assess_message_authoritatively(reuse_current_evidence=True)` → `_load_current_mimo_evidence_result`：读取已有证据，**不调用模型**。
  但它**不校验输入指纹**，也不校验上下文，生产上只在「重新分析」入口使用。不能直接拿来消费预取结果。

## 4. 方案

### 4.1 核心机制：带「上下文指纹」的预取加严格核对

**预取（推测）：**
- worker 处理 lane 头部消息 N 时，可以为同群排在后面的消息 N+1…N+k 发起首轮识别；
- 预取与生产路径使用同一套提示词和同一个上下文构造器，但结果写进一张**新表** `first_pass_prefetches`，不写 `MessageEvidenceVersion`，不产生任何权威状态；
- 每一行记录：
  - `raw_message_id`、`input_fingerprint`；
  - `context_fingerprint`：渲染后的上下文文本的 sha256；
  - `prompt_versions_json`、`model`、payload、耗时；
  - `consumed_at` / `discarded_reason`。

**消费（串行轮到 N+1 时）：**
- 照常在现在的时刻构造上下文，只查库，不调模型，耗时毫秒级；
- 同时满足以下四条才采用预取结果，走与今天完全相同的落库、上下文分析和执行路径：
  - 当前 `input_fingerprint` 等于预取时的；
  - 当前 `context_fingerprint` 等于预取时的；
  - 提示词版本一致；
  - 模型链首一致。
- 任一不等就丢弃预取结果，照今天的方式调用模型。

**正确性论证：**
- 采用的预取结果，其输入和今天串行调用时的输入逐字节相同：同一消息、同一上下文、同一提示词、同一模型。
- 二者之间唯一的差别是模型采样的随机性，而今天的重试和回退本来就接受这一点。
- 所以严格模式在语义上**等价于现状**。最坏情况是白花一次模型调用，不会改变任何决策。

### 4.2 两种发起时机

| | A. 流水线式（深度 1） | B. 提前式（深度 k） |
|---|---|---|
| 何时为 N+1 发起 | N 的首轮证据写入之后，N 进入上下文分析或执行时 | N+1 一入队就发起，与 N 的首轮并行 |
| 上下文指纹能否命中 | 较高：N 的证据已经在窗口里，只有 N 的上下文分析或执行改了生命周期时才不命中 | **严格模式下几乎总是不命中**：N+1 的上下文里没有 N 的证据，消费时有了 |
| 模拟收益（09-16 以来，假设全部命中） | 端到端均值 48.1 → 46.3 s，P90 108 → 102 s，最大 912 → 869 s | 均值 48.1 → 40.0 s，P90 108 → 87 s，P99 309 → 255 s，最大 912 → 541 s |
| 结论 | 安全，但收益很小：N 的上下文分析通常短于 N+1 的首轮，能叠起来的时间有限 | 收益才像样，但严格模式吃不到，除非放宽核对规则（见 4.3） |

模拟方法：逐群按入队顺序重放，服务时间用实测的首轮耗时和「首轮结束到落库」耗时，然后比较端到端分布。现状一栏的模拟值（P50 23.3 s）与实测值（P50 25 s）基本吻合。

### 4.3 放宽核对（只为 B 服务，需要单独批准）

- 允许消费时的上下文与预取时的上下文存在如下差异：窗口里多出了若干条**首轮判为闲话 / 非策略、生命周期事件为 none、没有产生任何生命周期变化**的同群前序消息的证据，其余部分完全相同。
- 理由：提示词要求「必须优先依据当前消息，不能把旧上下文当成当前动作」，而闲话证据对当前消息的判定通常是噪声。
- **反例风险**：Telegram 相册只有一张图带文字说明，其余图片 `text` 为空。第 2 张图的含义可能正要靠第 1 张的文字，而第 1 张的首轮可能恰好被判为闲话。放宽规则会让第 2 张看不到这段说明。纯图连发正是 B 收益最大的场景，所以这个风险不能靠推理排除，**只能靠离线回放测量**：
  - 对历史连发，比较「带前序闲话证据」和「不带」两种上下文下的首轮结论一致率；
  - 这需要用现有识别供应商重跑一批历史消息，会产生额外调用和费用；
  - 数据仍然只发给生产本来就在用的供应商，不涉及新的第三方，但需要用户批准。

### 4.4 与现有不变量的交互

| 机制 | 处理方式 |
|---|---|
| 同群顺序（`test_chat_lanes_are_ordered_while_different_chats_run_concurrently`） | 不变：预取不认领作业，不改变 lane |
| 300 s 作业认领租约、240 s 链总时限 | 预取不持有作业租约，预取自身设 240 s 上限；消费发生在正式认领之内，并且只查库 |
| `message_evidence_extraction_claims` | 预取**不**获取这个租约（它不写证据），避免与串行路径抢锁 |
| 跨群并发上限 `message_processing_max_parallel_chats`（默认 20） | 另设预取并发上限（建议全局 2–3），不占用 lane 名额；供应商故障期暂停预取 |
| `recovery_` / `history_reconcile_` 来源的作业 | 不预取：这些是补齐路径，本来就关闭了上下文调度 |
| 消息编辑 | 编辑会改变 `input_fingerprint`，消费时自动不命中 |
| 消息删除 | 预取结果不产生权威状态，删除后作业走原路径；预取行过期清理即可 |
| 缺口恢复与过期分类 | 看的是 `recognition_decisions`，预取不写这张表，不受影响 |
| 供应商健康线（`mimo_provider_health`） | 预取的调用**不写** `mimo_recognition_attempts`，只写自己的表，避免污染链首健康统计；被消费时再补写一行 attempt，并标明来自预取 |
| 审计 | `mimo_recognition_runs` 增加一个来源标记（prefetch_consumed）；页面卡片展示时注明 |

### 4.5 成本

- 严格模式 B 几乎全部不命中，等于每条被堵的消息多花一次模型调用：09-16 以来约 481 次，每次约 3 万输入 token。
- A 的浪费只发生在 N 改变了生命周期时。
- 所以阶段 1 必须先做**零调用的观测**，确定命中率之后再决定要不要花这笔钱。

## 5. 分阶段计划

| 阶段 | 内容 | 模型调用 | 等级 |
|---|---|---|---|
| 0 | 前提：先完成识别校验器修复（报告 §7）和上下文触发收紧（报告 §8.3，28 日之后），再重新测量基线 | — | — |
| 1 | **影子观测，零调用**：串行处理 N+1 时，分别计算「若在 N 首轮结束时预取」和「若在 N+1 入队时预取」的上下文指纹，与实际指纹比较；记录命中与否，以及不命中时的差异类别（多了前序证据 / 生命周期变化 / 回复链变化） | 0 | L1 |
| 2 | 按阶段 1 的数据决定：A 的命中率足够高就实施 A（严格模式，默认关闭，按群开启）；否则只在 4.3 的离线回放获批并通过后才考虑 B | A：少量 | L2 |
| 3 | 实施后观察：同群顺序、预取浪费率、端到端分布、供应商健康线 | — | L2 观察窗 |

**关闭与回滚：** 一个全局开关加一个群白名单；关闭后行为与今天逐字节一致。预取表是新增表，回滚时不需要删除。

## 6. 结论与建议

- 同群并行识别**能**做到与现状语义等价（严格核对），但严格模式下的真实收益，取决于首轮上下文在消息之间变化得有多频繁，目前还不知道。
- 按模拟上限估算：B 能把端到端 P90 从约 108 s 降到约 87 s，最慢的连发从约 15 分钟降到约 9 分钟；A 只能降到约 102 s。
- 相比之下：
  - 报告 §7 的校验器修复（识别 P90 从 65 s 降到约 27 s），以及让上下文分析更快，性价比都高得多；
  - 而且它们会**同时**缩短 lane 等待，因为 lane 等待就是前一条消息服务时间的累加。
- **建议**：先做阶段 1 的零调用观测，同时完成 §7 和 §8.3，再用新的基线决定是否进入阶段 2。不建议现在直接实施 B。
