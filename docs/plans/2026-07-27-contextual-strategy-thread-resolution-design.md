# 上下文策略链自动归属设计

## 背景

部分 Telegram 群组会连续发布同一策略的开仓、更新、取消和持仓管理消息，
并大量使用“更新”“先取消”“有入场的”“保护成本”等依赖上下文的表达。
当前识别流程会向 MiMo 提供最近消息和活跃生命周期，但上下文缺少消息时间、
真实持仓与挂单状态，也没有持久化的策略修订链。结果是同一策略的“更新”可能
被创建为独立策略，后续“取消”只作用于新策略，旧挂单仍可能成交。

图文混合消息还存在另一层风险：MiMo 当前一次性接收文字和图片并输出综合
结论，历史截图里的参数可能与当前文字混合。DeepSeek 无法直接读取图片，
也就无法独立检查视觉证据。

本设计的目标是在不依赖日常人工选单的情况下，把消息、引用关系、策略版本和
交易所状态组成可审计的事件链，由二次 AI 完成归属裁决，再由确定性安全规则
决定是否允许执行。

## 设计原则

1. 图片只在消息首次处理或内容版本变化时读取一次，后续复用已保存的结构化
   证据。
2. Telegram 直接回复关系是强身份线索，但不能越过币种、方向、生命周期和
   真实持仓校验。
3. “更新”默认表示修订已有策略，而不是无条件创建新策略。
4. AI 负责语义归属；交易写入前仍由确定性代码验证精确策略、订单和持仓身份。
5. 歧义不应立即升级人工。系统先等待后续消息或状态变化并自动重分析。
6. 无法唯一归属时禁止扩大风险；目标集合可验证时，允许自动执行撤单、减仓、
   提高止损等风险降低动作。
7. 原始输入、提取证据、裁决结果和执行结果都必须可版本化、可追溯。

## 总体架构

流程拆成五层：

1. **消息证据提取**：MiMo 分别提取文字事实和图片事实，不作跨消息归属。
2. **策略链候选生成**：确定性代码根据回复链、历史链接、群组、币种、方向、
   时间和状态生成有限候选集。
3. **上下文二次裁决**：DeepSeek 读取标准化消息事件、候选策略和交易所摘要，
   判断当前消息属于哪个策略链以及动作类型。
4. **安全执行规划**：现有管理规划器把裁决结果转换为精确生命周期、绑定、
   执行腿和 `posId` 操作。
5. **结果反馈与重分析**：新消息、消息编辑、挂单成交或持仓状态变化会重新评估
   未决裁决，但不会静默重放已经提交的交易写入。

## 1. 标准化消息证据

新增版本化的 `message_evidence_versions` 记录。每个版本至少保存：

- `raw_message_id`
- 消息内容指纹，包括文字、媒体指纹和编辑时间
- MiMo 模型与提示词版本
- 提取状态和整体置信度
- `text_evidence_json`
- `image_evidence_json`
- `normalized_evidence_json`
- 创建时间和被新版本替代的时间

文字证据和图片证据必须分开。每个交易字段都保存：

- 字段值
- 来源：`text`、`image` 或 `both`
- 证据片段或图片区域说明
- 置信度
- 是否与另一来源冲突

图片证据还需标记图片类型：

- 策略参数图
- 持仓截图
- 成交或委托截图
- 行情图
- 盈利展示或复盘
- 广告或无关图片
- 无法判断

MiMo 首次提取图片事实时不决定该消息应该管理哪个历史策略。后续 DeepSeek
只读取保存的结构化视觉证据，不需要直接看图。

如果消息被编辑、媒体变化或提取模型升级，生成新版本，旧版本保留。若旧版本
已经触发交易，新版本只能进入差异审查和后续规划，不能撤销或重放历史请求。

## 2. Telegram 回复链

现有 `raw_messages.reply_to_message_id` 作为回复图入口。上下文构建器应：

1. 在同一 `chat_id` 内解析被回复消息。
2. 附带被回复消息的当前证据版本及其策略链链接。
3. 最多向前追踪五层回复，检测循环。
4. 若目标消息不在本地，尝试通过 Telegram 精确补取一次。
5. 补取失败时记录 `reply_target_unavailable`，不得伪装成没有回复关系。

归属线索优先级为：

`直接回复 > 已确认策略链链接 > 明确身份参数 > 时间邻近 > 语义相似度`

引用关系不是无条件执行授权。引用 BTC 多单但当前文字明确描述 ETH 空单时，
二次裁决必须返回冲突。引用已结束策略的复盘消息不能创建新策略；只有明确的
“再做一次”“重新进场”等动作才允许创建新策略链。

## 3. 策略链与消息链接

新增 `strategy_threads`，表示人类语义上的一轮策略，而不是单条消息：

- `id`
- `chat_id`
- 根消息 ID
- 币种和方向
- 当前状态
- 当前生命周期 ID
- 创建与更新时间

新增 `strategy_message_links`：

- `strategy_thread_id`
- `raw_message_id`
- `message_evidence_version_id`
- 关系类型：
  `root_entry`、`revision`、`cancel`、`management`、`hold`、`exit`、`reopen`
- 裁决来源和置信度
- 引用的证据消息 ID 列表
- 裁决版本与状态

`strategy_lifecycles` 增加可空的 `strategy_thread_id`。历史数据可以渐进回填；
没有充分证据的历史生命周期不自动合并。

同一策略链可以有多条参数修订消息，但真实交易身份仍由生命周期、绑定、执行腿
和 `posId` 决定。策略链只解决语义连续性，不能代替交易所身份链。

## 4. 二次 AI 归属裁决

以下情况触发二次裁决：

- 出现“更新”“取消”“有入场的”“继续持有”“保护成本”等上下文话术；
- 第一轮识别返回管理动作但没有唯一目标；
- 同群同币种同方向存在多个候选策略；
- 文字与图片证据冲突；
- 回复关系与第一轮目标不一致；
- 第一轮把疑似修订识别为新开仓。

上下文窗口采用动态规则：

- 从最早仍未结束的相关策略开始；
- 最多回看 72 小时；
- 最多 50 条消息；
- 回复链消息不受普通时间截断影响，但仍受五层限制。

提供给 DeepSeek 的输入包括：

- 当前消息及时间、消息 ID、编辑状态和回复关系；
- 窗口内各消息的标准化证据；
- 回复链；
- 候选策略链及其全部消息链接；
- 生命周期、绑定和执行腿状态；
- 精简后的真实持仓、未成交入场腿和当前保护摘要；
- 第一轮 MiMo 的动作判断；
- 候选生成器给出的候选目标及原因。

DeepSeek 必须输出闭合结构：

- `decision`: `new_thread`、`revise_thread`、`manage_thread`、
  `cancel_thread`、`exit_thread`、`hold_thread`、`unresolved`
- 一个或多个目标策略链 ID
- 动作和参数
- 置信度
- 支持证据消息 ID
- 反对证据消息 ID
- 是否存在文字/图片或回复/内容冲突
- 是否允许风险降低型多目标扇出
- 建议的重新分析触发条件

不能只输出自然语言结论。

## 5. 确定性动作语义

### “更新”

- 若唯一目标仍是 `pending_entry`，把消息链接为修订；规划器取消该策略链尚未
  成交的旧入场腿，再按新参数创建替代腿。
- 若目标已有真实持仓，更新只能形成持仓管理计划。未明确加仓时不得创建新的
  入场策略。
- 若文字明确“另一单”“再开一单”“重新进场”，才创建新策略链。
- 替换入场必须先确认旧腿取消结果；结果未知时禁止提交新腿。

### “取消”

- 回复或唯一归属目标为 `pending_entry`：取消该策略链全部未成交入场腿。
- 目标已有持仓且文字只说“取消挂单/策略先取消”：仅取消未成交入场腿，
  不自动平掉已成交仓位。
- 只有“离场、平仓、全部止盈”等明确退出语义才可关闭真实持仓。
- 同一策略链存在已成交和未成交腿时，分别处理，不能把撤单等同于平仓。

### “有入场的”

- 候选范围限定为同群、相关时间窗口、币种和方向一致且拥有已验证真实持仓的
  策略链。
- “止盈一半、带保护、移动保本”等风险降低动作可对全部验证目标自动扇出。
- 加仓、放宽止损、取消保护等风险增加动作必须唯一归属。

### “保护成本”

- 动作语义与价格参数分开。`move_stop_to_break_even` 必须以每个真实持仓自己的
  `avgPx` 计算，不能复用生命周期中的旧支撑位或模型猜测价格。
- 若消息明确给出保护价，先验证该价格确实降低风险，再使用明确价格。

## 6. 自动消歧与失败处理

`unresolved` 不直接要求人工选单。系统持久化未决裁决，并在以下事件发生时
自动重跑：

- 同群收到下一条消息；
- 被回复消息补取成功；
- 入场腿成交或取消；
- 真实持仓或保护状态变化；
- 消息被编辑；
- 证据提取生成新版本。

未决期间：

- 保持现有仓位和保护，不取消有效止损；
- 不提交新开仓、加仓或放宽止损；
- 若存在完整、唯一且风险降低的多目标集合，可执行减仓、撤销未成交入场腿或
  收紧保护；
- 记录自动重试次数和截止时间；
- 超过截止时间仍未解决时发送一次异常通知，但不要求操作者逐仓选择，除非后续
  确实需要扩大风险。

API 超时或交易结果未知继续沿用现有 fail-closed 和精确对账机制，绝不因为 AI
重新裁决而自动重试可能已成功的交易请求。

## 7. 数据流

1. Telegram 消息入库，保存文字、媒体和 `reply_to_message_id`。
2. MiMo 生成版本化的文字/图片证据。
3. 第一轮动作识别判断是否包含策略或管理语义。
4. 候选生成器构造策略链候选和回复链。
5. 简单且唯一的新开仓继续走现有路径；上下文动作进入二次裁决。
6. DeepSeek 输出结构化策略链决策。
7. 确定性验证器检查消息来源、生命周期、绑定、执行腿、`posId`、持仓和保护。
8. 规划器生成幂等批次；执行器按现有精确写边界提交。
9. 对账结果回写策略链链接、生命周期和未决裁决。

## 8. 可观测性

策略详情页应展示：

- 策略链根消息与全部修订/管理消息；
- 每条消息的时间、回复关系和证据版本；
- 图片提取摘要及来源；
- 二次裁决选择的目标、置信度和证据消息；
- 当前真实持仓、未成交腿和保护；
- 未决原因及下一次自动重分析条件。

告警应聚焦系统无法自动恢复的异常，不为每次普通二次分析或自动重试发送通知。

## 9. 测试范围

### 单元测试

- 图文消息分别保存文字和图片证据，字段来源不混合。
- 图片提取失败、低置信度和文字/图片冲突。
- 消息编辑产生新证据版本，旧版本保留。
- 直接回复、五层回复、循环和缺失回复目标。
- 动态 72 小时/50 条窗口及回复链越界保留。
- 二次裁决闭合输出校验和非法目标拒绝。
- `move_stop_to_break_even` 使用真实 `avgPx`。

### 场景回放

- `1460 → 1462 更新 → 1465 取消` 被识别为同一策略链，旧入场腿不会继续
  成交。
- 图中是旧 BTC 多单，当前文字是 ETH 空单，系统返回冲突。
- 回复待入场策略说“取消”，只撤未成交腿。
- 回复已入场策略说“取消挂单”，保留真实仓位和保护。
- 同群多个 BTC 多单收到“有入场的止盈一半带保护”，只对验证持仓执行风险
  降低型扇出。
- “保护成本”对每个分仓使用各自均价。
- 结果未知、消息编辑和服务重启不会重复提交。

### 生产验证

按项目流程先运行本地单元测试。部署后仅使用服务器真实消息和只读交易所快照
验证策略链、回复链和裁决输出。先保持新裁决器为 shadow 模式，对历史消息和
新消息运行至少一个观察窗口，比较现有结果与新结果；确认不会跨策略修改订单后，
再逐群启用自动执行。

## 10. 迁移与上线

1. 增加证据版本、策略链、消息链接和未决裁决存储。
2. 首次只对新消息生成证据版本；历史消息按活跃策略所需窗口惰性回填。
3. 二次裁决器以 shadow 模式运行并记录差异。
4. 先在“大漂亮社区 11分组”启用上下文归属，但执行仍沿用现有安全写边界。
5. 验证 `1460/1462/1465` 历史回放和新消息。
6. 启用风险降低型自动动作。
7. 最后才允许唯一目标的挂单替换；风险增加动作继续要求唯一、高置信目标。

## 不在本次范围

- 用 AI 猜测交易所订单或持仓归属。
- 自动合并缺少证据的历史生命周期。
- 在结果未知时重试真实交易写入。
- 让 DeepSeek 直接读取图片。
- 因新证据版本自动撤销已经执行的历史交易。
