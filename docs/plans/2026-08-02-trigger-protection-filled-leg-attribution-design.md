# 触发入场保护单成交腿归属修复设计

## 背景

触发入场单在未成交时只有父入场 `ordId`，尚未产生仓位
`posId` 和止损子单 `ordId`。Deepcoin 在父单成交后异步生成附带
止损，但待触发 TPSL 读回经常缺少 `posId`、父入场单号和入场
价格。因此系统必须在成交后把新出现的止损子单与已验证入场
腿绑定，然后才能写入权威 `posId ↔ ordId` 保护账本。

舒琴 ETH 多单暴露了当前缺口：

- 第一腿入场价 `1828`，已成交，获得
  `posId=1001124534587219`；
- 第二腿入场价 `1808`，仍处于 `pending`；
- 两腿数量都是 `0.6`，计划止损都是 `1695`；
- Deepcoin 为第一腿产生了止损子单
  `ordId=1001124534587218`，但读回不包含 `posId` 或父单号；
- 当前冲突检查只比较合约、方向、数量和止损价，把未成交第二
  腿也当成潜在所有者，最终以
  `trigger_protection_candidate_not_unique` 拒绝写入账本。

两腿入场价并不相同。问题是止损子单根本不携带入场价，同时
当前规则没有利用“一腿已精确成交、另一腿尚未成交”的权威状态。

## 目标

建立触发入场附带保护的完整账本闭环：

```text
strategy_instance
→ execution_binding
→ entry_leg
→ parent_entry_ordId
→ filled_posId
→ protection_child_ordId
→ verified_position_protection_ledger
```

对每个活动自动仓位，保护子单 `ordId` 必须最终唯一对应一个
`posId`、一个入场腿和一个策略实例。不得使用单纯价格、数量或
时间推断绕过精确入场腿状态。

## 方案选择

采用“成交腿状态驱动的确定性认领”方案。

不采用以下方案：

- **成交后改为新建 `closePosId` 止损**：身份最清晰，但父单成交到
  持仓止损创建之间存在无保护窗口，需要另外引入失败自动平仓政策。
- **重建全局统一事件账本**：长期能力更强，但改动范围大，不是修复
  当前生产缺口的最小安全方案。

本方案保留现有触发入场附带主止损的方式，但修正成交后子单
所有者集合，并将计划保护腿的 `posId` 绑定提前到子单认领之前。

## 权威数据与不变量

### 入场腿

入场腿只有同时满足以下条件才是保护子单的潜在所有者：

- `purpose=entry`；
- `order_kind=trigger_limit`；
- `status=active`；
- `attribution_status=verified`；
- 具有非空且仍在交易所存在的精确 `posId`；
- 父入场 `ordId` 与已持久执行事件一致。

`pending`、`submitted`、`unassigned` 或没有 `posId` 的兄弟腿尚未产生
持仓，因此不能成为成交后持仓止损子单的所有者。

### 保护子单

没有交易所 `posId` 的 TPSL 子单只能在以下条件全部成立时认领：

- 不在该入场腿提交前的持久化 TPSL 基线中；
- 合约、持仓方向、数量和已请求保护集完全匹配；
- 子单的交易所创建时间不早于已验证入场成交时间；
- 交易所没有返回与目标 `posId` 冲突的仓位身份；
- 只有一个满足条件的子单 `ordId`；
- 没有另一个具有相同保护特征且同样为
  `active + verified + posId` 的入场腿。

价格、数量和时间只用于验证已经由精确成交腿状态缩小后的唯一
候选，不得单独产生自动交易权限。

### 账本唯一性

- 一个交易所保护 `ordId` 只能对应一个 `posId`、一个入场腿和一个
  binding；
- 一个计划主止损腿只能绑定一个交易所保护 `ordId`；
- 一个已验证入场腿只能绑定一个活动分仓 `posId`；
- 已持久映射为不可变身份，任何不一致读回都进入冲突状态，
  不得自动改绑。

## 成交后数据流

### 1. 绑定成交仓位

当现有入场归属逻辑把精确 `posId` 写入 `ExecutionOrderLeg` 时，同一
事务内把该 `posId` 绑定到该入场腿的所有
`PositionProtectionLeg`，并将状态从 `planned` 推进到
`waiting_fill` 或新的等价“等待交易所子单”状态。

这一步只绑定已经由入场归属层验证的 `posId`，不进行任何新的
交易所写入。

### 2. 筛选可认领保护子单

修改 `plan_trigger_protection_intent_adoption()` 的调用数据，使其获得其他
保护意图对应入场腿的最小权威状态，至少包含：

- `execution_order_leg_id`；
- `status`；
- `attribution_status`；
- `pos_id`；
- 父入场 `ordId`；
- 已验证成交时间。

当候选子单没有 `posId` 时，只有其他同特征意图对应的入场腿也是
`active + verified + posId` 时才产生真实冲突。单纯存在另一条
`pending` 保护意图不得阻塞已成交腿。

### 3. 原子落账

认领成功后，在同一数据库事务内：

1. 将主止损 `PositionProtectionLeg.exchange_order_id` 绑定为候选
   `ordId`；
2. 写入完整读回证据并将逻辑保护腿标记为 `verified`；
3. 写入或幂等更新 `PositionProtectionLedger`的
   `posId ↔ ordId ↔ entry_leg ↔ binding`；
4. 将 `TriggerProtectionIntent` 转换为 `adopted`，固化
   `adopted_order_id`；
5. 记录保护 revision，使 Web、风险检查和后续管理使用同一权威
   映射。

任何字段冲突都必须回滚整个事务。

### 4. 后续保护顺序

主止损账本未验证前：

- 不创建第二止损；
- 不创建分段止盈；
- 不开放保护修改或自动仓位管理权限。

主止损落账并重新读回验证后，继续使用当前“主止损 → 第二
止损 → 分段止盈”顺序。

## 失败状态机

### 候选尚未可见

- 保持 `pending` 或 `retrying`；
- 按有界退避重试；
- 不写入最终账本；
- 不把“尚未可见”误记为永久身份冲突。

### 交易所读取失败

- 记录 `evidence_unavailable`；
- 保留上次已验证入场归属；
- 不消耗为永久的保护认领失败；
- 恢复读取后继续原意图。

### 真实冲突

以下任一情况必须冻结并告警：

- 有多个候选子单；
- 另一条同特征入场腿也已
  `active + verified + posId`；
- 交易所返回的仓位身份与目标 `posId` 冲突；
- `ordId` 已被另一个账本所有者占用；
- 已绑定的 `PositionProtectionLeg` 身份与新证据不一致。

真实冲突不得通过更长时间窗口、最近价格或人工选择绕过自动
交易权限。

### 超过有界恢复窗口

- 保护意图进入 `failed`；
- 持仓保持失败关闭，禁止后续自动管理；
- 生成包含精确入场腿、`posId`、父入场单、候选子单和原因的事故；
- 不自动撤销、重建或平仓，以免扩大交易所写入范围。

## 存量失败意图修复

存量 `failed` 保护意图不得直接改回 `pending`。增加只读修复规划，
为每个候选输出：

- 策略实例、binding、入场腿和父入场 `ordId`；
- 精确 `posId`、合约、方向和当前数量；
- 计划止损和唯一候选止损 `ordId`；
- 所有兄弟入场腿的状态和仓位身份；
- 交易所快照时间；
- 不可变修复指纹；
- `repairable`、`conflict`、`evidence_unavailable` 或 `not_live` 结论。

执行修复必须携带人工批准的单仓指纹，执行前重新读取交易所和
数据库，只在指纹完全一致时写入账本。执行只建立已有交易所对象的
身份关系，不创建、撤销或修改任何交易所订单。

舒琴持仓修复前必须再次验证：

```text
entry_leg_id = 422
parent_entry_ordId = 1001124512202881
posId = 1001124534587219
stop_ordId = 1001124534587218
stop = 1695
size = 0.6
sibling entry_leg_id = 423 remains pending without posId
```

上述值只是当前读取的生产事实，不得硬编码到通用修复逻辑中。

## 与止损更正消息的边界

本设计只修复已存在主止损的账本归属。舒琴后续消息将止损从
`1695` 更正为 `1795`，但该消息因上下文解析合约错误未生效。

存量账本修复不得顺便修改交易所止损。`1795` 需要通过独立的消息
重处理或精确持仓止损调整流程执行，并单独完成请求、响应、读回和
账本验证。

## 测试策略

### 规则单测

- 两腿入场价不同，数量和止损相同；第一腿
  `active + verified + posId`，第二腿 `pending`；唯一子单应归属第一腿。
- 两腿均为 `active + verified + posId` 且保护特征相同；无 `posId`
  子单必须拒绝认领。
- 另一保护意图为 `pending`，但其入场腿已经精确成交；必须按成交
  腿状态而不是意图状态判断冲突。
- 子单在基线中已存在、交易所时间早于成交或返回冲突 `posId`；
  必须拒绝认领。
- 同时有多个匹配子单；必须拒绝认领。
- `ordId` 已被其他账本所有者占用；必须拒绝认领。

### 幂等与崩溃恢复

- `posId` 绑定后、子单认领前崩溃；重启后继续认领。
- 保护腿绑定 `ordId` 后、最终账本写入前崩溃；整个事务回滚。
- 账本写入后、意图转为 `adopted` 前崩溃；整个事务回滚。
- 重复 reconcile 不产生第二条映射，不改变已验证所有者。

### 集成测试

- 用伪造 Deepcoin 快照完整重现舒琴两腿场景，从入场腿归属到最终
  账本落地全链路验证。
- 验证主止损落账前第二止损和分段止盈均被阻塞。
- 验证主止损落账后按现有顺序解锁第二止损与分段止盈。
- 验证 Web 持仓页只从已验证账本显示该止损。
- 验证存量修复 dry-run 零数据库和交易所写入，指纹不一致时拒绝执行。

## 生产验证与回滚

1. 本地运行精确规则、执行绑定、保护账本、Web 和修复工具聚焦测试。
2. 提交并推送到 `codex/deepcoin-auto-trading-v1`。
3. 通过标准 Git 更新流程部署服务器。
4. 在不写入交易所的情况下执行新规则 dry-run，检查所有活动
   触发入场保护意图。
5. 生成舒琴单仓修复指纹，人工确认后只写入本地账本。
6. 重新读取 Deepcoin、生产数据库和 Web，验证三方的
   `posId`、`ordId`、触发价和数量一致。
7. 只在保护归属稳定后，单独处理舒琴 `1795` 止损更正。

代码回滚通过恢复上一个 Git 提交完成。账本身份映射为事实记录，
回滚代码时不删除已验证映射；如果新映射后续与交易所读回冲突，
通过显式事故和人工修复处理，不做破坏性回滚。

## 发布闸门

- 舒琴形状的两腿场景能把唯一止损子单落到已成交腿账本；
- 未成交兄弟腿不再产生假冲突；
- 两条同特征成交腿仍然失败关闭；
- 任何已验证保护 `ordId` 只对应一个 `posId` 和一个入场腿；
- 主止损未验证前不创建第二止损和止盈；
- 存量修复必须是只读计划加单仓指纹批准；
- 新逻辑不提交、撤销或修改任何额外交易所订单；
- 修复归属不与 `1795` 止损价更正混合。
