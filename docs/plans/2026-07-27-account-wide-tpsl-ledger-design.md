# 全账户 TPSL 权威账本设计

## 背景

Deepcoin 的待触发 TPSL 接口经常返回 `ordId`、方向、数量和价格，却不返回
`posId`。系统已经在多个本地表中保存了准确的 `ordId → posId` 绑定，但不同
读取路径对这些证据的使用并不一致：

- Web 展示会汇总主保护账本、第二止损表和止盈表；
- 保护健康审计只查看当前持仓自己的局部记录；
- 部分管理路径仍会按币种、方向、数量或创建时间选择 TPSL；
- `sz=0` 的全仓 TPSL 可能被视为会影响所有同方向持仓。

生产只读基线显示当前 8 个持仓对应 25 笔待触发 TPSL，25 笔都能从现有本地
记录得到唯一的 `ordId → posId` 绑定，没有真正的未归属订单或绑定冲突。
因此当前“全部 `protected=false`”主要是读取和归属规则不统一造成的误报，
不是账本证据缺失。

## 目标

将 `position_protection_ledger` 设为 TPSL 归属的唯一权威来源，并使展示、
健康审计、告警、管理计划、调整、替换和撤单全部使用同一份全账户
`(venue, ordId) → posId` 映射。

系统只接受两类自动归属证据：

1. 交易所 TPSL 行明确携带 `posId`；
2. 权威账本存在唯一的 `ordId → posId` 绑定。

币种、方向、价格、数量、`sz=0`、创建时间以及“候选唯一”只能用于人工审核
材料，不能建立自动归属，不能授权交易所写操作。

## 非目标

- 本次不合并或删除 `position_backup_stop_orders` 和
  `position_take_profit_orders`。它们继续记录业务流程、状态和审计信息。
- 本次不自动接管新的手动 TPSL。
- 本次不在验证过程中创建、修改或撤销真实订单。
- 本次不自动解除全局交易冻结。
- 本次不根据价格、方向或时间自动回填历史归属。

## 方案选择

### 方案 A：只修复当前误报

让保护审计同时读取三个表的全局映射。改动小，但三个表继续共同承担归属
权威，未来新增路径仍可能漏读其中一张表。

### 方案 B：单一权威账本

把现有精确映射回填到 `position_protection_ledger`，之后所有创建路径同步
写入该账本，所有读取和写操作只从该账本取得归属。业务表保留，但不再提供
归属授权。

这是采用的方案。它能在保留现有业务状态的同时消除多套归属规则。

### 方案 C：立即合并业务表

删除第二止损和止盈业务表，把所有状态都塞入账本。结构表面最简单，但会
混合归属证据与业务状态，迁移和回滚风险过高。

## 权威数据模型

现有 `position_protection_ledger` 已具有所需核心字段：

- `venue`
- `order_id`
- `pos_id`
- `execution_binding_id`
- `execution_order_leg_id`
- `strategy_instance_id`
- `instrument_id`
- `side`
- `purpose`
- `trigger_price`
- `size_text`
- `status`
- `evidence_source`
- `evidence_json`

现有 `(venue, order_id)` 唯一索引继续作为数据库级冲突防线。账本行保留历史
状态；订单成交或撤销后更新状态，但不改变其历史所有者。

业务表的职责变为：

- `position_backup_stop_orders`：第二止损提交、回读、取消和失败状态；
- `position_take_profit_orders`：分批止盈提交、回读、取消和完成状态；
- `position_protection_ledger`：唯一的订单归属和交易授权证据。

## 全账户账本读取层

新增统一读取组件，一次加载目标账户的全部保护账本行，构造不可变索引：

```text
(venue, order_id) → LedgerOwnership(pos_id, status, purpose, evidence)
pos_id → [LedgerOwnership]
```

读取结果区分：

- `owned`：账本唯一绑定，且交易所显式 `posId` 不与其冲突；
- `unowned`：交易所存在 TPSL，但账本没有该 `ordId`；
- `conflict`：同一订单出现多个所有者，或交易所显式 `posId` 与账本冲突；
- `stale`：账本订单不在当前 pending 快照中，或账本所有者已不是活跃持仓；
- `evidence_unavailable`：交易所快照读取失败或完整性无法确认。

`stale` 绝不能退回猜测逻辑重新归属。`conflict` 和
`evidence_unavailable` 必须失败关闭。

## 数据流

### 创建保护单

```text
准确的持仓 posId
  → 提交 TPSL
  → 获得响应 ordId
  → 按 ordId 回读当前 pending TPSL
  → 核对品种、方向、保护类型、价格、数量
  → 同一数据库事务写业务状态表和权威账本
```

缺少 `posId`、缺少 `ordId`、回读失败或核对冲突时，不写 `verified` 账本，
也不把持仓标记为已保护。

### 展示和健康审计

```text
全账户持仓 + 全账户 pending TPSL + 全账户权威账本
  → 先按交易所显式 posId 或账本 ordId 关联
  → 分别生成每个 posId 的保护摘要
  → 剩余订单进入全局未归属区
```

某个仓位的订单永远不能作为另一个仓位的 `manual_order_ids`。

### 调整、替换和撤单

```text
目标 posId
  → 查询该 posId 的权威账本行
  → 取得准确 ordId
  → 按 ordId 重新读取交易所
  → 核对交易所显式 posId（若有）
  → 执行准确订单操作
```

缺少账本或发生冲突时，仅冻结目标仓位的保护变更，不影响其他持仓。

## 保护状态语义

`protected` 不再承担“是否有任何止损”和“是否可安全自动管理”两种混合语义。
读取层至少分别提供：

- `has_verified_stop`
- `has_verified_backup_stop`
- `verified_take_profit_count`
- `has_unowned_orders`
- `ownership_conflict`
- `readback_complete`
- `automation_safe`

页面和告警据此区分：

- 已有止损，自动管理安全；
- 已有止损，第二止损缺失；
- 已有止损，但回读证据暂不可用；
- 交易所存在未归属 TPSL；
- 确认无止损；
- 归属冲突，自动管理冻结。

## 历史回填

回填器读取业务表中的现有准确记录，但只生成账本动作，不调用交易所写接口。
一条记录必须同时满足：

- `ordId` 和 `posId` 非空；
- 当前 pending 快照仍包含该 `ordId`；
- 交易所显式 `posId`（若存在）与本地一致；
- 同一 `ordId` 没有其他 `posId`；
- 关联执行腿已经验证；
- 品种和方向一致。

回填先生成完整 dry-run、拒绝列表和指纹。应用时必须重新读取快照并要求指纹
完全一致。当前生产基线的预期结果是 25 笔 pending TPSL 全部进入权威账本，
未归属和冲突均为零。

人工审核工具仍可展示价格、数量、方向和时间候选，但只能接收操作员明确提供
的 `ordId + posId + evidence_hash`，不能自动选择候选。

## 猜测代码清理范围

以下运行时行为必须删除或改为仅供人工审核：

- 按品种、方向和时间窗口分配 TPSL；
- 按仓位数量或分批止盈数量和选择 TPSL；
- 按“同品种同方向唯一订单”选择调整目标；
- 把 `sz=0` 订单视为可能属于所有同方向持仓；
- 无 `ordId` 时按时间或数量回退匹配；
- 账本所有者已经关闭后把旧订单重新归给新持仓；
- 管理 planner/executor 未传入全账户账本时继续生成交易动作。

保留价格、数量、方向和时间核对，但它们只能验证一个已经由 `ordId` 和
`posId` 建立的关系，不能创建关系。

## 分阶段切换

### 阶段 0：安全基线

保持交易冻结，保存持仓、pending TPSL、业务表、账本、服务版本和交易所写入
计数的只读快照。

### 阶段 1：统一读取组件

实现全账户账本索引、冲突检测和纯函数测试，不改变生产行为。

### 阶段 2：账本回填

实现带指纹的 dry-run 和数据库-only 应用，将现有准确业务记录迁入账本。

### 阶段 3：统一写入

使所有新的主止损、第二止损、止盈、替换和恢复路径在成功回读后原子写入
账本。

### 阶段 4：影子比对

旧逻辑和新账本逻辑同时计算，只记录差异，不改变展示或交易行为。

### 阶段 5：切换展示和审计

Web、健康审计、告警和运维快照只消费权威账本。

### 阶段 6：切换交易入口

管理计划、调整、替换和撤单只接受权威账本授权。

### 阶段 7：删除猜测逻辑

删除运行时启发式匹配及其成功测试，保留显式人工审核工具。

### 阶段 8：生产验证

通过 GitHub 拉取部署，保持交易冻结，运行服务器只读核对和测试。确认没有
交易所写调用后，再由操作员单独决定是否解除冻结。

## 测试策略

必须覆盖：

- 多个同品种、同方向拆分持仓；
- 每个持仓都有自己的 `sz=0` TPSL；
- 分批止盈和多个 TP `ordId`；
- 同一 `ordId` 的账本冲突；
- 交易所显式 `posId` 与账本冲突；
- 账本所有者已经平仓；
- 新的手动 TPSL 没有账本；
- pending 快照读取失败或不完整；
- 无账本时调整、替换和撤单被拒绝；
- 业务表写入成功但账本事务失败时整体回滚；
- Web、审计、告警和交易 planner 对同一快照得出一致归属。

## 部署和回滚

每个阶段独立提交、测试和部署。读路径切换前保留旧计算作为影子对照；写路径
切换通过独立开关完成。若新旧结果不一致、账本覆盖率下降或出现冲突，保持
交易冻结并回退到上一阶段代码，不修改真实订单。

生产验收至少包括：

- `telegram-kol.service` active；
- 服务器提交与推送提交一致；
- 当前持仓数与交易所一致；
- 当前 pending TPSL 全部由权威账本唯一归属；
- 未归属和冲突符合人工预期；
- 页面、保护审计和运维快照一致；
- 验证期间交易所写入计数为零；
- 未自动解除交易冻结。
