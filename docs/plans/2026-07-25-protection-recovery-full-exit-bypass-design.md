# 保护恢复异常下的精确全平旁路设计

## 背景

2026-07-24，大镖客 BTC 空单（策略 `deepcoin:-1003048800035:4091:BTC:short`，
`posId=1001124332208757`）在消息 4092 被识别为保本管理、在消息 4095 被识别为
“撞保”全平。两条管理批次均因 `protection_recovery_required` 被标记为 `blocked`。
识别、策略归属和目标生命周期均正确，但执行器没有提交保本更新或全平订单。

保护状态未知时冻结保护更新是正确的；但把已经精确绑定的全平也冻结，会让风险
退出失效。全平是降低敞口的操作，应该有比保护更新更窄、更严格的受控路径。

## 决策

只对明确的全平管理批次开放保护恢复旁路。保本、止损/止盈修改、部分平仓和任何
归属不确定的管理指令保持原有的 fail-closed 行为。

允许旁路必须同时满足：

- 批次的有效动作是 `full_exit` 或 `full_close`；
- 批次已解析出唯一目标 lifecycle、execution binding 和精确 `posId`；
- 该 `posId` 在当前 Deepcoin 快照中仍存在，且合约、方向、仓位模式及归属验证均与
  binding 一致；
- 快照中的数量为正，并可由现有的精确仓位经济性校验接受；
- 不存在同一 `posId` 的已提交或未决平仓保留记录。

满足条件时，执行器只提交带 `closePosId` 的市价平仓单，绝不按 symbol/side 扫描或
关闭其他仓位。

## 数据流

1. 管理规划器遇到 `protection_recovery_required`：
   - 非全平动作：创建/保留 `blocked` 批次，原因不变。
   - 精确全平：生成可执行的受控旁路批次，并在目标快照中记录旁路原因和验证证据。
2. 管理执行器重新读取实时持仓并执行全部精确归属校验。
3. 通过后，使用现有的按 `posId` 市价平仓及持久保留机制提交订单。
4. 记录旁路原因、前后快照、订单 ID 与事件；“已提交”不等于“已退出”。
5. 对账器确认交易所快照不再存在该 `posId` 后，才将策略/批次归档为已退出或已解决。

## 可观测性和失败处理

- 为旁路全平提供明确的原因码，例如
  `protection_recovery_bypassed_for_full_exit`，并在管理批次 UI/API 中展示。
- 提交、待交易所确认、确认成功、确认失败和前置校验失败都保留可检索事件。
- 旁路提交或最终对账结果发送一次高优先级通知，包含 KOL、消息号、策略、`posId`、
  原因码和订单 ID。
- 任意校验失败、交易所拒单或不确定响应都不自动扩大平仓范围或重复下单；保留冻结
  状态并发送明确告警。
- 使用唯一批次指纹、每个 `posId` 的 close reservation 和已有订单 ID 维持重启/重试
  幂等性。

## 验收标准

- 保护恢复异常时，保本/改止损/部分平仓仍不得提交交易所订单。
- 同样异常下，唯一且已验证的 `full_exit` 能只对目标 `posId` 发出一次市价平仓。
- 缺失、漂移或多重归属的持仓不能旁路。
- 交易所拒单、不确定响应和服务重启不会产生重复平仓单。
- 交易所确认仓位消失前，生命周期不能被标记为已退出。
- 批次详情、执行事件和告警足以审计这一路径。

## 发布与验证

先以单元和集成测试验证规划、执行、幂等性及对账。经审查后推送到
`codex/deepcoin-auto-trading-v1`，再使用既有服务器更新流程部署。生产验证只能使用
服务器凭据进行只读快照、数据库/事件检查和受控 dry-run；不得为验证而新开真实仓位。
