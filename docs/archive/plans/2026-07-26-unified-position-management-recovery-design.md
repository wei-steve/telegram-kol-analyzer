# 统一仓位管理与实盘恢复设计

## 目标

建立一条确定、可恢复、可审计的仓位管理链路，使 Telegram 中明确的
减风险指令能够在多策略、多分仓和 Deepcoin TPSL 证据不完整的情况下安全执行，
同时修复当前真实仓位中已经确认的漏撤单、漏减仓、漏平仓和保护不完整问题。

未来消息在安全边界内自动执行。当前存量仓位和历史订单只生成带指纹的只读修复
方案，由操作员逐项确认后执行。

## 已确认的生产问题

2026-07-26 只读核查确认当前有 12 笔 BTC 多仓，全部能通过 verified entry leg
唯一归属到群组和策略，但存在以下执行故障：

- 大漂亮 `#1465` 已取消策略，管理项因
  `authoritative_management_candidate_not_found` 失败，后续仍成交形成仓位。
- 舒琴 `#3381` 已宣布止盈，管理项因
  `target_strategy_binding_not_found` 失败，仓位仍存在。
- 三姐 `#1137` 要求减仓 50% 并移动止损到开仓价，管理批次因
  `protection_recovery_required` 被阻断。
- 陈哥 `#9719` 要求移动止损到成本保护，因同群存在多笔 BTC 多仓而未能唯一
  归属，系统跳过执行。
- 大镖客 `#4102` 给出“只留尾仓”或“求稳出局”两个减风险选项，系统将其当作
  行情分析；当前尾仓之外仍有未成交补仓腿。
- 多笔仓位缺少可由精确 `ordId ↔ posId ↔ entry leg` 证明的完整主止损、第二
  止损或分段止盈。
- 账户存在大量历史或人工 TPSL，无法唯一归属的订单会冻结自动管理。

## 设计原则

- `ExecutionOrderLeg.pos_id` 和 verified attribution 是真实仓位归属权威。
- 不从同合约、同方向、价格、数量或时间单独猜测仓位归属。
- 明确减风险指令可以在严格作用域内自动扇出；加风险指令不得扇出。
- 所有交易所写入都在不可变目标快照和提交前最新快照同时成立时才允许。
- 每个 `posId` 独立执行、独立回读和独立失败。
- 网络或交易所结果未知时只回读，不盲目重试。
- 当前存量修复逐项确认；未来符合规则的消息自动执行。
- 无法证明失效的历史订单不得仅因无法归属而自动撤销。

## 总体架构

统一管理编排器按固定顺序处理消息：

```text
Telegram message
  → authoritative recognition
  → management scope resolution
  → immutable target snapshot
  → cancel deferred entry legs
  → reduce / close / tighten protection
  → exchange readback
  → protection convergence
  → completed or recovery queue
```

复用现有 `StrategyLifecycle`、`ExecutionBinding`、verified
`ExecutionOrderLeg`、`StrategyManagementBatch`、保护账本和 Deepcoin 客户端。
不引入第二套仓位归属模型。

## 管理作用域

作用域按以下优先级确定：

1. 消息回复具体策略消息时，只管理该策略。
2. 权威识别结果携带唯一 lifecycle 或 strategy identity 时，只管理该策略。
3. 未回复具体策略，但消息明确描述当前群组的某标的和方向，并且动作是减风险时，
   自动扇出到同 `chat_id + symbol + side` 的所有 verified live entry legs。
4. 存在归属冲突、交易所快照不完整或目标不是 verified live position 时不执行。

允许扇出的动作：

- 取消未成交入场或补仓腿；
- 部分止盈或减仓；
- 全部平仓；
- 移动止损到成本或更紧的保护价；
- 收紧现有止损。

禁止扇出的动作：

- 新开仓；
- 加仓；
- 放宽止损；
- 取消有效止损；
- 反向开仓。

## 语言规则

- “减半”“止盈 50%”严格按 50%。
- “止盈一部分”“先出一部分”默认减仓 50%。
- “只留一点尾仓”默认减仓 80%，保留 20%。
- 每个分仓分别按合约数量步长向下取整，并在计划中展示总舍入差异。
- 同一消息给出多个减风险选项时，执行共同风险方向中的最小动作。
- “只留尾仓，求稳也可以出局”执行减仓到 20%，不自动选择全平。
- 选择减仓、尾仓或平仓后，先撤销目标策略所有未成交入场和补仓腿。
- 一般行情观点，例如“激进可以做空”“个人可以考虑”，不触发交易。

## 不可变目标快照

每个管理批次必须持久化：

- 原始消息 ID、权威识别 decision 和 recognition generation；
- 作用域类型、作用域证据和目标策略集合；
- lifecycle、binding、verified entry leg 和 exact `posId`；
- 当前仓位数量、均价、合约规格和数量步长；
- 未成交入场腿及其 exchange/client order ID；
- 当前主止损、第二止损、止盈和精确账本证据；
- 预期撤单、减仓、平仓和保护重建动作；
- 目标指纹和快照采集时间。

真正写入前重新读取 Deepcoin。仓位身份、数量、未成交腿或保护订单与目标快照不一致
时，本批次失效并重新规划，不继续使用旧计划。

## 执行顺序

每个目标策略按以下顺序执行：

1. 验证 binding、verified entry legs 和实时 `posId`。
2. 读取一次完整 Deepcoin position、pending regular order 和 pending TPSL 快照。
3. 精确匹配并撤销快照中的未成交入场腿。
4. 回读确认撤单完成；并发成交的腿转换为新的 live `posId` 目标。
5. 提交部分减仓或全平请求。
6. 按 exchange order ID 和 client order ID 回读成交结果。
7. 按真实剩余数量取消或替换旧保护。
8. 收敛主止损、第二止损和全部计划止盈。
9. 回读每条保护订单并写入精确 `ordId ↔ posId ↔ entry leg` 账本。
10. 所有目标完成后把批次标记为 `completed`。

一个 `posId` 失败不阻止同批其他 `posId`，但每个失败目标必须持久化原因和恢复状态。

## 状态机与失败恢复

正常状态：

```text
planned
  → preflight_verified
  → executing
  → reconciling
  → completed
```

异常状态：

- `blocked`：执行前证据不足，没有发送交易所写请求。快照恢复后可自动重新规划。
- `recovery_required`：请求可能已经发送但结果未知。禁止重复提交，只做交易所回读。
- `failed_terminal`：交易所明确拒绝、身份已经失效或动作无法安全恢复，需要新方案。

本次故障的修复语义：

- 不再为管理消息二次寻找一个可能不存在的 candidate；直接使用权威识别结果和作用域
  解析结果。
- 管理消息可以锁定仍处于 pending entry 的策略。取消或全平必须先处理其未成交腿；
  如果并发成交，则沿用相同 strategy identity 管理新形成的仓位。
- 保护恢复不再作为整个策略管理的永久锁。执行器按 `posId` 快照旧保护，减仓成交后
  按真实剩余量重建保护。
- 多仓不唯一时，明确减风险消息使用已批准的群组扇出规则，而不是直接跳过。

## 幂等性

- 幂等身份由 `raw_message_id + normalized_action + strategy_id + pos_id` 构成。
- 同一消息重新同步、服务重启和 worker 重试只能采用或回读既有动作。
- 每个交易所写请求前先持久化 submitting 状态和 client order ID。
- 超时、响应缺 ID 或读取不完整时进入 `recovery_required`。
- 只有读取到唯一终态或明确不存在且有安全证明后，才能决定重试或失败。
- 自动恢复有有界次数和退避时间；超过限制冻结单个目标并发送高优先级告警。

## 当前真实仓位修复

方案立即过期。

- 舒琴 `#3374`：对已宣布止盈但仍存在的 10 张生成全平方案。
- 三姐 `#1136`：20 张减仓 50%，剩余仓位止损移动到实际开仓均价，随后按剩余
  数量重建保护。
- 陈哥 `#9701`：移动止损到该仓实际成本价，并重建对应止盈。
- 大镖客 `#4101`：当前 5 张视为尾仓，不再减仓；撤销仍挂着的 25 张补仓腿，
  重新验证主止损、第二止损和三档止盈。

每项方案必须展示：

- 原始消息和最新管理消息；
- 目标 `posId`、当前数量和均价；
- 将撤销、提交或替换的订单；
- 修复前后仓位、止损和止盈；
- 原因码、方案指纹和过期条件。

操作员逐项确认后执行，不提供“确认全部”作为默认路径。

## 历史订单清理

- 能通过精确订单 ID 和权威 entry leg 证明归属的订单，修复本地账本并保留。
- 能证明仓位已不存在、策略已退出或订单已被新保护替代的，生成建议撤销项。
- 仅无法归属、但不能证明失效的订单保持不动。
- 所有存量撤销动作都进入逐项确认的修复方案。
- 未来系统创建的订单必须在响应返回 ID 后立即建立精确账本，避免产生新的未归属
  系统订单。

## 测试设计

本地测试至少覆盖：

- reply-to 精确作用域；
- 同群同标的同方向减风险扇出；
- 跨群、跨方向和跨标的隔离；
- 加仓、放宽止损和反向开仓禁止扇出；
- 50% 部分止盈、80% 尾仓及数量步长取整；
- 多选消息采用最小风险降低动作；
- 减仓和平仓前撤销未成交 entry legs；
- 撤单期间并发成交；
- 仓位数量、身份或保护快照变化时 fail closed；
- 分 `posId` 隔离失败；
- 网络超时后的回读和禁止重复提交；
- 重启和重复消息零重复交易；
- 历史订单只按精确证据保留或建议撤销；
- 存量修复方案指纹和过期检查。

## 发布设计

1. 部署前保存数据库、Deepcoin 只读基线、服务 SHA 和 12 笔仓位指纹。
2. 第一阶段启用影子模式：新编排器生成计划但不发送交易请求。
3. 回放近期历史消息，确认 `#1465`、`#3381`、`#1137`、`#9719` 和 `#4102`
   生成已批准的目标动作。
4. 影子结果通过后启用未来减风险指令自动执行；开仓逻辑保持现状。
5. 生成当前存量修复方案，由操作员逐项确认。
6. 每执行一项立即回读 Deepcoin，核对仓位、挂单和完整保护。
7. 重启 `telegram-kol.service`，重新 reconciliation，确认零重复写入。
8. 连续观察至少一个完整消息周期。出现未知交易结果、重复动作或归属冲突时，自动
   关闭新的管理写入，保留消息采集和只读监控。

## 验收标准

- 当前 12 笔仓位全部达到逐项确认的目标状态。
- 每个自动仓位都有 verified `posId`、主止损、第二止损和完整分段止盈。
- 已取消策略不存在残留未成交入场腿。
- 明确减风险消息不再因同群多仓而跳过。
- 重复消息、重启和重新同步产生零重复交易。
- 每项执行都能从原始消息追溯到具体策略、`posId` 和交易所订单。
- 无法证明归属或失效的历史订单没有被误撤销。
