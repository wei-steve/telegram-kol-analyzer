# 无干扰焦点恢复刷新设计

## 背景

交易持仓页面当前监听浏览器 `focus` 和 `visibilitychange`。标签页重新可见时，
恢复逻辑会强制重新加载当前持仓面板，并在面板容器上设置
`aria-busy="true"`。这会替换用户正在阅读的 DOM，同时触发全区域透明度变化和
旋转进度鼠标，造成明显的浏览中断。

页面已经有 SSE 实时事件连接、每 5 秒一次的轻量 freshness 检查，以及持仓面板
的手动加载入口。因此，焦点恢复不需要立即替换用户正在查看的持仓内容。

## 目标

- 标签页重新获得焦点时继续检查服务状态、数据库变化和最新交易所持仓数据。
- 后台检查不得设置持仓区域的忙碌状态、改变鼠标形状或替换当前 DOM。
- 只有检测到持仓面板内容变化时才提示用户。
- 用户点击提示后，用已经取得的最新快照更新面板，避免再次等待网络请求。
- 保留所选持仓分页和“真实列表/按群组”视图。
- 后台检查失败时保留最后一次成功内容，不弹出遮挡式错误。

## 方案比较

### 方案 A：取消焦点恢复时的持仓请求

实现最小，但用户回到页面后无法得知交易所仓位已经变化，只能手动刷新。

### 方案 B：后台取得最新快照，变化时提示用户应用（采用）

兼顾及时性和浏览稳定性。请求仍会发生，但不会切换加载状态或修改当前内容。
只有用户点击“有新持仓数据，点击更新”后才替换面板。

### 方案 C：后台直接替换 DOM，并恢复滚动、焦点和所有展开状态

看似自动，但需要追踪每个仓位卡片、详情折叠、焦点元素和滚动锚点。数据增删时
仍可能发生布局跳动，复杂度和回归风险明显高于方案 B。

## 设计

焦点恢复协调器继续调用监控状态和数据库 freshness 检查。当前视图为持仓时，
它额外请求 `/positions-panel`，在离屏 DOM 中解析新面板，并与当前持仓面板
比较：

- 内容相同：不做任何可见操作，并清除已过期的待更新提示。
- 内容不同：将新面板保存在内存中，在持仓容器顶部显示一个轻量提示。
- 请求失败：保留当前页面，不改变忙碌状态；下一次轮询或焦点恢复仍可重试。

用户点击提示后，前端使用内存中的新面板替换旧面板，重新绑定分页、视图、
平仓、同步和归属操作。现有 localStorage 恢复逻辑继续恢复所选分页和视图。

焦点恢复的后台检查不经过 `ensureWorkbenchViewLoaded(..., { force: true })`，
因此不会设置 `aria-busy="true"`，也不会触发旋转进度鼠标和整体变淡。

## 并发与一致性

现有 `recoveryRefreshPromise` 合并同一时刻由 `focus` 和 `visibilitychange`
产生的重复恢复事件。待应用的持仓快照始终以最近一次成功检查为准。普通首次
加载和显式导航仍沿用原有加载状态；只有焦点恢复检查采用静默路径。

## 测试

- 静态资产测试确认焦点恢复不再强制重新加载持仓工作区。
- 测试确认焦点恢复仍执行监控、freshness 和持仓变化检查。
- 测试确认后台检查只保存候选片段并显示提示，不直接替换当前面板。
- 测试确认用户应用候选片段后重新绑定持仓交互。
- 运行完整 Web 静态资产测试和相关页面渲染测试。
- 部署后验证切换标签页不会出现旋转鼠标或页面变淡，并确认数据变化提示可以
  更新持仓面板。
