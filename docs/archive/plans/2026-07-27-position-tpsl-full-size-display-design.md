# Web 持仓止盈止损数量语义展示设计

日期：2026-07-27

## 背景

Deepcoin 的持仓止盈止损接口把 `sz` 用作“部分止盈止损数量”。当创建的是
全仓止盈止损时，请求可以不传 `sz`，待触发订单快照通常返回 `sz=0`。这里的
零不是“平仓数量为零”，而是“触发时覆盖该仓位的全部剩余数量”。

当前 Web 展示层直接把待触发订单的原始 `sz` 渲染成
`数量 0 contracts`。因此部分止盈的正数数量可以正确显示，全仓止盈和止损却
被错误显示为零。该问题只影响展示，不代表 Deepcoin 实际订单数量为零。

## 目标

- 正确表达 `sz=0` 的全仓语义。
- 对已经精确归属当前仓位的全仓保护单，附带该仓位最新快照数量。
- 在已有可信合约规格时，同时显示 contracts 和基础币数量。
- 对无法归属的保护单保持保守，不借助币种、方向、价格或数量猜测仓位。
- 不改变交易、订单归属、保护单写入、撤单或策略执行逻辑。

## 方案选择

采用“结构化数量语义 + 当前快照数量”的方案。展示数据在进入 Jinja 模板前
完成 Deepcoin 字段解释，模板只渲染已经生成的展示字段。

不采用以下方案：

- 不在模板中判断 `size_text == "0"`，避免让模板承担交易所协议语义。
- 不把 `0` 静默替换成固定数值，因为全仓保护覆盖的是触发时的全部剩余仓位，
  数量会在部分止盈后变化。
- 不硬编码 BTC 或 ETH 的合约面值；换算只能使用已加载的可信合约规格。

## 数据模型

扩展 `PositionTpslDisplayRow`，为每条展示腿提供：

- `size_mode`：`partial` 或 `full_position`；
- `raw_size_text`：交易所原始数量，便于诊断；
- `size_display_text`：模板直接显示的完整数量文案；
- 现有订单类型、触发价、订单 ID、归属状态、币种和方向字段保持不变。

旧的 `size_text` 不再作为模板拼接单位的依据。若为了减少调用方迁移成本暂时
保留，它只能作为原始数量兼容字段，不能继续产生 `0 contracts` 文案。

## 数据流

1. `_load_deepcoin_live_position_rows()` 继续一次读取当前活跃仓位和待触发 TPSL。
2. `_split_exchange_protection_display_rows()` 把现有
   `DeepcoinContractSpecProvider` 传给 `build_position_tpsl_display()`。
3. `build_position_tpsl_display()` 先按交易所 `PositionID` 或已验证的本地
   `ordId -> posId` 证据完成精确关联。
4. 对 `sz>0`：
   - `size_mode=partial`；
   - 显示原始 contracts；
   - 若存在可信合约面值，再显示换算后的基础币数量，例如
     `2 contracts / 0.002 BTC`。
5. 对 `sz=0`、空值或数值等价的零：
   - `size_mode=full_position`；
   - 若已精确归属当前仓位，读取该仓位当前 `pos`，显示
     `全部剩余仓位（当前 10 contracts / 0.01 BTC）`；
   - 有仓位快照但无可信合约规格时，显示
     `全部剩余仓位（当前 10 contracts）`；
   - 当前仓位数量缺失或无效时，只显示 `全部剩余仓位`；
   - 无法归属时显示 `全部仓位（具体仓位未归属）`，不得引用任何当前仓位数量。
6. 每次刷新页面都重新读取当前仓位，因此部分止盈后的全仓保护数量随最新剩余
   仓位更新，不被固化为创建时数量。

## 数量格式

数量计算使用十进制定点语义，避免浮点换算产生
`0.010000000000000002` 一类展示。基础币符号从可信合约规格对应的
instrument ID 中取得，例如：

- `BTC-USDT-SWAP`：`10 contracts`、合约面值 `0.001`，显示 `0.01 BTC`；
- `ETH-USDT-SWAP`：仅在配置中存在有效面值时换算。

无规格、规格读取异常或数量无法解析时，降级为 contracts 文案。展示降级不能
让 `/positions-panel` 整体失败。

## 模板

持仓卡和“未归属交易所保护单”区域统一输出 `size_display_text`，不再自行追加
`contracts`。页面中精确归属的全仓保护单不应再出现 `数量 0 contracts`。

## 安全边界

- 数量和价格仍然只是展示字段，不参与订单归属。
- `sz=0` 不能成为从保护单反推仓位的证据。
- 当前仓位数量只在已经通过直接 `PositionID` 或强账本证据归属后使用。
- 合约规格缺失时只降级展示，不访问网络获取规格，也不影响持仓页面其他内容。
- 本变更不提交、修改或撤销任何 Deepcoin 订单。

## 测试

### 纯展示模型

- 精确归属、`pos=10`、`sz=0` 生成全仓语义和当前 contracts 快照。
- 注入 BTC 合约规格后生成 `0.01 BTC`。
- `sz=2` 保持部分数量语义，并在有规格时生成 `0.002 BTC`。
- 无规格时只显示 contracts。
- 无法归属的 `sz=0` 不读取任何仓位数量。
- 空 `sz` 和数值等价的零按照全仓处理。
- 非法数量安全降级，不使快照构建失败。

### 页面渲染

- 持仓卡显示 `全部剩余仓位（当前 …）`。
- 部分止盈仍显示正数 contracts 和可用的基础币换算。
- 未归属全仓保护显示 `全部仓位（具体仓位未归属）`。
- 响应中不再包含 `数量 0 contracts`。
- 原有 TPSL 精确归属、未归属隔离、排序和数量统计保持不变。

## 生产验证

实现通过本地测试、代码审查、提交和推送后，按项目标准流程更新服务器。生产
验证只执行只读检查：

1. 确认服务器部署 SHA 和 `telegram-kol.service` 状态；
2. 读取 `/positions-panel`，确认 HTTP 200；
3. 使用已知 `sz=0` 的当前保护单核对全仓文案及当前仓位数量；
4. 使用 `sz>0` 的分段止盈核对部分数量；
5. 确认未归属保护单没有获得猜测的当前仓位数量；
6. 不创建测试仓位，不修改或撤销真实保护单。
