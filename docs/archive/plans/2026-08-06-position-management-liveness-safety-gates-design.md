# 精确仓位管理存活性与安全门设计

## 背景

舒琴 ETH 空单使用两条同方向、同数量、同止损的触发入场腿。两条腿的真实 `posId`
已经分别由 `execution_order_legs` 唯一验证，持仓归属本身没有歧义。问题发生在
Deepcoin 原生 TPSL 回读：两张止损都缺少 `posId` / `closePosId`，且币种、方向、
数量和止损价完全相同。

第二腿成交后，当前逐意图匹配器先遇到第一腿的旧止损，因其创建时间早于第二腿
成交时间，立即返回 `trigger_protection_candidate_predates_fill`，没有继续考察与第二腿
同时创建的新止损。五次重试后意图进入 `failed`。主止损没有进入
`position_protection_ledger`，备份止损因 `primary_stop_not_verified` 被阻断，三档止盈收敛任务
继而永久停在 `waiting_backup_stop`。

这个故障暴露了两个设计问题：

1. 匹配是局部、顺序敏感的，而保护订单所有权必须是账户全局一对一的。
2. 保护订单归属不完整被扩大成了对精确 `posId` 所有风险降低操作的总阻断。

## 目标

- 在不放宽持仓归属和保护订单取消边界的前提下，精确解决同规格拆分腿的原生止损归属。
- 旧保护单暂时无法归属时，只禁止取消或替换不明订单，不阻碍针对精确 `posId` 的安全新增、
  减仓或全平。
- 任何管理组件在有界时间内进入已完成、等待新证据、需要恢复或已升级人工状态，不得静默永久失败。
- 异常只限制精确仓位和依赖它的组件，不阻塞其他腿、其他策略或无依赖的风险降低动作。

## 非目标

- 不使用 `ordId = posId - 1` 等未经 Deepcoin 文档承诺的规律。
- 不允许按币种、方向或价格相似度单独推测持仓或保护订单所有权。
- 不取消、修改或替换不能精确证明归属的交易所订单。
- 不更改现有消息识别、策略目标解析或 `execution_order_legs` 持仓归属权威链。

## 方案选择

### 方案一：跳过早于成交的候选

这可以消除当前的提前返回，但同规格的已成交兄弟腿仍会触发 `candidate_not_unique`。
匹配仍依赖 API 返回顺序，不能作为完整修复。

### 方案二：直接使用时间或订单 ID 规律

当前实例可以匹配，但证据不具有交易所合约级稳定性，可能把其他策略的止损写入错误账本。
拒绝采用。

### 方案三：账户全局一对一归属与按能力授权

采用此方案。保护归属改为全局、排他、无顺序依赖的一对一解析；交易所写入根据具体动作
需要的证据授权，不再由一个“保护完整”布尔值决定所有仓位管理。

## 架构

### 1. 账户全局保护分配器

新增一个交易所无关的纯函数分配器。输入为：

- 所有已验证且真实存在的入场腿；
- 所有当前和有界历史 TPSL 订单；
- 保护账本中已有的不可变 `ordId -> posId` 所有权；
- 触发保护意图、父订单、基线和已知交易所响应；
- 完整性标记及观察时间。

匹配证据分层：

1. 订单回读显式 `posId` / `closePosId`；
2. 本系统精确请求持久化的响应 `ordId`；
3. 交易所父触发或成交子订单关系；
4. 现有保护账本的排他所有权；
5. 从剩余未归属集合中，根据币种、方向、数量、保护价、成交时间和订单创建时间建立
   候选边。

第五层只在位置和订单两端都只有一条候选边时接受。任何一对多、多对一、时间缺失、快照不完整或
已有所有权冲突都不得新建所有权。早于目标成交的订单是被排除的候选，不是整个位置的终止错误。

分配结果必须包含稳定证据类型、参与候选 ID、排除原因和全局指纹。只有当当前快照指纹与计划指纹
相同时，才可以调用现有不可变账本写入器。

### 2. 按操作能力授权

安全门输出不再是单一 `blocked/allowed`，而是一组能力：

- `may_cancel_owned_protection`：仅当目标 `ordId` 在保护账本中唯一验证。
- `may_replace_owned_protection`：要求旧订单所有权、精确持仓和完整快照。
- `may_add_exact_backup_stop`：要求精确持仓、保存的策略止损和新鲜快照，不要求旧止损归属。
- `may_add_exact_take_profit`：要求精确持仓、已验证精确备份止损，并且账户全局证明没有可能作用于
  目标仓位的未归属止盈。
- `may_reduce_exact_position`：要求精确持仓和最新数量；部分减仓还必须证明保留止盈不会超量。
- `may_close_exact_position`：要求精确持仓和最新数量，不以旧保护单所有权为前置条件。

每个写入依然经过 `position_authority_lock`、持久化预留、最终精确仓位门、请求指纹和交易所回读。
“不要求旧保护归属”不等于使用弱持仓归属。

### 3. 主止损与止盈收敛解耦

触发腿成交后的收敛链改为两条相互协作但不相互永久阻断的通道：

```text
通道 A：原生主止损归属
position verified -> global assignment -> adopted | recoverable ambiguity

通道 B：精确风险降低保护
position verified -> exact backup stop -> staged take profits
```

优先完成通道 A。若在有界可见性窗口内仍无法归属原生止损，通道 B 使用入场请求中持久化的止损价，
创建一张直接绑定精确 `posId` 的备份止损。它不取消原生止损，也不将原生止损写入错误账本。

止盈收敛的前置条件从“已验证主止损且已验证备份止损”改为：

```text
精确真实持仓
AND 至少一张本系统精确所有的有效止损
AND 无可能作用于目标仓位的未归属止盈
AND 止盈总数量不超过当前仓位
```

这使已验证备份止损成为原生止损归属暂时不完整时的活性证据，同时保留止盈超量和未知提交结果的
严格阻断。

### 4. 结构化恢复状态

`TriggerProtectionIntent` 增加结构化的最后原因和恢复分类，不再从审计 JSON 的文字中搜索关键词。
状态机为：

```text
waiting_position
waiting_visibility
matching
ambiguous_recoverable
exact_backup_required
ready_for_take_profit
recovery_required
adopted
resolved
```

实现时保留对现有 `pending/retrying/failed` 数据的兼容读取。早于成交的候选被记录为排除证据，不消耗重试次数。
快照不可用时保持等待。真正多解进入 `ambiguous_recoverable`。超过可见性窗口后进入
`exact_backup_required`，而不是终止失败。

提交结果未知仍是 `recovery_required`，必须通过交易所回读或人工证据收敛，不自动盲目重试。

### 5. 组件隔离

一条管理指令按精确仓位和动作拆分为组件。旧保护取消、新备份止损、止盈收敛、部分减仓和全平使用独立
幂等键和状态。一个组件的不充分证据不得扩大为其他组件或其他 `posId` 的总失败。

## 数据流

```text
完整交易所快照
  -> 验证 execution_order_legs 持仓所有权
  -> 加载已有保护账本和未归属 TPSL
  -> 全局一对一分配
     -> 唯一：指纹校验后写入保护账本
     -> 不唯一：保留不明订单，不取消
  -> 计算每个 posId 的操作能力
  -> 需要时提交精确备份止损
  -> 回读并持久化 ordId -> posId
  -> 收敛该 posId 的分段止盈
  -> 后续快照继续收敛原生止损归属
```

## 错误处理

- 快照不完整：零交易所写入，保持可恢复等待。
- 真正多解：不写保护所有权，但允许不依赖该所有权的能力。
- 已有账本冲突：不可恢复冲突，冻结相关订单的取消和替换，立即升级。
- 备份止损请求结果未知：冻结该 `posId` 的后续保护提交，只做回读，不盲目重试。
- 止盈提交结果未知：保留现有收敛任务和幂等键，不重新计算或重复下单。
- 部分减仓后保留止盈可能超量：只阻断部分减仓组件；精确全平仍可使用。

## 观测性

策略记录和生产监控应显示：

- 持仓所有权是否已验证；
- 原生主止损归属是否已验证；
- 当前可用操作能力；
- 备份止损和止盈收敛状态；
- 最后结构化原因、下次尝试时间、升级时间和快照指纹。

监控必须区分“仓位归属不明”、“旧保护归属待恢复”和“风险降低保护缺失”，不得统一显示为
“保护未验证”。

## 测试策略

### 纯分配器

- 两条同方向、同数量、同止损的腿依次成交，两张止损返回顺序任意，结果恒定。
- 已归属第一腿的订单不进入第二腿未归属候选池。
- 早于成交的候选被排除，不会阻止同一快照中的后续唯一候选。
- 两端不互唯一、已有所有权冲突、时间或数量不完整时零新归属。
- 显式 `posId` 与旱证据冲突时，显式证据优先且记录冲突。

### 能力门

- 持仓所有权不明时所有写入均禁止。
- 旧止损归属不明但精确持仓存在时，旧单取消禁止，精确备份止损允许。
- 精确备份止损回读后，没有冲突未知止盈时允许分段止盈。
- 未知止盈可能作用于目标仓位时，仅止盈和可超量的部分减仓受限，精确全平仍允许。

### 集成与恢复

- 复现舒琴两腿数据，证明第二腿不再终止于 `candidate_predates_fill`。
- 原生止损唯一时，两腿均写入正确账本并各自收敛三档止盈。
- 原生止损真正多解时，第二腿通过精确备份止损旁路收敛止盈，不写入错误主止损所有权。
- API 候选顺序反转、服务重启、短暂快照缺失和提交结果未知均不会重复下单。
- 其中一腿冲突不会改变其他腿、其他策略或无依赖组件。

## 上线和回滚

新功能由 `position_management_liveness_v2_mode = disabled | shadow | live` 控制，默认 `disabled`。

1. 本地完成纯函数、集成、恢复、管理和 Web 回归测试。
2. 部署时保持 `disabled`，证明现有生产路径未变。
3. 在无时敏策略操作的窗口切换 `shadow`，仅保存候选分配、能力和本应执行的动作指纹。
4. 使用完整生产快照证明舒琴两腿的新分配结果唯一，且无非目标订单变更。
5. 审核指纹后切换 `live`，先执行单个精确 `posId` 的有界恢复。
6. 再次读取全部持仓、TPSL、保护账本和止盈收敛任务，运行生产安全监控。

回滚只需将模式设为 `disabled` 并恢复审查过的 Git 版本。已经由精确请求建立且回读的保护单和账本记录
必须保留，回滚不得取消、删除或重建已确认的交易所订单。

## 舒琴现有仓位的恢复验收

实盘恢复不在部署或服务重启中自动发生。审核过的恢复计划必须绑定最新快照指纹，并且只包含：

1. 验证 `1001124624877984` 仍是舒琴策略第二腿，方向和数量未漂移。
2. 若全局分配唯一，将 `1001124624877983` 写入第二腿保护账本。
3. 若仍不唯一，保留原生止损不动，为该 `posId` 建立精确备份止损。
4. 在至少一张精确所有止损可见后，收敛 `1890 / 1860 / 1825` 三档止盈。
5. 证明第一腿、其他 ETH 仓位和其他币种的持仓及保护单均未变。
