# 同消息多指令识别与执行设计

## 背景

2026-08-09，大镖客消息 `#4206` 在同一条文本中同时表达了两个独立动作：

1. “撤，不挂了，没挂到”取消 `#4205` 的 BTC 空单挂单；
2. 给出一套完整的 BTC 多单参数。

当前系统只保留了取消动作。上下文解析把消息归类为旧策略管理后，覆盖了原始策略输出，导致新多单没有形成独立候选。随后取消候选又缺少规范化管理动作，执行以 `authoritative_management_candidate_not_found` 失败。交易所旧挂单继续存在。

消息 `#4210` 又暴露了第二个问题：系统正确判断它是旧空单的参数修订，但把上下文目标置信度当成新开仓置信度，最终以 `confidence_below_minimum` 跳过精确挂单替换。

项目已经具备 `SignalCandidate`、`MessageInstructionItem` 及按顺序独立执行多个指令的基础设施。缺口主要位于 AI 输出合同、权威识别归一化、上下文目标解析和执行门槛，而不是执行器数量不足。

## 决策

采用原生多指令合同。一个权威识别结果可以声明有序的 `instructions`，每一项只表达一个动作：

- `entry`：独立新策略；
- `cancel_pending_entry`：取消旧策略未成交入场腿；
- `replace_entry`：替换旧策略未成交入场腿；
- `full_exit` / `partial_exit` / `partial_take_profit`；
- `move_stop_to_protect`、止盈止损修订等已有管理动作；
- `hold_update`：仅信息更新，不产生交易写入。

旧的 `strategy` 和 `lifecycle_event` 字段在兼容期继续接受，但必须先归一化为同一个内部 `instructions` 列表。执行层只消费归一化结果，不再根据消息级“是策略/非策略”二选一。

## 数据流

1. MiMo 对消息进行一次权威识别，输出一个或多个动作及每个动作的独立证据、参数和置信度。
2. 合同校验器拒绝缺字段、动作参数互相污染、重复或不受支持的项。
3. 仅管理类指令进入上下文目标解析。新开仓指令保留原始标的、方向、入场、止损和止盈，不允许上下文决策清空或改写。
4. 每个管理指令单独解析精确目标线程。目标不唯一时只阻止该管理项。
5. 每个归一化指令投射为独立 `SignalCandidate`，再投射为独立 `MessageInstructionItem`。
6. 同消息内按“风险降低/旧策略管理优先，新开仓随后”的顺序执行。每项独立持久化结果和幂等键。
7. 消息级结果汇总必须列出所有指令，禁止因其中一项成功、失败或未知而隐藏其他项。

## 指令独立性与安全边界

- 取消、平仓和修订只使用精确 lifecycle、binding、entry-leg、`ordId`、`clOrdId` 或 `posId` 所有权证据；禁止按币种、方向、价格或时间猜测。
- 管理项失败或结果未知时，后续新策略不会被静默丢弃。新策略仍单独经过允许币种、AI 置信度、风险预算、并发持仓、未保护仓位和合约规格门槛。
- 如果后续新策略被门槛阻止，必须持久化明确原因并通知，而不是把整条消息标为“已完成”。
- 未知交易所写入绝不自动重试。其他独立指令可以继续评估，但必须产生严重异常记录。
- 同一消息里的新策略拥有新的策略实例 ID；旧策略管理继续引用旧实例 ID。
- `replace_entry` 使用“目标解析可信度 + 完整替换参数 + 精确旧策略所有权”专用门槛，不套用新开仓的消息置信度门槛。

## 取消确认

本次人工补救中，两笔撤单写入成功，但同步流程先报 `pending_entry_cancel_not_terminally_confirmed`，随后后台回读才收敛成功。修复应保留严格终态证明，同时兼容 Deepcoin 历史响应可能不返回显式 `state` 的形状：

1. 记录每个精确撤单响应；
2. 重新读取待触发订单，确认精确订单已不存在；
3. 读取触发单历史，按精确订单 ID 匹配；
4. 历史行缺少状态时，只有在已有成功撤单响应、订单不再 pending、无成交/持仓证据且经济字段匹配时，才确认取消；
5. 任一证据冲突、缺失或出现成交迹象，进入恢复状态，不重试写入。

## 兼容策略

### 新合同

权威模型优先返回：

```json
{
  "instructions": [
    {
      "kind": "cancel_pending_entry",
      "target": {"relationship": "previous_pending_strategy"},
      "confidence": 0.95,
      "reason": "明确说撤、不挂了、没挂到"
    },
    {
      "kind": "entry",
      "strategy": {
        "symbol": "BTC",
        "side": "long",
        "entry": "64700-63800",
        "stop_loss": "63400",
        "take_profit": "65400-66100-66800"
      },
      "confidence": 0.95
    }
  ]
}
```

### 旧合同适配

兼容层把完整 `strategy` 转为 `entry` 项，把可执行 `lifecycle_event` 转为管理项。两者同时存在时必须同时保留。兼容层只用于迁移和异常回退，不用规则从任意聊天文本拼造新交易参数。

## 观测与告警

- 每个消息记录声明指令数、投射候选数、指令项数及各终态。
- 声明与投射数量不一致时，消息操作合同立即违规。
- “管理成功但开仓缺失”“管理失败且开仓未评估”“消息存在完整策略但没有 entry 项”均为严重异常。
- Telegram 汇总按顺序展示每项动作和结果，敏感响应保持脱敏。

## 测试

至少覆盖：

- `#4206`：取消旧空单和新建多单同时投射，管理在前、开仓在后；
- `#4210`：同向完整参数被解析为精确 `replace_entry`，不被新开仓置信度门槛误杀；
- `#4212`：条件性“走/反手”在条件未满足且参数不完整时不立即交易；
- 同消息“部分止盈 + 新策略”；
- 管理目标不唯一，但 entry 项仍有独立结果；
- 管理写入未知，不重试，entry 项仍被独立评估并产生严重告警；
- 多指令重复处理不产生重复订单；
- Deepcoin 撤单历史缺少 `state` 时的严格成功与拒绝案例。

## 发布

1. 本地测试通过并完成独立代码审查。
2. 推送 `codex/deepcoin-auto-trading-v1`。
3. 服务器先以 shadow 模式只投射未来消息，禁止历史回放和交易写入。
4. 核对候选数、指令项数、执行顺序、服务健康和交易所只读快照。
5. 在无活跃时效策略操作的安全窗口启用实盘多指令执行。
6. 回滚开关关闭新合同投射和执行，保留旧单动作路径及全部审计记录。

## 非目标

- 不用文本拆句规则替代权威识别。
- 不自动执行参数不完整的“反手”“等一下”“不破就走”等条件意图。
- 不回放历史消息下真实订单。
- 不通过修改生产历史行伪造正确结果。
