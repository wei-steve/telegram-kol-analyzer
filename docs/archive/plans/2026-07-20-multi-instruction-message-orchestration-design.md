# 同消息多指令编排设计

## 目标

允许一个群组的同一条 Telegram 消息同时包含：

- 针对已存在策略的仓位管理指令；
- 一个或多个新的开仓策略。

系统必须先提交旧策略管理，再立即尝试新策略开仓；两项具有独立的身份、幂等性、执行结果与告警。前项失败不得取消、跳过或阻止后项。

## 方案

引入持久化的“消息指令项”作为识别结果与交易执行之间的编排层。一条原始消息可拥有多个指令项，每项分别保存：序号、类别（`management` 或 `entry`）、关联的候选信号、目标旧策略或新策略参数、状态、幂等键、错误与执行摘要。

识别器不能再通过同一 `raw_message_id` 上的单行候选记录相互覆盖。它应分别保留管理候选和开仓候选，并由指令项投影为可执行工作单元。

## 编排规则

1. 同一消息的管理指令项排序在开仓指令项之前。
2. 管理项只引用其明确解析出的目标生命周期/策略实例；开仓项只使用其自身的策略参数与新策略实例 ID。
3. 编排器以顺序方式开始每个动作：管理提交完成或进入终态/恢复态后，立即尝试开仓提交。
4. 管理项失败、阻断、恢复中或提交结果未知，只影响自身状态与告警；开仓项仍被尝试。
5. 开仓项失败也不回滚管理项。每个失败均独立告警。
6. 任何请求结果未知均不可自动重试；保留为人工核对状态。明确拒绝可按现有安全策略处理。

## 安全与幂等

- 每个指令项以原始消息、项序号、动作类别和策略归属生成稳定幂等键。
- 提交前写入持久化 reservation；重启后不会重复执行已提交或结果未知的项。
- 同币种、同方向的长期与短期策略可以并存，前提是消息明确给出独立策略；不以“同币种已有仓位”推断或合并它们。
- 旧策略管理仍沿用精确策略、持仓和订单身份匹配，不会因同消息新策略而放宽归属校验。

## 可观测性

每条消息形成一个编排摘要，列出每个项的序号、动作、目标策略、状态、订单/批次 ID 和错误原因。管理失败告警包括腿与订单诊断；开仓失败告警包括交易所拒绝或不确定提交状态。摘要明确标出“后续开仓已继续尝试”。

## 验收测试

- 管理成功后开仓成功。
- 管理失败后仍提交并成功开仓。
- 管理成功、开仓失败，且不回滚管理。
- 同币种同方向的长期与短期策略分别获得独立绑定。
- 重复投递、服务重启、管理提交未知和开仓提交未知均不重复下单。
