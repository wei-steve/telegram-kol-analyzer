# 策略终止时清理未成交入场腿设计

## 背景

2026-07-27，大镖客策略 `deepcoin:-1003048800035:4106:BTC:short`
由一条 5 张市价入场腿和一条 16 张计划委托入场腿组成。第一条腿的仓位退出后，
生命周期被标记为 `exited`，但第二条腿仍在 Deepcoin 待触发。超时复核查询只
处理 `pending_entry` 和 `entered` 生命周期，因此已安排的下一次提醒也不再发送。

事故暴露了两个相互关联的问题：

1. 系统以 binding 的 `open/active` 状态近似判断真实执行暴露；binding 进入
   `unknown` 后，仍存活的入场腿不再阻止生命周期终态化。
2. 生命周期终态化和未成交入场腿清理不是同一个安全边界，主仓退出不保证剩余
   入场订单同步撤销。

## 已批准行为

- 第一条腿的主仓完全退出时，所有仍未成交的入场腿默认自动撤销。
- 不保留“继续等待旧策略第二腿”的隐式行为；如需再次入场，应创建新策略。
- 该规则是不可关闭的生产安全约束，不增加功能开关，不使用 shadow 模式。
- 不新增独立后台循环；历史异常兜底并入现有 Deepcoin 对账流程。
- 不改变第一遍识别、策略归属或上下文多信息解析。

## 核心不变量

生命周期只有在其 execution binding 的全部入场腿均满足以下任一条件后，才能
进入 `exited`、`expired`、`cancelled` 或 `invalidated`：

- 已成交并形成的仓位已经确认退出；
- 已由交易所确认撤销；
- 交易所回读确认订单已不存在；
- 已以其他可审计的终态结束。

任何没有 `pos_id` 且本地状态为 `open`、`pending`、`submitted`、
`partially_filled` 或 `partial` 的 entry leg 都属于未解决执行暴露。binding
即使为 `unknown`、`stale` 或存在持仓归属冲突，也不能使该暴露失效。

## 架构

### 统一执行暴露判断

扩展 `lifecycle_exit_intents` 中的判断，使“存在真实执行暴露”包含：

- binding 为 `open/active`；
- 存在非终态、未形成 `pos_id` 的 entry leg；
- 存在已验证且仍在交易所的持仓腿。

消息识别、生命周期监控和其他状态写入方统一使用这一判断，不再各自根据
binding 状态猜测。

### 统一终止前清理

在现有 Deepcoin 持仓写锁内增加终止前清理协调器。协调器：

1. 读取 lifecycle、binding、entry legs 和 Deepcoin 实时委托；
2. 只选择具有精确 `order_id` 或 `client_order_id` 的目标 entry legs；
3. 复用现有 `cancel_pending_entry_legs` 执行精确撤单；
4. 对普通委托和计划委托分别回读；
5. 持久化 trade signal、execution event、entry leg 终态和 binding 订单集合；
6. 返回 `resolved`、`already_absent`、`blocked` 或 `unknown`。

人工全平和自动 full exit 在提交平仓前先完成清理，以消除“平仓后旧挂单重新
开仓”的窗口。交易所止损、止盈或外部人工平仓已先发生时，对账流程先完成剩余
入场腿清理，再终态化 lifecycle。

### 生命周期监控边界

K 线生命周期监控器不拥有真实交易所撤单权限。它生成模拟退出转换后，持久化
前必须检查真实执行暴露。只要存在未解决 entry leg 或真实持仓腿，就跳过模拟
终态转换，交由 Deepcoin 对账和执行路径处理。

超时复核仍用于非终态待入场腿，但不再承担终态清理职责。终态 lifecycle 中
出现非终态 entry leg 视为违反不变量，由现有对账周期立即处理。

### 对账兜底

现有 Deepcoin reconciliation 每轮增加一次有界查询：

- lifecycle 已终态；
- execution binding 存在；
- 至少一条 entry leg 非终态且没有 `pos_id`。

每个异常只按数据库保存的精确订单身份读取交易所。身份唯一时自动撤销并回读；
身份缺失、冲突或交易所结果未知时不猜测、不批量撤单，记录紧急事故并阻止通过
数据库改状态掩盖真实订单。

## 顺序与幂等

所有主动全平遵循固定顺序：

1. 取得共享交易写锁；
2. 读取并冻结目标 binding 与 entry leg 身份；
3. 撤销未成交入场腿；
4. 回读确认撤单；
5. 提交精确持仓全平；
6. 由后续对账确认仓位消失；
7. 终态化 lifecycle 并清理超时复核调度。

每笔清理使用由 binding、entry leg、order ID 和终止原因组成的稳定幂等身份。
重复请求、服务重启或重复对账只能复用已有结果。结果未知的交易所请求不得自动
重提；必须先回读。

## 通知与审计

清理动作继续写入 `execution_events`。对终止清理事件增加独立、持久化的通知
状态和确定性指纹，支持 `pending`、`delivering`、`delivered`、`failed`。

- 自动撤销成功：发送“策略终止，遗留入场腿已自动撤销”。
- 订单已不存在：发送“交易所已无该订单，终止清理已确认”。
- 身份不精确、撤单失败或结果未知：发送最高优先级人工处理通知。

通知发送失败不回滚已经完成的减风险动作。通知可以有限重试，但同一清理指纹
只能产生一条最终通知。Telegram 返回的消息 ID 或失败摘要必须持久化，不能再
只记录“进入发送流程”的时间。

## 失败语义

- 撤单成功且回读消失：entry leg 标记 `cancelled`。
- 首次回读已不存在：标记 `cancel_absent_confirmed`，允许继续终态流程。
- API 超时或响应未知：立即回读；仍无法证明消失时返回 `unknown`，禁止终态化。
- 回读仍存在：返回 `blocked`，禁止平仓请求继续执行，避免留下重开仓窗口。
- 精确订单身份缺失：禁止猜测撤单，记录紧急事故。
- binding 为 `unknown` 但 entry leg 精确：允许撤销，因为该动作只减少风险。
- 通知失败：保留业务结果，重试通知，不重试已经确认的交易所动作。

## 数据迁移

若选择在 `execution_events` 上保存通知状态，新增字段均为可空列，并由 SQLite
兼容迁移幂等添加。历史事件不回填；只有新的终止清理事件进入通知队列。

部署后首次对账直接执行不变量修复。上线前的只读交叉核对用于确认目标身份，
不是 shadow，也不改变部署后的默认行为。

## 测试与验收

测试必须覆盖：

1. binding=`unknown` 但存在 pending entry leg 时仍视为真实执行暴露；
2. 人工全平先撤第二腿、确认消失后才提交平仓；
3. 撤单失败、超时或回读仍存在时零平仓提交且 lifecycle 非终态；
4. KOL full exit、最终止盈、止损完全退出和外部人工平仓使用相同不变量；
5. K 线监控不能终态化仍有未解决 entry leg 的 lifecycle；
6. 终态 lifecycle + pending leg 可由现有对账周期自动修复；
7. 多策略、多 binding 时只撤销精确目标订单；
8. 重启和重复对账不重复撤单、不重复通知；
9. 通知失败可重试且不会回滚撤单；
10. 现有 full-exit deferred-entry 测试、持仓归属测试和保护单测试全部通过。

生产验收必须在服务器完成：确认分支提交、服务健康、自动交易设置、全部真实
持仓、普通委托、计划委托、entry legs、execution events 和 Telegram 通知一致。
不得通过新建真实仓位来验证。

## 部署与回滚

不增加运行时开关。完成本地测试和代码审查后，推送
`codex/deepcoin-auto-trading-v1`，通过标准 GitHub 拉取、editable reinstall
和 `telegram-kol.service` 重启流程一次性部署。

部署前必须证明没有正在执行的时间敏感策略操作。部署后立即执行只读全账户交叉
核对并观察一次自然对账。若实现存在缺陷，回滚方式是撤回该修复提交、重新部署
前一已知良好版本；已确认完成的撤单不做反向恢复。
